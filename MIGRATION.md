# Moving tierstore out of kbf

This is the plan. Nothing in it has happened yet. After review it is carried out in the order below. No
code lands on `main` here before the plan is agreed.

## What moves

| From kbf | To this repository | Notes |
|---|---|---|
| `crates/tierstore/` (213 files: the library, the `tierstore` binary, `docs/`, `site/`) | `crates/tierstore/` | in the import commit (see History) |
| `crates/objstore-s3/` | `crates/objstore-s3/` | the S3 client tierstore uses. kbf keeps using it too (see below) |
| `packaging/tierstore/` | `packaging/` | the systemd unit, the README of the package, the sample configuration |
| `.github/workflows/tierstore-site.yml`, `tierstore-site-publish.yml` | `.github/workflows/` | rewritten for this repository (CI, release, site) |
| the tierstore sections of `.config/nextest.toml` | `.config/nextest.toml` | with the per-test overrides that guard against hangs |

## What stays in kbf

- **The site infrastructure program** (`infra/site`). It serves kbf.dev and tierstore.dev from one program, so it
  stays. Only the repository that tierstore.dev's publish role trusts changes (see "The site").
- **kbf's own crates.**
  - kbf-front and kbf-task use tierstore. After the move they depend on this repository by git, pinned to a
    commit: `tierstore = { git = "https://github.com/komira-ai/tierstore", rev = "<sha>" }` with a comment naming
    the tag, as kbf already pins its other git dependency. kbf's root `Cargo.toml` names it once.
  - kbf-front uses tierstore as a normal dependency (`server::presign_put`), so every kbf-front build compiles
    tierstore's server code from git. Whether `presign_put` belongs in objstore-s3 instead is an open question.
- **objstore-s3.** It moves here, because tierstore must not depend on anything in kbf. kbf depends on it by
  the same pinned commit. `kbf-objstore` keeps re-exporting it, so kbf code does not change.
- **tierstore-bench.** It stays in kbf for this move, with its workflow, so benchmark campaigns in progress are
  not interrupted. It gets objstore-s3 by the same pinned commit, and keeps using `kbf-testkit` in kbf. Moving it
  is a separate step later.
- **The layering test.** kbf's `kbf-integration-test/tests/layering.rs` checks that tierstore and objstore-s3
  name no kbf crate. Its tierstore and objstore-s3 clauses are deleted with the move (here, no kbf crate exists
  to depend on); its tierstore-bench clause stays.

## Dependencies to cut first

- **The S3 client.** tierstore's `s3` feature uses `kbf-objstore` today, and so do its tests (`kbf-objstore` with
  the `testkit` feature, in `tests/s3_front/*`, `cache_cli_tests`, `keep_s3_tests` and others). kbf#2094 (open)
  switches all of them, tests included, to `objstore-s3` (and its testkit). It lands in kbf first.
- **The test helper.** tierstore's tests and objstore-s3's (`tests/s3_wire.rs`: `port::{Reserved, is_taken,
  dead_addr}`) use `kbf-testkit` as a dev-dependency. The helpers they use are copied, unchanged, into a
  `tierstore-testkit` dev crate here, which serves both crates. tierstore-bench keeps `kbf-testkit` in kbf.
- **Workspace dependencies.** tierstore's `Cargo.toml` uses `workspace = true` for most dependencies. This
  repository gets its own root `Cargo.toml` with the same versions as kbf's at the moment of the import. Its
  `Cargo.lock` is generated by cargo, not copied.

## History

The import is one commit, with no history rewritten anywhere:

1. Copy the paths in the table above from kbf `main` at the cut commit, renaming `packaging/tierstore/` to
   `packaging/`.
2. Commit them as one commit. The message is `Import tierstore from komira-ai/kbf at <full sha>`, with the body
   `History before this commit: komira-ai/kbf, paths crates/tierstore, crates/objstore-s3, packaging/tierstore.`
3. Push it to a branch here, `import/from-kbf`, and open it as a pull request against `main`.

The trade: `git log` and `git blame` here start at the import commit, and the authors of earlier changes are
credited by kbf's history, which the import commit names. Nothing is lost: kbf is public and keeps the full
history of these paths. No history-rewriting tool is used, on kbf or on a copy of it.

**Scan before the first push.** A script runs over every file of the imported tree and the import commit's
message, and refuses the push on any match. It looks for:
- host names and private addresses;
- account or session names;
- endpoints other than loopback or documentation examples;
- dates before 2026-09-01.

## Order

1. **Land what is in flight.** In kbf, land these tierstore pull requests, in order:
   - the drain (#2129), the listen addresses (#2130), the cache lock (#2133) and the test fix (#2142);
   - kbf#2094;
   - the cache scrub (#2047) and the streamed cache reads (#2050).

   They come across in the import.
2. **The cut.**
   - The import is cut from one named kbf commit, which is announced. The announcement also names the last kbf
     release that carries a tierstore asset (the rollback target, see step 5).
   - After the cut, no tierstore change merges in kbf, and new tierstore work opens here.
   - A kbf pull request still open at the cut is re-opened here by its owner, as a cherry-pick of its commits.
     The paths are the same, so most apply cleanly. The kbf pull request is closed with a link to the new one.
   - The cut waits for the work in step 1 to land.
3. **Import.**
   - Before copying, the importer runs `git diff <cut>..origin/main -- crates/tierstore crates/objstore-s3
     packaging/tierstore` in kbf, and refuses to go on if it is not empty. A change that landed after the cut
     is applied here as a follow-up commit.
   - Copy the paths at the cut commit as one commit (see History), scan, push `import/from-kbf`, and open the
     pull request.
   - Then add the new root `Cargo.toml`, `tierstore-testkit` and the CI workflows. CI here must be green on the
     import before it merges.
4. **First release here.** Tag `vX.Y.Z` (the next version after kbf's last tierstore release). Build the binaries
   and checksums the way kbf's release did. The release notes say where tierstore came from.

   **4b. Hosts accept releases from here.** This is a kbf pull request (code, with tests). It makes kbf's
   installer accept this repository's `artifacts.yml` signer for the tierstore asset only, alongside kbf's. The
   signer is fixed in the installer's code today. That change is released and rolled out to hosts before any
   host installs the first release from here. kbf's signer stays accepted until the rollback window closes
   (step 5).
5. **Switch kbf.** One kbf pull request does all of this:
   - repoints `tierstore` and `objstore-s3` to the pinned commit of the release tag;
   - adds `https://github.com/komira-ai/tierstore` to cargo-deny's `allow-git`, as kbf's other git dependency is;
   - deletes `crates/tierstore`, `crates/objstore-s3`, `packaging/tierstore` and the tierstore site workflows;
   - deletes the layering test's tierstore and objstore-s3 clauses;
   - stops building and releasing the tierstore asset in kbf's release;
   - updates the kbf docs that name those paths (for example `docs/artifacts.md`, `docs/deploy/kbf-modes.md`,
     `ARCHITECTURE.md` and the design docs) to point here;
   - keeps kbf's CI green.

   **Rollback.** The last tierstore asset released from kbf stays on its release and is the rollback target.
   Hosts keep accepting kbf's signer for it until releases from here have run on every host.
6. **The site.** tierstore.dev's build and publish workflows move here. The site infrastructure program stays in
   kbf; only the publish role's trusted repository changes. The one-time setup (see "The site" below) is done
   once, against this repository. The tierstore paper's link to the code is repointed here when the import
   merges.

## CI, release, the site and the hosts

**CI.** The CI here starts as a copy of the parts of kbf's CI that these crates use.
- `ci.yml`:
  - `cargo fmt --check`;
  - cargo-deny (bans, licences, sources) with the same pinned release as kbf;
  - clippy with `-D warnings`, on default features and on `--features server`;
  - nextest under llvm-cov, with a 99% line and 99% branch gate per crate (a copy of kbf's coverage gate tool,
    which links nothing of kbf).
- Hang guards live only in `.config/nextest.toml`. No test asserts or depends on timing.
- Repository lints:
  - every `uses:` pinned to a commit with a version comment;
  - a top-level `permissions: {}`;
  - `id-token: write` only on the signing jobs;
  - no `pull_request_target`.
- A daily advisories check that opens one issue.

**Release.**
- `artifacts.yml` builds `tierstore` (`--features server --bin tierstore`) for linux-x86_64 and linux-arm64.
  It packages each the way kbf does: `tierstore-<commit>-<platform>.tar.gz`, a CycloneDX SBOM, and `SHA256SUMS`.
- On `main`, a signing stage attests build provenance per file and the SBOM per tarball. The signing identity
  is this repository's `.github/workflows/artifacts.yml`.
- `release.yml` attaches exactly those files and verifies the attestations again. It never rebuilds.
- Because the signing identity changes, kbf's installer must accept the new signer before a host installs a
  release from here (step 4b).

**The site.** tierstore.dev keeps its domain. Its build and publish workflows (today in kbf) move here. A
maintainer does the one-time setup once, against this repository, at step 6:
- a `prod-site-tierstore` environment limited to `main`, with the bucket, distribution id and publish role
  variables;
- the publish role's trust pinned to this repository's numeric id.

Then the publish workflow runs here. kbf's two site workflows are removed in the switch PR (step 5). kbf.dev is
not touched.

**The hosts.**
- Hosts install tierstore with kbf's installer. The installer verifies the release tarball's attestation against
  a fixed signer.
- Step 4b makes it also accept this repository's signer for the tierstore asset, before the first release here is
  installed.
- Later updates go through the generic host updater, with tierstore's own update hook (planned work, below).

## Open pull requests in kbf

- **Landing before the cut:** the pull requests in step 1, in that order. They come across in the import.
- **Planned work.** The update hook is the next piece of planned work. It starts here, after the import.
- **Everything else.** Any other tierstore pull request still open in kbf at the cut is re-opened here by its
  owner (step 2).
