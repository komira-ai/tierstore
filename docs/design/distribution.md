# Distribution: testing first, install checks, the lab through hostkeeper, then the public channels

Status: **proposal, for review; the parts marked "built" below are in the code.** Built so far (against the order of 2026-11-07, which this revision replaces): `release tap-tarball` and `release deb` with the extended `release check` (the files of section 3), `channels gate`, `channels upload`, `channels formula` and `channels tap`, `channels apt read`, `index`, `sign` and `write` (all for the one suite `stable`), and `channels soak` with the jobs `farm-check`, `farm` and `soak`, the public jobs waiting for `soak`. **Not built, and what this revision asks for** (section 10 says in which pull request): the suite as a parameter of the apt verbs and the `testing` jobs; `channels apt promote`; `channels upload --no-latest` and `channels latest`; the jobs `formula`, `check-apt`, `check-brew`, `check-install-sh`, `promote-check` and the `stable-apt-*` jobs; `channels decide`; the lab stage repointed at the testing `.deb`; and a soak of more than 0 hours, which needs a read-only call that hostkeeper's CI client does not have yet (5.3); `FARM_SOAK_HOURS` stays `0`. It is a living document: each pull request that builds a part of it changes the part's section from "will" to what the code does (AGENTS.md P10), and a decision that changes is changed here first. What it says about the repository was read in `.github/workflows/release.yml`, `.github/workflows/tierstore-site-publish.yml`, `crates/xtask/` and `packaging/` on main at the time of writing. What it says about the sibling repositories (buildrules, homebrew-tap, komira-internal, hostkeeper) and the sibling site's CDK app was read in checkouts of them at the time of writing and is cited by file. **Revision of 2026-11-08: the owner decided the release order** (replacing "the farm first, then public" of 2026-11-07): publish to **testing** (the `.deb`s into the shared pool and the apt suite `testing`; the release files to `releases/<V>/` without moving `latest.json`; the formula rendered, no tap pull request), run the **install checks** against testing, install on the **lab** through hostkeeper, then **promote the same bytes** automatically: the apt suite `stable`, `latest.json`, the tap pull request (section 5).

## 1. The problem

A tierstore release today is a GitHub release (`release.yml`): the commit-named tarballs, SBOMs, hostkeeper packages, provenance bundles, `index.json` and `SHA256SUMS`. That is what a host operator with hostkeeper takes. Everybody else has nothing to install from: no `brew install`, no `apt install`, no stable URL that does not need a GitHub login on a browser, and no site. tierstore.dev is a domain the project has; the site's source is in `crates/tierstore/site` and `tierstore-site-publish.yml` publishes it, but the cloud side (bucket, CDN, certificate, the roles the workflows assume) does not exist: neither the `tierstore-dns-zone` nor the `tierstore-prod-site` CloudFormation stack is deployed, and its CDK app is in the sibling repository (`infra/site`), which lists `tierstore.dev` as a second site.

What the user wants:

- `brew install komira-ai/tap/tierstore` on macOS (Apple silicon) and Linux (x86_64, aarch64).
- `sudo apt install tierstore` on Debian and Ubuntu (amd64, arm64) from `packages.komira.ai`, the apt repository the organisation's products share.
- A file anyone can `curl` from `https://tierstore.dev/releases/<version>/`, and `https://tierstore.dev/releases/latest.json` that says which version is the newest.
- All of it from the release that already happens by itself on every push to main that changes code: no manual tag, no human verdict (AGENTS.md B12). Every release that has passed the install checks (and the lab, where configured) goes to every public channel.
- A release is tried before anybody outside is pointed at it: it is published to a **testing** place (the apt suite `testing`, `releases/<V>/` on tierstore.dev, a rendered formula), installed from there on clean machines by the way a user installs (apt, Homebrew, `install.sh`), and, where hostkeeper's side is configured, installed on our lab by hostkeeper and kept healthy for N hours (a configuration value, `0` for now). Only then do the public pointers move: the apt suite `stable`, `releases/latest.json` and the Homebrew pull request. The bytes are the same at every step; nothing is rebuilt.
- Nothing runs on the project's side until the owner has made the one-time settings, and the merge of the pull requests that carry this design breaks no release.

## 2. The design

| | Before | After |
|---|---|---|
| Release files | GitHub release: commit-named tarballs, SBOMs, hostkeeper packages, bundles, `index.json`, `SHA256SUMS` | the same, plus `tierstore-<V>-{macos-arm64,linux-aarch64,linux-x86_64}.tar.gz` (and their bundles) beside the commit-named ones |
| tierstore.dev | nothing deployed | CDK app in `infra/site` of this repository: a bucket behind a CDN, the zone, the certificate and two roles |
| `https://tierstore.dev/releases/<V>/` | nothing | written at the testing stage, before any check; the tap-named tarballs, their bundles, `tierstore_<V>_amd64.deb`, `tierstore_<V>_arm64.deb` and the directory's `SHA256SUMS`, written once (the bundles of the `.deb`s too: the build job signs them) |
| `https://tierstore.dev/releases/latest.json` | nothing | the newest **promoted** version and its files, written at promotion, never to an older version |
| Homebrew | nothing | the formula is rendered at testing and installed from a local tap by the checks; at promotion `komira-ai/homebrew-tap` gets `Formula/tierstore.rb` by a pull request from the release bot |
| apt | nothing | `packages.komira.ai` lists `tierstore` for amd64 and arm64 in the suite `testing` at once, and in `stable` at promotion |
| the lab | hand-installed; a release reaches it when somebody runs `hostkeeper-desired.yml` | hostkeeper installs the testing `.deb` and the coordinator moves the lab, by `release.yml` (section 5.3), when its settings exist; absent, the stage is skipped and promotion goes on |
| `release.yml` | `plan`, `verify`, `publish` | the same three, then the testing jobs, the install checks, the lab stage and the promotion jobs (section 5) |

What does not change (section 9): the existing release files and their names, the hostkeeper packages and the update hook, the signer of every attestation (`artifacts.yml` on `refs/heads/main`), and the key the shared apt repository is signed with.

Decisions, from the owner:

1. **tierstore.dev's CDK moves into this repository** at `infra/site`. The repository is the one the OIDC trust names; the site and the release files belong to the project that produces them.
2. **apt only**; no rpm yet. The shared repository keeps `apt/` as a prefix so a later `rpm/` fits beside it.
3. **Every release that passes goes to every public channel**: there is no "stable" or "latest only" subset, and the public channels do not wait for one another once promotion is decided.
4. **Packages are public artifacts of the site**: `https://tierstore.dev/releases/<V>/` (write-once) and `releases/latest.json`. The tap and apt do not depend on it (section 4 says where each reads from); it is the stable URL.
5. **Homebrew** through the organisation's tap, `komira-ai/homebrew-tap`; **apt** through `packages.komira.ai`, package name `tierstore`.
6. **Testing, checks, lab, promotion** (2026-11-08, replacing the farm-first rule of 2026-11-07). A release is published to testing, install-checked against it, installed on the lab through hostkeeper when the lab is configured, and then the same bytes are promoted. The lab stage is skipped, with a notice, when its settings are absent, and **does not block promotion**; when present it must converge healthy and then soak for N hours, the repository variable `FARM_SOAK_HOURS` (`0` for now), read by `release.yml` and passed to the tool as a flag (AGENTS.md S2). The soak is a timer, automatic; no person approves anything (B12).
7. **One apt repository, two suites.** `testing` and `stable` live in the shared repository `packages.komira.ai`, signed with the one shared key; the `.deb`s are in the one shared pool, written once at testing. Promotion adds index entries to `stable` and writes no package.

## 3. The files of a release

For a version `V` (`X.Y.Z`, the tag without the `v`) and a commit `C`.

**Tap-named tarballs.** The tap's guard accepts a formula only if it equals its template line for line (`.github/guard/guard.js` in homebrew-tap, `template`), and the template fixes where the files are and what they are called: `https://github.com/komira-ai/tierstore/releases/download/v<V>/tierstore-<V>-<target>.tar.gz`, for the targets `macos-arm64`, `linux-aarch64` and `linux-x86_64`, with `bin.install "tierstore"` and a test that runs `tierstore --version` and wants `tierstore <V>` in it. So the Homebrew files must be assets of the GitHub release, under these names. They cannot be the files on tierstore.dev, and the platform name for arm64 Linux is `aarch64` there, where the commit-named file says `linux-arm64`.

Each is a **copy of the commit-named tarball with the same bytes**, under the tap's name: `tierstore-<V>-macos-arm64.tar.gz` is `tierstore-<C>-macos-arm64.tar.gz`, `tierstore-<V>-linux-aarch64.tar.gz` is `tierstore-<C>-linux-arm64.tar.gz`, and `tierstore-<V>-linux-x86_64.tar.gz` is `tierstore-<C>-linux-x86_64.tar.gz`. Nothing is repacked, so:

- the SHA-256 in the formula is the one `SHA256SUMS` already lists for the commit-named file, and the formula is rendered from that one file (nothing is downloaded or hashed to make it);
- the attestation of the commit-named tarball is an attestation of this file too (it names a digest), so `gh attestation verify` on either passes, and no new signing step and no new signer is needed. Each tap-named tarball is published with a copy of its tarball's bundle, `<name>.sigstore.json`;
- the tarball holds `tierstore` and `THIRD-PARTY-LICENSES.txt`, and `bin.install "tierstore"` finds the binary at the top, as the tap expects (`docs/ci-and-release.md` says how a host extracts it by name).

`SHA256SUMS` is not changed: it is produced and checked by `artifacts.yml`, the signer's workflow, and the copies need no line of their own. `cargo xtask release check` learns the copies as a rule instead: a file named `tierstore-<V>-<platform>.tar.gz` must exist for each commit-named tarball and have its digest. A tap-named file with other bytes, or one missing, fails the `verify` job before anything is published.

**Debian packages.** `tierstore_<V>_amd64.deb` and `tierstore_<V>_arm64.deb`, made in the `verify` job (no token) from the verified linux tarballs by `cargo xtask`, byte for byte the same for the same inputs: members and entries sorted, owner root, one modification time (the commit's committer time, passed as a flag), no time in the gzip header. That matters twice: the package is never attested (the attestation is the tarball's), so anyone can rebuild it from the tarball and compare; and a `.deb` is written to the pool once and never replaced, so a re-run must produce the same bytes (section 8).

| path in the package | from |
|---|---|
| `/usr/libexec/tierstore/tierstore` | the tarball's binary (the path `packaging/tierstore.service` runs) |
| `/usr/lib/systemd/system/tierstore.service` | `packaging/tierstore.service` |
| `/usr/lib/sysusers.d/tierstore.conf` | `packaging/tierstore.conf` |
| `/usr/share/doc/tierstore/examples/tierstore.toml` | `packaging/tierstore.toml` (an example, not read by anything; `/etc/tierstore` is the operator's) |
| `/usr/share/doc/tierstore/copyright`, `THIRD-PARTY-LICENSES.txt` | the project licence and the tarball's notice |

- **Not started on install.** The unit has no `[Install]` section and the package does not enable or start it; the operator copies the example to `/etc/tierstore`, edits it and starts the unit (`packaging/README.md`). The only maintainer script is a `postinst` that creates the account from the sysusers entry (`systemd-sysusers`) and runs `systemctl daemon-reload` when systemd is running. Removal leaves the account and `/etc/tierstore`; the package says so.
- `Architecture:` `amd64` or `arm64`; `Version:` is `V`; `Depends:` nothing the static binary does not need (the control file is listed in the pull request that writes it).
- The hostkeeper packages (`.tar.zst`) are not in the `.deb` and not on tierstore.dev: hostkeeper's channel is unchanged.

**On tierstore.dev.** `releases/<V>/` holds the three tap-named tarballs and their bundles, the two `.deb`s and their bundles (the build job attests the packages, so a bundle exists for each and is published with it), and `SHA256SUMS`, which lists exactly the files of that directory (it is not the release's `SHA256SUMS`, which lists the commit-named files; a tap-named tarball's line here equals the commit-named line there). `releases/latest.json`:

```json
{"version": "X.Y.Z", "tag": "vX.Y.Z", "commit": "<40 hex>",
 "files": {"tierstore-X.Y.Z-linux-x86_64.tar.gz": {"sha256": "<64 hex>", "size": 0}}}
```

`files` lists every file of `releases/<V>/` except `SHA256SUMS`. The format is additive from the start (AGENTS.md B8): a reader ignores a key it does not know, and a later release may add keys.

**The install script.** `https://tierstore.dev/install.sh` is `crates/tierstore/site/static/install.sh`, a POSIX `sh` script that the site build copies to the root of `dist/` (the one file of the site that is not a page, a script or a stylesheet; it is uploaded as `text/x-shellscript` with the pages' short cache, so it is replaced with the site and never touches `releases/`). It takes flags only (`--version`, `--prefix`, `--system`, `--base-url`), reads `releases/latest.json` for the newest version, downloads `tierstore-<V>-<platform>.tar.gz` and `SHA256SUMS` from `releases/<V>/` for Linux x86_64, Linux aarch64 or macOS arm64, and installs the binary only if the tarball's SHA-256 is the one listed. It writes to `~/.local/bin` (or `/usr/local/bin` with `--system`, using `sudo` only when the directory is not writable), starts nothing, and on another platform stops with the Homebrew and apt commands. The check catches a damaged download; it does not prove who built the file, because the sums come from the same address (the provenance bundles do, and the install guide says how to check them).

## 4. The cloud side: `infra/site`

A CDK app (TypeScript, us-east-1), copied from the sibling repository's `infra/site` (`README.md` there is the description of what it builds) and cut down to the one site; the held steps (`held/main.ts`) come with it. What the stack builds is the the sibling site design as it stands, so a reviewer who knows it reads only the differences:

- a **private bucket** behind a CDN with origin access control, a Route 53 zone, a certificate, a headers policy (one Content-Security-Policy) and a router function;
- the site at the root of the bucket; `releases/<V>/` and `releases/latest.json` beside it. Pages are served `public, max-age=60, s-maxage=300`; `latest.json` is written `public, max-age=60`, so a release is visible within a minute without an invalidation. The upload job still invalidates `/releases/latest.json` when the variable `TIERSTORE_RELEASES_DISTRIBUTION_ID` is set (`channels upload --distribution-id`; empty means none), which shortens that minute, and the role as built (`infra/site`) may create invalidations; a file of `releases/<V>/` is immutable (`max-age=31536000, immutable`).
- stack names `tierstore-dns-zone` and `tierstore-prod-site`, bucket `tierstore-prod-site-<account>`. Neither stack exists, so nothing is replaced when the names are written; the account is a CDK context value and a flag of the held steps, never in a file (AGENTS.md S1).

**Two roles, assumed by GitHub OIDC; no stored key.** The repository's subject template is the default with the immutable subject, so a role trusts `sub = repo:komira-ai@<owner id>/tierstore@<repo id>:environment:<env>` (the ids are read by the held step from `gh api`, which refuses a repository whose name differs from the one given, as in the sibling app; they are not written in a file), and the `job_workflow_ref` and `environment` claims as well:

| | `tierstore-prod-publish` (site) | `tierstore-prod-releases` (release files) |
|---|---|---|
| workflow it trusts | `.github/workflows/tierstore-site-publish.yml` at `refs/heads/main` | `.github/workflows/release.yml` at `refs/heads/main` |
| GitHub environment | `prod-site-tierstore` | `prod-releases-tierstore` |
| may write | the site's objects at the root, and delete them in the sync; **no write under `releases/`** | `releases/<V>/*` only with `If-None-Match` (write-once); `releases/latest.json` only with `If-Match` or `If-None-Match` |
| may read | the bucket's listing (for the sync) | `GetObject` on `releases/*` (the files are public; this is for the re-run check, section 8), and `ListBucket` on the bucket only under the `releases/` prefix, so a missing `latest.json` answers `NoSuchKey`, not `AccessDenied`. Granted by the stack since this pull request; the open question on the role as built having no read is resolved by it |
| may invalidate | the one distribution | nothing |
| delete | the site's own objects | **never**; the bucket policy also denies `DeleteObject` and `DeleteObjectVersion` on `releases/*` to every principal |

Today's `publish.ts` already excludes `releases/` from every upload and from `--delete`; the role's policy turns that convention into a rule the program cannot break. The policy is pinned by a TypeScript test of the synthesized template (the language of the component, AGENTS.md T11); the conditions (`s3:if-none-match`, `s3:if-match`, `s3:ObjectCreationOperation` for multipart parts) are policy text and are not exercised against AWS by any test: the first release's upload is the proof, and a refusal there is a red `channel-upload` job and nothing else (section 8). The bucket is versioned, so a wrongly overwritten `latest.json` is restored by copying the previous version back, an administrator step.

**The workflow `tierstore-site-publish.yml` is not changed** by this design: it already names the three variables (`TIERSTORE_SITE_BUCKET`, `TIERSTORE_SITE_DISTRIBUTION_ID`, `TIERSTORE_SITE_PUBLISH_ROLE_ARN`) of the environment `prod-site-tierstore` and is off until `TIERSTORE_SITE_PUBLISH` is `true`.

**Supersession (AGENTS.md B22).** Copying is not moving: the sibling repository keeps its own `infra/site` (it serves the sibling site, with golden tests that pin every the sibling site name) and its `SITES` entry for tierstore.dev stays valid until the owner has deployed from here. Removing that entry, and the note in its README that the trust is "not moved yet", is a separate pull request in that repository, after the deploy of section 7 step 6. Two apps must not deploy the same stack, so the owner deploys from one of them only: from here (section 7), and the sibling repository's entry is removed once that has happened.

## 5. The jobs of `release.yml`

`release.yml` keeps its shape: `plan` (read), `verify` (read; builds nothing that holds a token), `publish` (the one `contents: write`). `verify` gains the steps that make the copies and the packages (`cargo xtask release channel-files`) and checks them; the GitHub release gains the tap-named tarballs and their bundles as assets (they are in `release-assets`); the packages go in a second artifact, `channel-files`, that no `release check` lists, because they are not assets of the GitHub release.

The release moves through four stages after `publish`, in the owner's order (2026-11-08): **testing**, **install checks**, **the lab**, **promotion**. The same bytes go through all four; nothing is rebuilt.

| stage | jobs | what it does | where the release is afterwards |
|---|---|---|---|
| testing | `formula`, `testing-upload`, `testing-apt-read`, `testing-apt-index`, `testing-apt-write` (and the attempts `-2` and `-3` of the three apt jobs) | the `.deb`s into the shared pool and into the apt suite `testing`; the release files to `releases/<V>/` (write-once) without touching `releases/latest.json`; the Homebrew formula rendered and kept as an artifact, no tap pull request | GitHub release, tierstore.dev `releases/<V>/`, apt `testing`, a formula artifact |
| install checks | `check-apt` (amd64 and arm64), `check-brew`, `check-install-sh` (Linux and macOS) | install the release from what testing holds, the way a user would, and run `tierstore --version` (section 5.4) | unchanged |
| the lab | `farm-check`, `farm`, `soak` | hostkeeper installs the testing `.deb` on the lab and the job waits until the lab is healthy (section 5.3) | unchanged |
| promotion | `promote-check`, `promote-latest`, `tap`, `stable-apt-read`, `stable-apt-index`, `stable-apt-write` (and `-2`, `-3`) | the suite `stable` gets the entries testing holds, `releases/latest.json` moves, the tap pull request is opened | public: `stable`, `latest.json`, the tap |

A failed job un-releases nothing: the release is already a GitHub release and its tag exists (as in buildrules, whose `release.yml` these jobs follow). What a failure leaves is the subject of section 8: always "testing has it, public does not", or less.

| job | environment | holds | does |
|---|---|---|---|
| `formula` | none | `contents: read` | `channels formula` from the verified `SHA256SUMS`: renders `Formula/tierstore.rb` and uploads it as the artifact `formula`. Opens nothing |
| `testing-upload` | `prod-releases-tierstore` | `id-token: write`, no repository write | assumes `tierstore-prod-releases`, uploads `releases/<V>/*` with `If-None-Match`; **does not write `latest.json`** (`channels upload --no-latest`) |
| `testing-apt-read`, `testing-apt-index`, `testing-apt-write` | `apt-publish`, `apt-signing`, `apt-publish` | read job and write job: the cloud role (`id-token: write`) and no key; index job: the signing key and no role | the `--suite testing` run of the three verbs: read the suite's index, merge the `.deb`s and sign it, upload the `.deb`s to the pool and write the index of `dists/testing/`; a lost write starts attempt 2, then 3 (`testing-apt-*-2`, `-3`) |
| `check-apt`, `check-brew`, `check-install-sh` | none | `contents: read`, no secret, no token, no cloud role | section 5.4. They use the public URLs only |
| `farm-check`, `farm`, `soak` | none (`farm`: `id-token: write`) | as in 5.3 | the lab stage, repointed at the testing `.deb` |
| `promote-check` | none | `contents: read` | `channels decide`: reads the results of the jobs before it and says `promote=true` or `promote=false` (5.3, "Deciding to promote") |
| `promote-latest` | `prod-releases-tierstore` | `id-token: write` | `channels latest`: reads `releases/<V>/SHA256SUMS` from the bucket, checks every file of it against the release's `SHA256SUMS`, writes `releases/latest.json` with `If-Match` if `V` is newer |
| `tap` | `release` | `contents: read`, the release bot's token for `komira-ai/homebrew-tap` alone | opens the pull request `bump/tierstore-v<V>` in the tap as the bot from the artifact `formula` (rendered at testing, checked again against the verified `SHA256SUMS`), with auto-merge when the tap allows it |
| `stable-apt-read`, `stable-apt-index`, `stable-apt-write` | `apt-publish`, `apt-signing`, `apt-publish` | as the testing apt jobs | `channels apt promote`: reads the index of `testing` and of `stable`, takes the entries of `V` from `testing` into `stable` and checks their digests against `SHA256SUMS`; signs; writes the index of `dists/stable/` with `If-Match`; **uploads no `.deb`** (the pool already has them from testing) |

The six apt jobs and their split are copied from buildrules' `release.yml` (the `apt-*` jobs; `RELEASING.md`, "The apt repository"): no job holds both the signing key and the cloud role, so a compromise of one step cannot sign and publish. As built, the jobs of one suite are nine, three attempts of three: the `-2` read job runs only when the write of attempt 1 answered `conflict=true` (its `if:` says so, besides the `if:` of `publish`), the `-3` read job only after attempt 2's, and the write of attempt 3 passes `--last`. The role is assumed by `aws-actions/configure-aws-credentials` (pinned by SHA, as in the upload job), not by a verb of this repository: the OIDC exchange is that action's and buildrules' `apt_publish assume` is not ported. The signing key and its passphrase reach the signing step as the step's two secrets, are written by it to two files of mode 0600, and `channels apt sign` takes the files by flag (S2) and removes them, with its private keyring, when it ends. The shared repository's own role for the product (`komira-apt-publish-tierstore`) is created by the apt repository's stack in komira-internal (section 7), trusts `.github/workflows/release.yml` of this repository at main in the environment `apt-publish`, may write `apt/pool/tierstore/*` with `If-None-Match` only and the shared `apt/dists/*` with `If-Match` or `If-None-Match`, and may delete nothing. **`apt/dists/*` covers every suite**: `testing` and `stable` are two directories of the same prefix (`INDEX_PREFIX` in `infra/apt_repo/lib/config.ts` of komira-internal, read on 2026-11-08), so the grant needs no change for `testing`. The pool is shared by both suites; a `.deb` is written to it once, by the testing stage, and promotion never writes it.

**The workflow lint** (`crates/xtask/tests/workflows`, AGENTS.md B10): the new jobs go in the existing workflow, not in a new one (B9); the lint lists, for `release.yml`, which jobs may hold `id-token: write` (`farm`, `testing-upload`, `promote-latest` and the apt read and write jobs of both suites; `soak` holds none, section 5.3), under which `if:`, and that `contents: write` stays with `publish` alone. It also lists the runners of the install checks: `check-apt` on `ubuntu-24.04` and `ubuntu-24.04-arm` inside a container whose image is named by digest, and `check-brew` and `check-install-sh` on `macos-15` and `ubuntu-24.04`, each with `contents: read` alone and no `environment`; a macOS runner in `release.yml` is allowed for those two jobs only (B9 is about pull requests, and `release.yml` runs on no pull request, section 9). The `if:` of the testing jobs is the one `publish` has (`needs.plan.outputs.release == 'true' && github.ref == 'refs/heads/main'`), and the jobs after a stage that may be a green no-op also carry `!cancelled() && !failure()` (a skipped predecessor must not skip them; a failed one must). Actions are pinned by commit SHA; the release bot's token comes from `actions/create-github-app-token` pinned the same way, in the last two steps of `tap`, given to the one step that opens the pull request.

**Where each channel reads from.** The testing jobs read `release-assets` and `channel-files`; the index and write jobs check the `.deb`s against `SHA256SUMS` and the assets of the commit again, because they crossed the artifact store. **Promotion reads what testing holds**: `promote-latest` reads `releases/<V>/SHA256SUMS` from the bucket and every file's digest from `GetObject`; `stable-apt-*` read the entries of `V` in the index of `testing` from S3 (the `Filename` and `SHA256` lines); the tap pull request uses the formula rendered at testing. Each is compared with the verified `SHA256SUMS` of the release, and a difference is a red job (section 8). The install checks read the public URLs, never the bucket. The tap's template reads the GitHub release (the template fixes it), which exists before any of this runs. The lab reads the testing `.deb` through hostkeeper (5.3).

### 5.1 A job is a green no-op until its settings exist

Every channel job starts with `cargo xtask channels gate`, which is given each setting of the job as a flag `--setting NAME=VALUE` (the workflow passes the variables and secrets of the environment as environment variables of the step, and the step's `run:` line gives the gate `NAME=${VAR:+set}`: the verb reads only whether the value is empty, so a secret never reaches a command line, and reads no environment, AGENTS.md S2) and writes `enabled=true` or `enabled=false` to `$GITHUB_OUTPUT`. Every later step has `if: steps.gate.outputs.enabled == 'true'`.

| settings of the job | result |
|---|---|
| none of them set | `enabled=false`, a notice naming the job and the settings, the job ends **green**, writes nothing |
| all of them set | `enabled=true`, the job runs |
| some of them set | the job ends **red** naming the missing ones, writes nothing |

The same three rows judge `farm-check`, the job before `farm` that holds the farm's gate (a job that calls a reusable workflow has no steps of its own); its settings are in the table below, and are repository variables, as `hostkeeper-desired.yml` has them, because a job that calls a workflow cannot name an environment. The third row is the half-made settings of section 8: a typo in a variable name must not leave a channel silently off. Before the owner has begun, all the jobs are green no-ops, so merging the workflow changes no release. With `farm-check` a green no-op the lab stage is skipped with a notice and **promotion goes on** (5.3, "When the settings are absent"); this is the reverse of the rule of 2026-11-07.

|---|---|
| `farm-check` | repository variables `HOSTKEEPER_COORDINATOR_URL` and `HOSTKEEPER_COORDINATOR_CA` (the first gate, label `farm`); and, only if the coordinator is reached over the tailnet, `HOSTKEEPER_TAILNET_CLIENT_ID`, `HOSTKEEPER_TAILNET_AUDIENCE` and `HOSTKEEPER_TAILNET_COORDINATOR` (the inputs of `set-desired.yml`'s `join_tailnet`): a second gate, label `farm-tailnet`, run when the first said `enabled=true`, where none set means no join and some set is red. | `farm` | none of its own: it runs when `farm-check` said `enabled=true` |
| `soak` | none: it runs when `farm` ended with `converged=true` |
| `formula` | none |
| `testing-upload`, `promote-latest` | variables of `prod-releases-tierstore`: `TIERSTORE_RELEASES_BUCKET`, `TIERSTORE_RELEASES_ROLE_ARN`; `promote-latest` also `--require` the output of `testing-upload` and of `promote-check` |

The index and write jobs follow another job, and a job whose predecessor was off must be off too, not red for "some of its settings set": `channels gate --require NAME=VALUE` (the workflow passes the predecessor's output) turns the job off, green with a notice, unless every `VALUE` is exactly `true`, and then does not judge the job's own settings. The label of an apt gate is the job's name. This is also how promotion stays tied to testing: a `stable-apt-*` job whose testing counterpart was a no-op is a no-op.

No secret is committed in a file, and no account id, endpoint or role ARN is (S1): they are the values of the environments. The upload and write steps run `aws` from a flag-given program (`--aws`, default `aws`, as `verify-assets attestations` takes `--gh`) with the role assumed from the job's OIDC token by the SHA-pinned `aws-actions/configure-aws-credentials` step before it.

### 5.3 The lab, and the decision to promote

**What exists.** `hostkeeper-desired.yml` (by hand) already does the lab half: its `check` job (`cargo xtask release desired`) refuses a release whose hostkeeper index lacks a platform, and its `set-desired` job calls hostkeeper's reusable workflow (`set-desired.yml`, pinned to a hostkeeper release by commit), which proves that release, sets the desired version of the service `tierstore` with the job's OIDC token and reads the convergence every 10 seconds (`docs/ci-and-release.md`, "Setting the desired version on the hostkeeper coordinator"; `docs/deploy/ci-client.md` in hostkeeper). It is not changed. buildrules' `release.yml` has the same pattern for its own farm: the `gamma` job joins the farm's network by Tailscale workload identity (an OIDC token exchanged for a short-lived node, no stored key).

**What changes (2026-11-08).** The lab stage no longer comes straight after `publish` and no longer gates the public channels by being configured. It takes the **testing `.deb`** as the artifact the coordinator and the channel name: hostkeeper installs `tierstore_<V>_<arch>.deb` from the apt suite `testing` of `packages.komira.ai` (hostkeeper's packages design, pull request 188 there, which the owner is building), not the `.tar.zst` of the GitHub release. The owner builds hostkeeper's side; this repository only says which version and digest are desired. Where the hostkeeper side is not ready or the settings are absent, the stage is skipped (below).

| job | holds | does |
|---|---|---|
| `farm-check` | `contents: read` | the gate of 5.1; `release desired`, changed to check the **testing index** instead of hostkeeper's `index.json`: the suite `testing` read over the public URL lists `tierstore` `V` for amd64 and arm64 with the `SHA256` of the `.deb`s of `SHA256SUMS` (it prints the package version and the digest); then, if `HOSTKEEPER_RELEASE_CHANNEL` is set, waits (curl's own retries, 40 seconds apart, at most 30 minutes) until the channel serves what the coordinator needs for the version, because the coordinator refuses a version the channel does not hold with `not_in_channel` and `set-desired.yml` does not retry a refusal. Without the variable the step says so and relies on the refusal: if the channel is late `farm` is red, and re-running the failed jobs continues |
| `farm` | `contents: read`, `id-token: write` (the call of `set-desired.yml`, and the tailnet join when its variables are set) | hostkeeper's reusable workflow, pinned to the same commit and release as `hostkeeper-desired.yml` (the workflow lint holds the two pins equal), for the service `tierstore`, with `wait: true` and `max_polls` from `FARM_MAX_POLLS`, the audience `tierstore-hostkeeper-release`; ends green with `converged=true` when the coordinator reports the service converged on the version, red otherwise |
| `soak` | `contents: read` | `cargo xtask channels soak --hours "${FARM_SOAK_HOURS:-0}" ...`: with `0` it ends at once; with N it reads the convergence until N hours have passed since `farm` converged, and fails the moment a read shows the lab not healthy. Runs only when `farm` ended with `converged=true`. It holds no `id-token: write`, see "Reading the farm again" below |

**When the settings are absent: skipped, and promotion goes on.** While the settings of `farm-check` (5.1) are empty it is a green no-op that writes `enabled=false`, `farm` and `soak` are skipped, and the job prints a notice naming the stage and the settings. **This does not block promotion**: this reverses the rule of 2026-11-07 ("no farm, no public release"). The reason is the owner's order: the install checks of 5.4 now guard the public channels, and the lab is a second guard only where it is configured. The half-made case (some of the settings set) is still red (5.1), because a typo in a variable name must not leave the lab silently out. When the settings are present the stage must converge healthy and then soak, and a failure blocks promotion.

**Healthy, concretely.** The word means what hostkeeper reports, and the gate adds nothing of its own:

1. A host is healthy for a version when its daemon reports the service `live`, at that version, and its health check passes (a `[health]` URL answering 2xx, or no `[health]` and the version not contradicted); `stopped`, `transitioning`, `unobserved` and a `version_mismatch` are unhealthy (`docs/service-observation.md` in hostkeeper).
2. The coordinator counts a host done when it is up at the desired version and has baked `bake_beats` healthy heartbeats (`docs/operations/rollout-plans.md`). The lab's plan for `tierstore` is hostkeeper configuration, not of this repository.
3. **The lab is healthy on V** when the coordinator's convergence answer reports the service converged on V: every live host at V, none updating, none failed (`set-desired.yml`'s output `converged` is `true` and `reason` is `converged`). A host that is silent is not live and the coordinator does not wait for it; `soak` does not either: its reads fail when a role of the answer shows a host `down` (or `failed` or `updating`). `farm` cannot make that check: the called workflow gives back only `converged` and `reason`, so between the lab's convergence and the first read of a soak of more than 0 hours a silent host goes unseen.
4. A halt, or the version marked bad, is not healthy (`reason` `halted` or `held_bad`), and neither is an automatic rollback that set the desired version back to the last good one.

**Deciding to promote.** `promote-check` runs `cargo xtask channels decide`, given the result of every job before it as a flag (`--result NAME=RESULT`, the workflow passing `needs.NAME.result`) and whether the lab was enabled (`--farm-enabled`), and writes `promote=true` or `promote=false` with the reason to `$GITHUB_OUTPUT` and the step summary. A verb, not an `if:` expression, so the rule has tests with negative cases (T15):

- `promote=true` when every result is `success` or `skipped`, a `skipped` result is acceptable only for a job whose settings were absent (the job's own `enabled=false` output is given with it: a job skipped for any other reason, such as a failed predecessor, is not acceptable), and the lab stage is either off (`--farm-enabled false`) or `farm` and `soak` both `success`;
- `promote=false` on any `failure` or `cancelled`, on a skipped job that was enabled, and on a lab stage that is enabled and not both `success`.

Every promotion job runs only when `promote-check` said `promote=true` **and** its own gate (5.1) says enabled **and** its testing counterpart did its work (the counterpart's output is given to the gate as `--require`). So a channel whose testing job was a no-op is not promoted: stable never gets what testing never had.

**The soak is a timer, not a verdict (B12).** Nobody approves it and no job waits for a person. The time is measured from the moment `farm` read converged, passed to `soak` as a flag (`--reached-at`); the tool takes the clock as an injected value so a test reads no real time (AGENTS.md T10). A hosted job lives at most 6 hours, so one run can soak up to 5 hours; the tool refuses a larger N. While `soak` waits it holds the workflow's `release` group (the next release waits for it); a newer push is planned from the tip of main afterwards, so nothing is lost.

**Settings and N.** `FARM_SOAK_HOURS` is a repository variable (empty means `0`). `release.yml` reads it into the step's environment and gives it to the tool as `--hours`; the tool reads no environment (S2). Raising N is a change to the variable alone.

**Reading the farm again (not built).** `soak` for more than 0 hours must read the coordinator's convergence while it waits. `hostkeeper ci` has one command, `set-desired`, which sets and then reads; a call that only reads does not exist, and setting the same version again every minute is what this design does not do. `channels soak` therefore takes the reading as a program (`--read-command`), and `release.yml` passes none: a soak of more than 0 hours fails at once, naming the missing program, so promotion does not follow a soak that read nothing. What is asked of hostkeeper is a read-only mode of its CI client (`hostkeeper ci converge`). Until then `FARM_SOAK_HOURS` stays `0`.

**Rolling the lab back.** The coordinator's own automatic rollback sets the desired version back to the last good one and marks the failed one bad. By hand, with the operator token: `hostkeeper ctl releases mark-bad` for the version, then `hostkeeper ctl releases set-desired` for the previous good version (`docs/ctl.md` in hostkeeper). Nothing in this repository rolls a host back.

### 5.4 The install checks

Three jobs, release-time only (`release.yml`, after the testing stage; no pull request runs them, B9), on GitHub-hosted runners, with `contents: read` and nothing else: no secret, no token, no environment, no cloud role. They install the release from the **public** testing URLs, so they also prove that what testing holds is reachable and signed. Each is a green no-op when the testing job it reads from was a no-op (its output is given to the gate with `--require`), and red on any failure; a red check stops the release before anything public changes, because `promote-check` sees it.

| job | runner | does |
|---|---|---|
| `check-apt` | matrix: `ubuntu-24.04` amd64, and `ubuntu-24.04-arm` arm64 (the repository already uses that hosted arm runner, `artifacts.yml`'s `linux-arm64`); the step runs in a clean Ubuntu container whose image is named by digest (`ubuntu@sha256:...`, the digest in the workflow, checked by the lint) | downloads `https://packages.komira.ai/apt/komira-archive-keyring.gpg` and checks its fingerprint against the one written in the workflow; writes a deb822 file (`Types: deb`, `URIs: https://packages.komira.ai/apt`, `Suites: testing`, `Components: main`, `Signed-By:` the keyring); `apt-get update`; `apt-get install tierstore=<V>`; then asserts `tierstore --version` prints `tierstore <V>`, `/usr/lib/systemd/system/tierstore.service` and `/usr/lib/sysusers.d/tierstore.conf` exist, the account of the sysusers entry exists, and the unit is neither enabled nor active (`systemctl` is not running in a container, so the check reads the absence of the `wants` symlinks and, with systemd present, `is-enabled` and `is-active`). It is a Rust verb (`cargo xtask channels check-apt`) that writes the source file and runs the asserts, so the logic is tested with stand-ins for `apt-get` and `tierstore`. The job builds `xtask` on the runner (`cargo build --release -p xtask`, as the other jobs run it) and runs it in the container with `docker run --rm -v "$PWD/target/release/xtask:/xtask:ro" ubuntu@sha256:...`; the image is Ubuntu 24.04, the runner's own release, so the host-built binary finds the glibc it needs, and the container has nothing of the repository. | `check-install-sh` | matrix: `ubuntu-24.04` and `macos-15` | `curl -fsSL https://tierstore.dev/install.sh`, then `sh install.sh --version <V>` into a scratch prefix; `tierstore --version` prints `tierstore <V>`. It reads `releases/<V>/` (written at testing), never `latest.json` |

## 6. The xtask verbs

Rust, in `crates/xtask`, with Rust tests (AGENTS.md T11; there is no shell test). Small verbs, one subject each, each its own pull request (P7). A verb that calls `aws` or `gh` takes the program as a flag and reaches it through a trait (`channels::aws::Aws`, `release::Gh`), so a test hands it an in-process stand-in that answers as S3 does (the conditions of `put-object`, the ETag, `NoSuchKey`). No second stand-in binary is added: the real `aws` wrapper (`RealAws`) is run against the existing `gh-fake`, whose `print` and `fail` commands give it a success, a refusal and a missing program, so the coverage run reaches every line of it.

| verb | what it does |
|---|---|
| `release channel-files dist --commit C --version V --time T --out channel-files` | makes the tap-named copies in `dist` (same bytes, with their bundle copies) and the two `.deb`s and `SHA256SUMS` of `releases/<V>/` in `--out` |
| `release check dist --commit C` (extended) | adds the rule of section 3: each commit-named tarball has its tap-named copy with the same digest, and nothing else of that name |
| `channels gate --label L --output FILE --setting NAME=VALUE ...` | built: the three-way result of 5.1 |
| `channels decide --result NAME=RESULT... --farm-enabled B --output FILE` | **not built**: the rule of 5.3, "Deciding to promote"; writes `promote=true` or `promote=false` and the reason; reads no cloud, no clock, no environment |
| `channels latest D --tag T --commit C --bucket B [--aws P]` | **not built**: reads `releases/<V>/SHA256SUMS` from the bucket and checks every file's digest against the release's `SHA256SUMS`, then writes `latest.json` as `channels upload` does today (section 8) and nothing else |
| `channels check-apt --version V --arch A --keyring-url U --fingerprint F --apt-get P --tierstore P` | **not built**: the container-side asserts of 5.4 (source file, install, version, unit file, sysusers, account, not enabled, not active) |

| `channels upload D --tag T --commit C --bucket B --work W [--distribution-id I] [--attempts N] [--no-latest] [--aws P]` | built, except `--no-latest` (**not built**: with it the verb stops after the files of the version, writes no `latest.json` and no invalidation; `testing-upload` passes it): puts each file of the version (the tap-named tarballs and `.deb`s from `D`, each held to the digest `D/SHA256SUMS` lists, their bundles, and a `SHA256SUMS` of exactly these written to `W`) with `If-None-Match`; on `412` reads the stored file's digest and succeeds only if it equals the local one; then `latest.json` (section 8) and, when `I` is given, its invalidation. The merge and the index writer follow buildrules' `tools/channels/apt.zig` and `tools/deploy/apt_publish.zig`, ported to Rust, not called from there: this repository builds with `cargo` and has no Zig. With `--suite testing` the paths, the `Suite` and `Codename` lines of `Release` and the by-hash paths read `testing` in place of `stable`; nothing else of the format changes, and the golden for `stable` is unchanged. A golden test pins the index text against what the Zig tool writes for the same inputs (buildrules' own golden files of `Packages` and `Release`, copied into the test; only the two `Packages.gz` lines of the `Release` differ, because the compressor is another program, and the test checks them against the file written instead), so the two repositories feed one repository the same format. The `.deb` writer is `release deb` (pull request 1 of this stack, an `ar` of `debian-binary`, `control.tar.gz` and `data.tar.gz`); the apt verbs read the control file back out of the package bytes, with `flate2` and `tar`, already dependencies of `xtask`. No dependency was added for the apt verbs.

Coverage is the repository's: every crate at 99% of lines and branches by `coverage-gate` (T1). The tests assert behaviour, listed by name in each pull request with what each proves (T8): a re-run of an upload with the same bytes passes, with other bytes at the same key fails, a gate with some settings fails and names the missing, a `.deb` built twice is byte-identical, an index merged twice equals the index merged once, a promotion of a version `testing` does not hold fails, a promotion with a digest that differs from `SHA256SUMS` fails, a promotion run twice writes the same index, the testing index and the stable index never share a path, `decide` says `promote=false` for a failed check, for a skipped job that was enabled and for a lab stage that is enabled and not green, and `promote=true` for a lab stage that is off.

## 7. What the owner sets up, and in which order

Every step before the tag is a held step (AGENTS.md S3): it is run by the owner with their own AWS credentials and `gh` login, is a dry run unless `--apply` is given, never forces, and refuses to run unless the profile's account equals the `--account` given. No pull request and no workflow deploys anything.

0. **The lab under hostkeeper (optional for a release, the owner's own work).** The lab's tierstore is hand-installed today. The owner is building hostkeeper's side: installing the testing `.deb` (hostkeeper's packages design, pull request 188 there). A release does not wait for it: with step 9 not made, the lab stage is skipped and promotion goes on. Before the lab stage can be switched on, each farm host is enrolled in hostkeeper, the service `tierstore` is assigned to its role (`Services.Assign`; `docs/operations/assignments.md` in hostkeeper), and the host runs the hostkeeper-installed package (units `tierstore@a/@b`, the update hook) instead of the hand-installed one. A service left installed and unmanaged is never ordered by the coordinator, so a version set for it moves nothing. The moving of each host from the hand-installed to the managed tierstore is its own runbook with a rollback (the hand-installed copy kept until the managed one has run) and is not part of this design's pull requests. ## 8. Failure modes

**What each failure leaves.** The rule: a failure leaves the release at testing, never public. Where it stops:

| failed job | testing has it | public (`stable`, `latest.json`, tap) | what to do |
|---|---|---|---|
| a testing job (`testing-upload`, `testing-apt-*`, `formula`) | whatever it wrote before failing (every write is write-once and complete-or-absent, below) | does not have it: the checks and promotion need the testing jobs, or run only for channels whose testing counterpart worked | fix the cause, re-run the failed jobs |
| an install check | all of it | does not have it: `promote-check` says `promote=false` | the check's log names what the user would see; fix (a package, the formula, `install.sh`, the keyring) and re-run the failed jobs, or release again |
| `farm-check`, `farm`, `soak` (settings present) | all of it | does not have it | fix or roll back the lab (5.3) and re-run the failed jobs; the lab stage is the only job that can be red because of a machine of ours |
| the lab stage with its settings absent | all of it | has it (skipped with a notice) | nothing; set the settings (section 7, step 9) to turn it on |
| a promotion job | all of it | some channels may have it, each complete or absent | re-run the failed jobs: each promotion job is made to be run again (below) |

A coordinator that cannot be reached (the tailnet join or the listener) is a red lab stage. A release that no one fixes stays at testing; the next push makes the next version, and since `stable`, `latest.json` and the tap only go up, the next release's promotion carries the newer number past it. `testing` keeps the newest 25 versions per architecture, so a stale one ages out.

**How a re-run resumes.** Re-run the failed jobs of a run, not the whole run (as `release.yml` says today). The jobs that succeeded are not run again, and the jobs after a failed one run after it is green because they `needs` it. In particular: a failed install check re-run does not re-upload testing; a green lab stage is not re-run when only promotion failed; `promote-check` re-reads the results of the run, so it says `promote=true` the moment the last red job is green.

**Promotion without testing.** Possible only if the workflow is wrong: a promotion job lists `promote-check` and its testing counterpart in `needs`, and the lint holds both (a promotion job without either fails the lint, T15), and `channels decide` is given every job of the checks and the lab stage; a job missing from its flags is a defect the lint catches by comparing the flags with the job's `needs`.

**Promotion reads what testing holds.** The three promotion jobs do not build or download anything from the GitHub release but `SHA256SUMS`; they read the stored objects (the `releases/<V>/` objects, the testing index entries, the formula artifact) and compare digests with `SHA256SUMS`. A mismatch is red and writes nothing: it means testing holds other bytes than the release (a defect in what testing wrote, or a bad object put there by hand), and the owner decides.

**Half-made settings.** Some of a job's settings set, others not: the job is red and names the missing (5.1), writes nothing, and the release is unaffected. A variable that is set but wrong (a role ARN of another role, a bucket of another name) is not a half-made setting; the first write is refused by AWS (the role's trust or policy), the job is red with AWS's answer, and nothing is written. The release was made, the other channels ran. The fix is the variable, then a re-run of the failed job.

**A role's trust does not match.** The first `AssumeRoleWithWebIdentity` is refused (`Not authorized to perform sts:AssumeRoleWithWebIdentity`) when the `sub` the job sends is not the one the role trusts: a different environment name, a workflow file moved, a repository renamed (the immutable subject survives a rename; a delete and re-create does not). The workflow file names in section 4 are part of the contract: renaming `release.yml` or `tierstore-site-publish.yml` is a change to the stack.

**A re-run.** Re-run the failed jobs of a run, not the whole run (as `release.yml` says today). Every channel job is made to be run again:

- *testing upload*: a file that exists answers `412` to `If-None-Match`; the verb then reads the stored file's SHA-256 (`GetObject`, permitted) and passes when it equals the local one and fails (red, naming the file) when it does not. A different file at a version's key is never overwritten: it is a defect in what the release made, and the owner decides. `latest.json` is not written at testing; it is written at promotion, by `channels latest`, after `releases/<V>/` is checked, so a pointer never names a missing or different file.
- *`latest.json` and an older release*: `channels latest` reads `latest.json` and its ETag, and writes only when the version in it is lower than this release's, with `If-Match` on that ETag. A re-run of an older release, or an older release that finishes late, writes nothing. A `412` (another release wrote between the read and the write) makes the verb read again and decide again.
- *tap*: the formula was rendered at testing; the pull request exists, or the formula at this version is in the tap already: finish with success. A pull request for a version lower than the tap's is refused by the tap's guard ("not higher than ... on the base"), and the job is red, which is correct: the tap has a newer formula.
- *testing apt*: a `.deb` already in the pool answers `412`; the verb compares its digest, which is why the writer is deterministic (section 3) and the modification time is the commit's. An index already listing this version is not written again.
- *stable apt*: `apt promote` of a version `stable` lists with the same bytes writes the same index, which `apt write` does not write again; of a newer one listed, it fails (red, correct: a newer release has been promoted).

**A lost apt index race** (both suites; the race is per object, `dists/testing/*` and `dists/stable/*` are different objects). Two writers (another product's release, or a second tierstore release) read the same index; one writes first; the other's `If-Match` is refused (`412`). The write job reports `conflict=true` and the next attempt (`-2`, then `-3`) reads the index again, merges again and signs again. The `.deb` it uploaded is in the pool already and is found there. The third attempt's write fails the job instead of starting a fourth. The index is the only shared mutable object; the pool is write-once, so a lost race loses no package. A release whose apt jobs all failed is still a release: run the apt jobs again.

**A release made between plan and publish.** The plan walks the first-parent history of main from its tip and names a tag and a commit. A newer commit can be released by a manual run (own concurrency group) in between, or a tag can appear. `publish` refuses an existing tag or release, so no channel job runs for the lost plan (they need `publish`). When both releases do publish, they publish in the order they finish, and:

- `latest.json` never goes down (above);
- the apt merge and `apt promote` refuse a version older than the newest listed, and the tap's guard refuses a version not higher than the base;
- a file of `releases/<V>/` belongs to its own version, so the two releases do not meet in the bucket.

The automatic path cannot reach this state: the workflow's group serialises runs triggered by pushes, never cancels one, and holds the next until the first is done.

**A `.deb` or a tarball with wrong bytes.** Found before publishing, by `release check` (the copies are the commit-named tarballs, the packages are rebuilt from them by the same verb in `verify` and again in the channel job, which compares them). After publishing, nothing here deletes a file: the role cannot, and a bad file under `releases/<V>/` is dealt with by a new release; the administrator can remove it from the bucket with their own credentials, and from the apt pool the same way.

**The site is down or the CDN is stale.** `latest.json` is cached for a minute and is the only mutable file; the files of a version are immutable. A user who sees an old `latest.json` sees an older complete version, never a mix.

**Partial deploys of this design's pull requests.** The jobs are no-ops until the settings exist (5.1); the workflow lint refuses a job with a stray write scope; the tap needs the bot's secret. A release made while only some pull requests have landed publishes the files that exist: if `release check` learns the copies in one pull request and the copies are made in another, the pull requests land in the order of section 10 so no state fails the check.

## 9. What does not change

- **The existing release files**: names, bytes and `SHA256SUMS`. The tap-named tarballs are additional files beside them; the commit-named ones stay, so every installer, pin and doc that names them keeps working (`docs/ci-and-release.md`, `packaging/README.md`, the install guide).
- **The hostkeeper packages and the update hook**: the `.tar.zst`, `index.json`, the `tierstore@a/@b` units and the plist. A host under hostkeeper takes the release as before; a host that installs the `.deb` is not under hostkeeper and does not update through it (apt does).
- **The signing identity.** The signer of every attestation is `artifacts.yml` on main; nothing here signs a build. The `.deb`s are not attested: they are rebuilt from the attested tarball and compared. The apt index is signed with the key the shared repository already uses (the secrets of `apt-signing`), not a new key and not a tierstore key; a user who has `packages.komira.ai` configured for another komira product gets tierstore without another key.
- **The formats of tierstore itself**: nothing here touches a stored format, the wire, the configuration of the server or a data path (AGENTS.md B16 does not apply: no job here handles object data). The only new formats are `latest.json` (section 3, additive) and the index of the shared apt repository (the existing format).
- **The PR checks.** No job is added to a pull request's checks (B9); the jobs, the install checks included, are in `release.yml`, which runs after a push to main and on no pull request. The two `macos-15` checks are in that workflow and run at release time only; this repository's one macOS pull-request job, `macos.yml`, is not touched. Nothing is dispatched or run by a pull request.
- **Release automation (B12).** Releases stay automatic from main: no manual tag, and nothing that holds a release for a person's verdict. The install checks, the lab stage and the soak are automatic and read what the machines report; the soak is a timer; `promote-check` is a rule, not a person. The held steps of section 7 are one-time setup, not a gate on any release.
- **`hostkeeper-desired.yml`** stays as the by-hand way to set a version (for a rollback to an older release, say); `release.yml` does not call it, it runs the same reusable workflow. Its `check` still reads hostkeeper's `index.json`; the `release.yml` lab stage reads the testing index (5.3), and the two checks differ only in what they read.

## 11. Open questions

- **Version in the apt index and `+`.** `tierstore --version` prints `X.Y.Z+<12 hex>` after the name, and the tap's test line matches `tierstore X.Y.Z` as a prefix of it. The `.deb` uses `X.Y.Z` as its version, which is what the index lists and what `apt index` requires (`X.Y.Z` only, so apt's ordering is the tag's, and the version a `.deb` is named by must be the version in its control file).
- **The apt role's conditions and the by-hash copies.** `apt write` puts the by-hash copies of the `Packages` files (`apt/dists/stable/main/binary-<arch>/by-hash/SHA256/<hash>`) with `If-None-Match`, as buildrules' tool does, because the `Release` it writes says `Acquire-By-Hash: yes`. The role of section 5 says the shared `apt/dists/*` is written with `If-Match` only; if the role is built that way these puts are refused and the first release fails in the write job after the `.deb`s are in the pool. The role in komira-internal must admit `If-None-Match` for `apt/dists/stable/*/binary-*/by-hash/*` (and for the index objects that do not exist yet, on the first release), or this verb changes. Settled on 2026-11-08 by reading `infra/apt_repo/lib/apt-repo-stack.ts` in komira-internal: the role has `PutIndexIfAbsent` (`s3:if-none-match` set) beside `PutIndexIfMatch` on all of `apt/dists/*`, so the by-hash puts and the first write of a suite pass; the paragraph of section 5 states the grant as built.
- **A soak of more than 5 hours.** One hosted job is limited to 6 hours. If N should be larger, the soak needs a continuation that is not a job waiting: a `schedule` trigger on release.yml (the workflow lint pins its two triggers today) or a separate scheduled workflow that publishes the newest release whose N hours have passed. Not designed until N is raised above 5; `0` is the value now.
- **Reading the convergence again in `soak`.** Settled by reading hostkeeper's `docs/deploy/ci-client.md` and `crates/hostkeeper-ci`: its client has only `set-desired`, which sets and then reads; there is no read-only call. Hostkeeper is asked for one (5.3, "Reading the farm again"); until then a soak of more than 0 hours is refused.
- **`down` hosts.** Settled: the answer of `releases converge` carries `down` (and `failed`, `updating`) per role, and `channels soak` reads them from there. `farm` cannot, since the reusable workflow's outputs are `converged` and `reason` only (5.3, "Healthy, concretely").
- **The releases role as built has no read.** `infra/site/lib/site-stack.ts` gives `tierstore-prod-releases` `PutObject` (with `If-None-Match: *` under `releases/<V>/`, unconditionally on `releases/latest.json`) and `CreateInvalidation`, and its README says "No read, no list"; section 4 above says `GetObject` on `releases/*` and conditions on `latest.json`. `channels upload` needs the read: the check of a `412` and the read of `latest.json` are `get-object` calls. Until the stack grants `s3:GetObject` on `releases/*`, the files of `releases/<V>/` are put (each once, with `If-None-Match`), and then the job fails with `AccessDenied` on its first `get-object` of `latest.json`, even on the first release (`latest.json` is read before it is written, with or without a stored one), so the version has no pointer; a re-run fails earlier, at the first `412` read-back. The grant must also include `s3:ListBucket` on the bucket: without it S3 answers a missing key with `AccessDenied`, not `NoSuchKey`, and the first release's read of the absent `latest.json` would still be red. The stack change and its policy test are their own pull request, to be deployed before the first release.
- **`install.sh` does not exist yet.** `crates/tierstore/site/content/get-started.html` shows `curl -fsSL https://tierstore.dev/install.sh | sh`, but no such file is in the repository or in the site's `static/` directory (read on 2026-11-08). The check `check-install-sh` needs it, served by the site publish (`tierstore-site-publish.yml`, which already carries files of the site root and excludes `releases/`), with `--version V` that reads `releases/<V>/SHA256SUMS` and verifies the tarball's digest before unpacking, and no `latest.json` read when `--version` is given. It is written in the pull request of item 9 or a pull request before it, as a script with tests in the language of the site's tests (T11 allows no new shell test, so the script's logic is tested through the site's TypeScript harness or the script is a small Rust verb that the page names instead; the owner decides which). Until it is live on the site, `check-install-sh` is red for every release whose testing upload is configured, so the site publishes it before the owner turns the testing upload on (section 7, step 10).
- **What hostkeeper asks for in the lab stage.** The owner builds hostkeeper's side (hostkeeper's packages design, pull request 188 there). The inputs `release desired` hands to `set-desired.yml` today (package version and digest of the `.tar.zst`) may differ for a `.deb`; the stage is written against the testing index (version `X.Y.Z`, the `.deb`'s SHA-256 per architecture) and adapts when that design fixes the call. Not decided here.
- **The keyring's fingerprint in the workflow.** `check-apt` pins the fingerprint of `komira-archive-keyring.gpg` so a replaced key file is caught. A rotation of the archive key (an administrator step in komira-internal) makes `check-apt` red until the fingerprint in the workflow is changed in a pull request; that is the cost of the pin, and `stable` is unaffected.
- **Brew and arm Linux.** `check-brew` runs on `macos-15` (Apple silicon) only; the formula's Linux targets are not installed by any check. A hosted Linux runner with Homebrew is a later addition if the Linux formula proves to need it.
