# Stored formats

tierstore keeps a few small objects and files of its own. A new release reads what an older one wrote, and an older release must still read what a newer one writes while the two share a tier during an update. So these formats change only by adding.

## What is stored

| What | Where | Format |
|---|---|---|
| Journal object (written by the releases before the entries, neither read nor written by this release; removed by the release after it) | `_journal/<proxy_id>/<seq>` in the hot tier, `seq` in 20 digits | JSON list of entries: `op` (`PUT`, `DELETE` or `PUTMIRROR`), `key`, `size`, `time`, and the optional `cold_tag` and `hot_tag` |
| Key entry (reserved by every release since the bridge release; written by the puts, deletes and cold reads of a proxy whose format is active and by the entry reconciler, see "The format object") | `_entries/<sha256 hex of the key>` in the hot tier | JSON: `v`, `key`, `op` (`PUT`, `DEL`, `CB` or `EVICT`), `st` (`HELD`, `PENDING` or `SEALED`), `owner` (or `null`), `nonce`, `created_ms` |
| Proxy marker | `_tiering/proxies/<proxy_id>` in the hot tier | JSON: `proto` (1 in the release with the heartbeat, 2 in the release that works the entries), `boot`, `hb`, which the proxy rewrites every heartbeat, and the optional `phase` (the format phase the proxy acts on) and `writes_in_flight`, left out of the body when not set (this release sets neither); an empty object (the registration of a release before the heartbeat) reads as none, and a reader that lists the names never reads the body |
| Checkpoint (written by the releases before the entries, neither read nor written by this release; removed by the release after it) | `_tiering/checkpoint/<proxy_id>` in the hot tier | JSON: `seq`, `evict_seq`, `evict_idx` |
| Format | `_tiering/format` in the hot tier | JSON: `phase` (`drain`, `drained`, `active` or `active-marks`), and the optional `epoch` and `marks_bucket` (see below) |
| Marker (the library has the calls on it, `Markers`; no code of this release runs them yet) | the object named exactly by the key, in the marks bucket of the hot store (`hot_store.marks_bucket`) | JSON: `v` (1), `key`, `st` (`DIRTY`, `LOCK`, `CLEARING` or `WANT`), `gone`, `dirty`, `why` and `owner` (for a lock; left out when not set), `nonce` (see "Markers") |
| Usage | `_tiering/usage` in the hot tier | JSON: `hot_bytes`, `copy_lag`, `time` |
| Lease | `_tiering/lease` in the hot tier | three lines: the holder, a nonce, the count of bodies written |
| OCI upload session and chunks | `<prefix>uploads/<id>/begin` (empty) and `<prefix>uploads/<id>/c<20-digit offset>` in the store behind the OCI front | the session is an empty object; each chunk is the bytes of one `PATCH`; both are deleted when the upload ends or is cancelled |
| OCI tag version | `<prefix>tags/<name>/<tag>/<inv>`, `<name>` with `/` written `~`, `<inv>` the 20 digits of `18446744073709551615` less the number of earlier versions | the 71 bytes `sha256:<64 hex>` of the manifest the tag pointed at; a tag is its newest version (the smallest key); a version is never overwritten |
| Directory tier object | a file of the tier's directory, named by the key encoded (`/` as `~`, every byte but ASCII letters, digits, `_`, `-` and `.` after the first byte as `%` and two hex digits); `<first 100 bytes of that name>~<SHA-256 of the key in hex>` if the name would be over 255 bytes | the SHA-256 of the body (the content tag), then for a hashed name only the length of the key as 8 bytes (big-endian) and the key, then the body. A name of at most 255 bytes is written as it was in every release, so a release before the hashed names reads and lists those files; it lists a hashed file under the key its 165-byte name decodes to and cannot read it |
| Cache sidecar | `obj/<aa>/<bb>/<hex>.meta` in the local cache directory | JSON: `key`, `size`, `sha256`, `tag`, `modified` |
| Update hook record | `state.json` in the hook's state directory | pretty JSON: `schema`, `kind`, `updating`, `markers`, `from`, `to`, `version`, and for the systemd arm `live`, `next`, `mode`; an absent optional key is left out |

### The journal objects of the earlier releases

A release before the entries kept, for each proxy, journal objects and a checkpoint, and a reconciler that read them. This release has neither: no code of it reads or writes `_journal/` or `_tiering/checkpoint/`, and both prefixes stay reserved, so no client names a key under them. The objects that earlier releases left stay in the hot tier until the release after this one removes them, so that a rollback to the bridge release (the one that drains them) still finds them. The format of their entries (the operations `PUT`, `DELETE` and `PUTMIRROR`, and the tags `cold_tag` and `hot_tag`) is that of the bridge release and is not repeated here.

### Key entries

An entry says who is working on a key and what is to be done next. A reader ignores fields it does not know and reads an `op` or `st` it does not know as `Unknown`, which no transition accepts. `created_ms` is for metrics only. `nonce` is written afresh by every write, so that an actor that did not get an answer to a write reads the entry back and tells whether the write was its own.

### Markers

A marker says that a change to its key is not yet the cold tier's too, or that someone holds the key (`docs/design/put-without-lock.md`, section 4). It is one JSON object, named exactly by the key, in a bucket of the hot store of its own, so that every key S3 accepts can be marked. The library has the calls on markers (`Markers`), and the code that serves requests does not call them yet, so this release reads and writes none; the body and its fixtures are here so that the releases that do are held to them. A reader keeps the fields it does not know (in the order of their names) and the `st` and `why` words it does not know, as the text they were, and a rewrite carries them over, so a later release adds fields and states without a new `v`. `why` and `owner` are left out of the body when they are not set. `nonce` is written afresh by every write (128 random bits drawn when the `Markers` is made, a dot, and the count of that `Markers`'s writes), so the content tag of the object, which a conditional write names, is unique per write. The fixtures are `marker.json` (a dirty marker), `marker_lock.json` (the lock of a delete) and `marker_newer.json` (a state, a reason and two fields a later release adds).

### The format object

`_tiering/format` says whether writes are paused for a change of format. No object means no pause to a release before this one, and no write to this one. This release takes no write until the object says `active` with an `epoch` of 2 or more: it answers every write with 503 while there is no object, and for a phase or an epoch it does not take as active. A proxy reads it before a write, at most once for each `format_refresh` (5 seconds); while `phase` is `drain` or `drained` it answers every write (put, streamed put, delete, and the multipart calls that create, write a part or complete) with 503 `ServiceUnavailable` and keeps serving reads. The operator writes `drain`. The reconciler of the bridge release that holds the lease writes `drained` over it (only over the object it read, by its tag) once it has seen `drain` for `drain_settle` (15 seconds), long enough for every proxy to read it again (a write admitted earlier and still running is not waited for), and a pass applied every journal object without a failure; it keeps the `epoch`. A bridge-release reader ignores fields it does not know and takes a `phase` it does not know (and `active`) to be no pause; this release takes none of those as active. The phase `active-marks` (with an `epoch` of 3 and the optional `marks_bucket`, the name of the marks bucket, set by the operator's activation of the markers) is one of them for a release before it. This release reads the word and the field, pauses nothing, and its entry reconciler does nothing; under it, with an `epoch` of 3 or more and a `marks_bucket` that is the name of the bucket the proxy is configured with, a delete is made on the marker of its key (a lock, a hot HEAD, `gone`, a plain hot DELETE, the answer, the release) and every other write is answered 503 (the text it gives for a phase that is not active); with another name, or none, even the delete is 503. Nothing activates the phase yet: no tool of this release writes it. The format of a store without a `marks_bucket` reads and is written back without the field, byte for byte (`format_active_marks.json` is the fixture of the phase). With `phase` `active` and an `epoch` of 2 or more, a proxy makes its puts on entries (put, streamed put, presigned put, and the completion of a multipart upload): it creates the entry of the key create-only, writes the object create-only (to the hot tier, or to the cold tier when the hot tier is full or for a multipart completion), and replaces the entry with `(PUT, PENDING)`, which is when it answers. It does so only while its registration's heartbeat is acknowledged; before that, and after the heartbeat has stopped being acknowledged for the departure time less the margin, it answers `Unavailable`. A proxy that reads no object, `active` with no epoch, or an epoch below 2 answers every write with 503 and writes no journal. A delete on those entries creates the entry of the key too, and waits for the release of an entry that holds or seals a reconciler copy, a copy-back or a handed-over delete (answering 503 if it does not come). With the same format, a read of a whole object that the hot tier lacks and the cold tier has copies nothing itself: it creates the entry `(CB, PENDING)` of the key create-only (nothing happens if an entry exists) and the entry reconciler copies the cold object into the hot tier under it. No get or head reads an entry.

The prefix `_entries/` is reserved: no client put, delete, read or listing names a key under it, in the proxy, the local cache, the OCI prefix, the scoped and GC key prefixes and the presigned URLs. A client key that starts with `_entries/` is therefore refused by the bridge release; a release before it treats such a key as a client key (and on a directory tier it neither lists nor reads the `_entries/` subdirectory that the entry objects are kept in).

## The rule

A format changes only additively: a new optional field, a new operation word that a reader may skip, a new object under a new key. A field is never renamed, removed or given another meaning, and a field a reader needs is never added without a default. A reader ignores what it does not know and never refuses a file for it,.

A cache sidecar or a usage object with a field this release does not know is read as if it were not there. The hook record ignores a key it does not know, so the previous release's hook reads a record of this release (the keys `live`, `next` and `mode` of the systemd arm are ignored by it) and this release reads the previous release's. `crates/compat/tests/hook_record.rs` has the previous release's hook read and check what this release writes for an update in flight on systemd and on launchd, and this release read what the previous release writes. A record of a higher `schema` is refused as newer, not read: a test holds that with a record of schema 2 and a key this release does not know. The record of the earlier two-slot hook is gone: no host ran that hook, and the hook keeps its record in a new directory, so nothing reads it.

The upload records of the OCI front are new objects under new keys, and the blobs and manifests a push stores are the objects the front already read, under the keys it already used. The previous release does not list or read `uploads/`, so it ignores an open upload; `crates/compat/tests/oci.rs` pulls a pushed blob and manifest through the previous release's front with an upload left open in the same directory, and pulls the previous release's objects through this release's front. The tag versions of the OCI front are new objects under a new key prefix, `tags/`, which the previous release does not list or read, and each is written once and never replaced; `crates/compat/tests/oci.rs` moves a tag through this release's front and pulls both manifests by digest through the previous release's front (which serves no tag and answers a pull by tag 404), and has this release tag a manifest the previous release stored.

## The fixtures

The bytes of each format as a release wrote them are in `crates/tierstore/tests/stored_formats/fixtures/`. The tests in `crates/tierstore/tests/stored_formats/` use them in two ways. For a fixture the current release writes (each format's plain fixture), the current code reads it to the value the test expects, and writes that value as exactly the bytes of the fixture. The compatibility fixtures are read only: the `*_newer` fixtures (a key or operation added later) and the hook record of the release before (`hook_record_single.json`, with no `live`, `next` or `mode`) are read to the value the test expects and are not written back, and the newer hook record is refused as newer, not read as a value. The lease body holds a random nonce, so its test puts the fixture's nonce in before it compares.

A change that renames, removes or re-means a field fails one of those tests. Do not edit a fixture to make it pass: add a second fixture for the new field, keep the old one, and let both tests read the old fixture too. A change to an existing fixture in a diff is the thing to look at.
