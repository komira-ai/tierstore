# Stored formats

tierstore keeps a few small objects and files of its own. A new release reads what an older one wrote, and an older release must still read what a newer one writes while the two share a tier during an update. So these formats change only by adding.

## What is stored

| What | Where | Format |
|---|---|---|
| Journal object (written by the releases before the entries, neither read nor written by this release; removed by the release after it) | `_journal/<proxy_id>/<seq>` in the hot tier, `seq` in 20 digits | JSON list of entries: `op` (`PUT`, `DELETE` or `PUTMIRROR`), `key`, `size`, `time`, and the optional `cold_tag` and `hot_tag` |
| Key entry (reserved by every release since the bridge release; written by the puts, deletes and cold reads of a proxy whose format is active and by the entry reconciler, see "The format object") | `_entries/<sha256 hex of the key>` in the hot tier | JSON: `v`, `key`, `op` (`PUT`, `DEL`, `CB` or `EVICT`), `st` (`HELD`, `PENDING` or `SEALED`), `owner` (or `null`), `nonce`, `created_ms` |
| Proxy marker | `_tiering/proxies/<proxy_id>` in the hot tier | JSON: `proto` (1 in the release with the heartbeat, 2 in the release that works the entries), `boot`, `hb`, which the proxy rewrites every heartbeat; an empty object (the registration of a release before the heartbeat) reads as none, and a reader that lists the names never reads the body |
| Checkpoint (written by the releases before the entries, neither read nor written by this release; removed by the release after it) | `_tiering/checkpoint/<proxy_id>` in the hot tier | JSON: `seq`, `evict_seq`, `evict_idx` |
| Format | `_tiering/format` in the hot tier | JSON: `phase` (`drain`, `drained` or `active`), and the optional `epoch` (see below) |
| Usage | `_tiering/usage` in the hot tier | JSON: `hot_bytes`, `copy_lag`, `time` |
| Lease | `_tiering/lease` in the hot tier | three lines: the holder, a nonce, the count of bodies written |
| OCI upload session and chunks | `<prefix>uploads/<id>/begin` (empty) and `<prefix>uploads/<id>/c<20-digit offset>` in the store behind the OCI front | the session is an empty object; each chunk is the bytes of one `PATCH`; both are deleted when the upload ends or is cancelled |
| OCI tag version | `<prefix>tags/<name>/<tag>/<inv>`, `<name>` with `/` written `~`, `<inv>` the 20 digits of `18446744073709551615` less the number of earlier versions | the 71 bytes `sha256:<64 hex>` of the manifest the tag pointed at; a tag is its newest version (the smallest key); a version is never overwritten |
| Cache sidecar | `obj/<aa>/<bb>/<hex>.meta` in the local cache directory | JSON: `key`, `size`, `sha256`, `tag`, `modified` |
| Update hook record, two slots (Linux) | `state.json` in the hook's state directory | pretty JSON: `schema`, `serving`, `previous`, `mode`, `markers`, `boot_id`, `guard_placed` |
| Update hook record, single instance (macOS) | `state.json` in the hook's state directory | pretty JSON: `schema`, `kind`, `updating`, `markers`, `from`, `to`, `version` |

### The journal objects of the earlier releases

A release before the entries kept, for each proxy, journal objects and a checkpoint, and a reconciler that read them. This release has neither: no code of it reads or writes `_journal/` or `_tiering/checkpoint/`, and both prefixes stay reserved, so no client names a key under them. The objects that earlier releases left stay in the hot tier until the release after this one removes them, so that a rollback to the bridge release (the one that drains them) still finds them. The format of their entries (the operations `PUT`, `DELETE` and `PUTMIRROR`, and the tags `cold_tag` and `hot_tag`) is that of the bridge release and is not repeated here.

### Key entries

An entry says who is working on a key and what is to be done next. A reader ignores fields it does not know and reads an `op` or `st` it does not know as `Unknown`, which no transition accepts. `created_ms` is for metrics only. `nonce` is written afresh by every write, so that an actor that did not get an answer to a write reads the entry back and tells whether the write was its own.

### The format object

`_tiering/format` says whether writes are paused for a change of format. No object means no pause to a release before this one, and no write to this one. This release takes no write until the object says `active` with an `epoch` of 2 or more: it answers every write with 503 while there is no object, and for a phase or an epoch it does not take as active. A proxy reads it before a write, at most once for each `format_refresh` (5 seconds); while `phase` is `drain` or `drained` it answers every write (put, streamed put, delete, and the multipart calls that create, write a part or complete) with 503 `ServiceUnavailable` and keeps serving reads. The operator writes `drain`. The reconciler of the bridge release that holds the lease writes `drained` over it (only over the object it read, by its tag) once it has seen `drain` for `drain_settle` (15 seconds), long enough for every proxy to read it again (a write admitted earlier and still running is not waited for), and a pass applied every journal object without a failure; it keeps the `epoch`. A bridge-release reader ignores fields it does not know and takes a `phase` it does not know (and `active`) to be no pause; this release takes none of those as active. With `phase` `active` and an `epoch` of 2 or more, a proxy makes its puts on entries (put, streamed put, presigned put, and the completion of a multipart upload): it creates the entry of the key create-only, writes the object create-only (to the hot tier, or to the cold tier when the hot tier is full or for a multipart completion), and replaces the entry with `(PUT, PENDING)`, which is when it answers. It does so only while its registration's heartbeat is acknowledged; before that, and after the heartbeat has stopped being acknowledged for the departure time less the margin, it answers `Unavailable`. A proxy that reads no object, `active` with no epoch, or an epoch below 2 answers every write with 503 and writes no journal. A delete on those entries creates the entry of the key too, and waits for the release of an entry that holds or seals a reconciler copy, a copy-back or a handed-over delete (answering 503 if it does not come). With the same format, a read of a whole object that the hot tier lacks and the cold tier has copies nothing itself: it creates the entry `(CB, PENDING)` of the key create-only (nothing happens if an entry exists) and the entry reconciler copies the cold object into the hot tier under it. No get or head reads an entry.

The prefix `_entries/` is reserved: no client put, delete, read or listing names a key under it, in the proxy, the local cache, the OCI prefix, the scoped and GC key prefixes and the presigned URLs. A client key that starts with `_entries/` is therefore refused by the bridge release; a release before it treats such a key as a client key (and on a directory tier it neither lists nor reads the `_entries/` subdirectory that the entry objects are kept in).

## The rule

A format changes only additively: a new optional field, a new operation word that a reader may skip, a new object under a new key. A field is never renamed, removed or given another meaning, and a field a reader needs is never added without a default. A reader ignores what it does not know and never refuses a file for it, with one exception: the two-slot hook record, below.

A cache sidecar or a usage object with a field this release does not know is read as if it were not there. The single-instance hook record ignores a key it does not know. The two-slot hook record does not: it refuses a key it does not know, so a key added to it raises its `schema`, which an older hook reads as newer than it understands and leaves alone. A test holds that: a record of schema 2 with a new key reads as newer, not as corrupt.

The upload records of the OCI front are new objects under new keys, and the blobs and manifests a push stores are the objects the front already read, under the keys it already used. The previous release does not list or read `uploads/`, so it ignores an open upload; `crates/compat/tests/oci.rs` pulls a pushed blob and manifest through the previous release's front with an upload left open in the same directory, and pulls the previous release's objects through this release's front. The tag versions of the OCI front are new objects under a new key prefix, `tags/`, which the previous release does not list or read, and each is written once and never replaced; `crates/compat/tests/oci.rs` moves a tag through this release's front and pulls both manifests by digest through the previous release's front (which serves no tag and answers a pull by tag 404), and has this release tag a manifest the previous release stored.

## The fixtures

The bytes of each format as a release wrote them are in `crates/tierstore/tests/stored_formats/fixtures/`. The tests in `crates/tierstore/tests/stored_formats/` use them in two ways. For a fixture the current release writes (each format's plain fixture), the current code reads it to the value the test expects, and writes that value as exactly the bytes of the fixture. The compatibility fixtures are read only: the `*_newer` fixtures (a key or operation added later) and the first-release hook record are read to the value the test expects and are not written back, and the newer two-slot hook record is refused as newer, not read as a value. The lease body holds a random nonce, so its test puts the fixture's nonce in before it compares.

A change that renames, removes or re-means a field fails one of those tests. Do not edit a fixture to make it pass: add a second fixture for the new field, keep the old one, and let both tests read the old fixture too. A change to an existing fixture in a diff is the thing to look at.
