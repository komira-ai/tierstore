# Farm measurements for the cold tier and the cache device (November 2026)

These measurements decide the constants of tierstore's redesign: the cold tier on the nodes' HDDs,
the cache device, and the CPU budget for hashing. Each section is one arm of the measurement plan. The
constants, the inferences the numbers contradict, and the choices made while measuring are at the
end.

Values marked [I] in the "was" column were the redesign's inferences before measuring.

## How the measurements were taken

**Where.** One of the six build nodes (here called n3) ran every arm that touches a drive. It
had no jobscheduler bookings for the whole window, and its load and container count were
logged every minute. The other five nodes kept running builds. The node's two HDDs (Seagate
ST8000DM004, drive-managed SMR, xfs) also hold silo's data. silo's erasure set spans all twelve
drives, so builds on the other nodes reach these drives too. Draining one node does not make
its drives idle.

**The guard.** Each cell of the drive arms ran under a guard, and its row records what the
guard saw:
- the disk bytes of the silo process during the cell;
- the write requests per second on the drives the cell only reads (any write there is
  foreign);
- the load average.

Before a cell the guard waits up to 120 s (20 s for the prototype) for a quiet 5 s window. A cell that saw more than
10 foreign writes/s, 2 MB/s of silo bytes, or a load above 64 is run once more. Its second
result is kept as it is, marked `attempts=2`.

The design's rule "abort the run if a drive is over 5% busy for 60 s" could not be kept. silo
keeps about 2–12 small writes/s on every drive of the set, and each write holds an SMR drive
busy for its whole log flush (up to 40% busy at 2 writes/s, see E). So the per-cell guard
replaces it, and the foreign activity is reported beside every number instead of hidden.

**The cells.**
- A cell is a 5 s warm-up, then a 20 s measured window.
- The drives' `/proc/diskstats` are read at the window's start and end, which gives
  `iostat -x` over exactly the window.
- Before each cell the page cache of every file the cell reads is dropped with
  `POSIX_FADV_DONTNEED`, per file and not node-wide, so builds on the node keep their cache.
- Latency is per request, from the issuing thread.
- MB/s means 10^6 bytes per second; sizes are in MiB.

**Scratch space.** Every write went to a dedicated scratch directory beside silo's data on
the drives' xfs (`ts-cold-scratch/`). The churn arm used a fixed-size xfs on a loop device
over an image in that directory. Nothing under silo's directories was written. The write arms
refuse to start if they would leave less than half of the drive's file system free.

**Reproducing.** The tool is `crates/tierstore-measure`, binary `ts-measure`. Build it with
`cargo build --release -p tierstore-measure`. Every verb takes `--out DIR` and writes
`<arm>.jsonl` (one JSON object per cell) and `<arm>.md` (the tables below). The runs here were:

| arm | command |
|---|---|
| A | `ts-measure hdd-prep` with the same directories, then `ts-measure hdd --dir <hdd1>/ts-cold-scratch/a --dir <hdd2>/ts-cold-scratch/a --sets one,both <guard>` |
| B | `ts-measure cache --target loop=<cache dir> --target rootfs=<root dir> --target loop-dio=<dir> --fstrim loop-dio=<mount> <guard>` |
| C-5 cells | `ts-measure write-cells --dir <hdd1>/ts-cold-scratch/c5 <guard>` |
| C-5 sustained | `ts-measure write-sustained --dir <hdd1>/ts-cold-scratch/c5 --rewrite-cap-mib 204800` |
| C-5 churn | `ts-measure loopfs-setup --gib 128 --direct-io ...`, then `ts-measure churn --lo 89 --hi 91 --turns 2` (and `--lo 84 --hi 86`), then `loopfs-teardown` |
| prototype | `ts-measure cold-prep --drive hdd1=<dir> --drive hdd2=<dir> --packs 24 --pack-mib 1024`, then `ts-measure cold-local` with the same drives and `--arms c2,c4,c3,mixed,slow <guard>` |
| D | `ts-measure cpu` |
| E | `ts-measure facts` |

`<guard>` is `--guard-comm silo --guard-write-dev sdb --guard-write-dev sdc --guard-max-w-s 10
--guard-max-load 64 --guard-quiet-ms 5000 --guard-attempts 2`, with `--guard-max-wait-ms 120000` for A and
B and 20000 for the prototype.

## A. Raw HDD reads

**What ran.**
- On one drive: the full grid, 120 cells. Request size {1, 2, 4, 8, 16} MiB × streams {1, 2,
  4, 8} × {buffered with `read_ahead_kb` 8192, buffered with 512, `O_DIRECT`} × {adjacent,
  scattered}.
- On both drives at once: 36 cells. Size {1, 4, 16} × streams per drive {1, 2, 8} × {8192,
  `O_DIRECT`} × both patterns.
- Each stream reads its own 8 GiB region file. An adjacent stream reads its region in order;
  a scattered stream reads aligned random offsets over all eight regions of its drive (64 GiB).
- `fw` is the foreign write requests per second the guard saw on the drives during the cell.
  Cells with `fw` above about 20 are depressed by silo's writes.

**What it shows.**
- One sequential stream gets the media rate: about 120 MB/s on sdb and 91–93 MB/s on sdc,
  whatever the request size from 1 MiB up. The drives run at 100% util with no foreign writes.
  The vendor's 190 MB/s is an outer-zone figure, and these regions are not in the outer zone.
- A scattered 1 MiB read takes a median 22–23 ms, so positioning costs 13.5 ms. Scattered
  reads deliver 43 MB/s at 1 MiB, about 72–76 MB/s at 4 MiB and 90 MB/s at 16 MiB.
- Two or more sequential streams on one drive cost a seek at every switch:
  - with `O_DIRECT`, throughput falls to 53–60 MB/s at 1 MiB and to 70–86 MB/s at 4–16 MiB;
  - buffered with `read_ahead_kb` 8192, it holds 85–93 MB/s, because readahead turns each
    switch into a 4 MiB request (rareq-sz 4 MiB, against 0.5 MiB for `O_DIRECT`);
  - latency grows with the stream count: 8 streams of 1 MiB have a p99 of 0.7–1.6 s.
- Two drives are independent. Each stream count gives the sum of the two drives' single-drive
  rates (213 MB/s for one stream each, 189 MB/s at two), so nothing between them (bus, HBA) is
  shared.
- **Inference contradicted:** `O_DIRECT` requests do not reach the drive as 4 MiB.
  - The drives accept 4096 KiB requests (`max_sectors_kb` 4096, `max_hw_sectors_kb` 32767).
  - Yet every `O_DIRECT` cell shows rareq-sz of about 510 KiB, whatever the read size.
  - The likely limit is the scatter list.
    - The buffer of a direct read is ordinary 4 KiB pages, and each page is a separate segment.
    - The controller takes at most 168 segments of up to 64 KiB each (`max_segments`,
      `max_segment_size`).
    - So a request of 4 KiB pages stays well under 1 MiB.
  - Readahead does issue 4 MiB requests: it reads into large page-cache folios, which make few,
    large segments.
  - The design's "chunk = 4 MiB `O_DIRECT` = the device's max request" does not hold without
    huge-page buffers.

**Derived constants (the tool's `derive`, one drive, quietest cells).**

| constant | value | from |
|---|---|---|
| `media_MBps` | 120 | best one-stream adjacent `O_DIRECT` rate, sdb |
| `pos_ms` | 13.5 | scattered 1 MiB `O_DIRECT` median 22.3 ms less 1 MiB at 120 MB/s |
| `gap_cells` | 2 | `ceil(13.5 × 120 / 1.048576 / 1000)` |
| cold-tier read mode | buffered with `read_ahead_kb` 8192 for streams, `O_DIRECT` for single demand reads | see the decision below |

The `O_DIRECT` versus buffered decision is not the design's default.
- With one stream per drive the two are equal: 119 against 122 MB/s.
- With 2–8 streams, buffered readahead of 8 MiB beats `O_DIRECT` by 30–70%: 85–93 against
  53–77 MB/s at 1–4 MiB.
- The scheduler (C-2) admits at most two streams, and it slices them. So the read mode matters
  less there than here, where every stream runs at once.
- C-2 measures the prototype both ways and settles it.

## B. The cache device

**The device.**
- Every node has one 1 TB consumer SATA SSD. The root ext4 fills it.
- The cache is xfs on a loop device, over an image file on that ext4.
- On every node the loop is attached with `DIO=0`, so it is not in direct-I/O mode.

**The three targets.** Each ran the same tests:
- `loop`: a scratch directory in today's cache file system;
- `rootfs`: a directory of the root ext4;
- `loop-dio`: a 40 GiB xfs on a new loop device with `--direct-io=on`, over an image on the
  root ext4.

**Writes** (20 s windows; MB/s of writes completed inside the window).

| target | 128 KiB ×1 buffered | 128 KiB ×1 direct | 1 MiB ×1 buffered | 1 MiB ×1 direct | 1 MiB ×4 direct | 4 MiB ×16 direct |
|---|---|---|---|---|---|---|
| rootfs | 320 | 84 | 133 | 94 | 160 | 129 |
| loop-dio | 146 | 127 | 139 | 120 | 166 | 124 |
| loop (today) | 263 | 946 | **1.2** | 464 | 2497 | not run |

`buffered` writes are followed by an `fdatasync` after every 32 MiB. The full table is
`b.jsonl` (54 write cells).

- **The SSD sustains about 120–165 MB/s of writes.** `rootfs` `O_DIRECT` writes show this, with
  the device 92–98% busy. The design's cache write ceiling of "about 500 MB/s" is about 3×
  too high.
- Reads from the same SSD run at about 550–590 MB/s (the DONTNEED read-back below).
- **Today's loop does not do direct writes.** `O_DIRECT` through it runs at 464–2500 MB/s,
  faster than the device. The loop is buffered, so the bytes stop in the host page cache of
  the image.
- **Through today's loop, `fdatasync` collapses.** One 1 MiB writer with a sync every 32 MiB
  completes 1.2 MB/s, against 133 MB/s on the root fs. With 4 writers, none finished a write
  inside the window.
- **Sixteen buffered writers stalled the whole node for about 20 minutes:**
  - 27 GB of dirty page cache built up behind the image, draining at about 110 MB/s;
  - 85% "full" I/O pressure;
  - remote logins timed out and the node's other services stalled.

  The 16-writer cells on `loop` were not run again for that reason. `loop-dio` behaves like
  `rootfs`, within the noise of single cells.

**`fdatasync` latency.** Every second, 1 MiB is written to each of 8 entry files and each is
`fdatasync`ed; 60 commits make 480 syncs. The test ran idle, and beside 4 writers of 1 MiB with
an `fdatasync` every 32 MiB.

| target | idle p50 ms | idle p99 | idle max | loaded p50 | loaded p99 | loaded max |
|---|---|---|---|---|---|---|
| rootfs | 3.3 | 10.8 | 38.5 | 13.6 | 1237 | 1592 |
| loop-dio | 4.6 | 37.0 | 82.2 | 9.2 | 2015 | 2579 |
| loop (today) | 5.2 | 8.5 | 41.0 | 9.7 | 2019 | 2992 |

**Mixed load.** 8 jobs: 70% random 128 KiB `O_DIRECT` reads, 30% 1 MiB sequential writes.

| target | read MB/s | read p50 ms | read p99 | write MB/s |
|---|---|---|---|---|
| rootfs | 33.1 | 3.35 | 364 | 117 |
| loop-dio | 22.0 | 15.1 | 157 | 79 |
| loop (today) | 27.1 | 0.27 | 10.7 | 95 |

The `loop` reads are not reads of the SSD. The read set was written through the buffered loop,
so the "direct" reads are served from the host page cache of the image.

**Punch** (1 GiB file, every other 16 MiB group punched).
- On every target the file's allocation and the file system's free space drop by 512 MiB at
  once.
- The image behind a loop gives nothing back: 0 MiB, on both loops.
- Running `fstrim` on the `loop-dio` file system returned 9086 MiB to the image: all of its
  free space, our punches included.
- So in today's layout, evicted cells free space in the cache file system but never in the
  root file system, unless `fstrim` runs or the loop passes discards.

**DONTNEED on a read-after-serve pattern** (`loop-dio`, 4 GiB in 1 MiB cells, committed per
32 MiB, then read back). Page-cache growth is from `/proc/meminfo` (node-wide, so only
indicative on `rootfs`).

| policy | page cache grew MiB | read-back MB/s | read p99 ms |
|---|---|---|---|
| never | 4096 | 5977 | 0.30 |
| at commit | 0 | 562 | 2.23 |
| cap 256 MiB | 256 | 587 | 2.27 |

**Decisions this arm gives (the cache-device gate).**
- **Move the cache off today's loop: yes.** The gate's own test is "sustained write under 80%
  of the raw SSD at 1 MiB". It fails outright: 1.2 against 133 MB/s with `fdatasync`. And a
  burst of buffered writes can stall the node for minutes.
- `fdatasync` p99 is not worse than 2× the root fs (8.5 against 10.8 ms idle, 2019 against
  1237 ms loaded), so that part of the gate passes.
- **The interim step:** attach the loop with `--direct-io=on`. `loop-dio` matches `rootfs`
  within noise in every test. In this design that is the documented stop-gap, not the end
  state.
- **There is no unallocated SSD space on any node** (E). A dedicated partition needs the root
  ext4 shrunk offline, or a re-provision through hostkeeper. ext4 can be shrunk; the design
  feared xfs, and that fear does not apply.
- **Dirty cap.** Writeback at about 130 MB/s means 256 MiB is 2 s of writeback.
  `min(256 MiB, 2 × node budget)` stands.
- **DONTNEED default: (c), cap-driven.**
  - (a) "never" keeps the whole written set in page cache, where it competes with the build's
    own cache.
  - (b) "at commit" makes every warm re-read a device read: 562 MB/s against 5977.
  - (c) bounds the cache cost and keeps the most recent cells warm.
  - The cap value is set by the tier's own benchmarks.

## C. The cold tier

### C-1, C-6 and C-7: not reported

These three arms measure silo itself: its ranged GETs, its bytes and object sizes, and the placement of
its real key set. silo is being removed from the farm, and the silo arms were cancelled while this
run was under way, so they are left out of this report:
- **C-1:** only three cells of the silo GET grid read from the drives; every later cell re-read
  objects already in the page cache.
- **C-6 and C-7:** they need the whole key list. silo's S3 listing ran at about 14 objects/s and
  timed out repeatedly, and the part it returned covers one prefix only.

The drive facts of C-6 that do not depend on silo (`xfs_info`, `lsblk`, free-space fragmentation) are
in E. The tool's `silo-list`, `silo-get` and `analyse` verbs stay in the crate. They resume a
listing that stops (`--after`), and they run against any S3 store holding the packs.

### The prototype (C-2, C-3, C-4, mixed, slow consumers)

**What it is.** `cold-local` runs a prototype of the cold tier's read path on the node:
- one server per drive, on a loopback port, serving byte ranges of packs over HTTP;
- each server has the design's per-drive scheduler: admitted streams, slices, demand
  preemption at a chunk boundary, at most `demand_preempt_max` preemptions a second, and a bounded
  queue;
- 24 packs of 1 GiB on each drive, in its scratch directory;
- the loads come from the same process: background streams reading 64 MiB parts in order (or
  whole packs), a demand read every 500 ms, and optionally a hedge, slow consumers or a write
  stream.

Every cell changes one parameter from the design's defaults:
- 2 streams, 1 write stream;
- 32 MiB slices;
- preemption on, at most 4 a second;
- chunks of 4 MiB read with `O_DIRECT` at depth 2;
- 4 background streams of 64 MiB parts;
- a 1 MiB demand read.

**The runs were not quiet, and neither result stands alone.** Both runs were on the same drives
with the same cells. Neither had idle drives:
- **First run:** silo served about 26 MB/s of other nodes' reads from the drive under test, and the
  other drive was 40–84% busy without being touched.
- **Second run:** silo was being erased from the node for its replacement. The drives saw 20–450
  foreign writes/s, and the untouched drive was 100% busy with writes. Every cell was retried once
  (`attempts` 2) and kept.

So the absolute rates and latencies below are for a drive shared with another writer or reader,
not for an idle drive. What the two runs agree on is used; where they disagree, nothing is decided.

The first run's background rates fell from the slice cells on, while silo's reads of the drive
grew. Its whole-pack row has no background rate, because its counter only counted whole transfers.

What the two runs agree on:
- **More streams buy background throughput and cost the demand read.** From 2 to 3 or 4 streams,
  background MB/s rises by 20–40%, and the demand first byte doubles (p50 230 to 470–600 ms).
- **8 MiB chunks are the worst for a demand read** in both runs (p50 541 and 551 ms, against 134–236
  ms at 1–4 MiB). Chunks of 1–2 MiB are no worse than 4 MiB, and better in the first run.
- **Preemption helps the median demand.** At a 4 MiB demand, p50 is 571 against 832 ms and 275
  against 502 ms. The p99s disagree between the runs.
- **Depth 4 doubles the demand wait** (p50 465–474 ms, against 230 at depth 2) and buys no
  throughput that both runs show.
- The slice size and the read path (`O_DIRECT` against `sendfile` plus DONTNEED) give opposite
  answers in the two runs. Nothing is decided from them.

- **Fresh writes hold 95–118 MB/s for the first 130 GiB.** That is the media rate of A.
- **From 140 GiB, the rate falls to 40–60 MB/s and stays there.**
  - The mean write request falls from 511 to about 390 KiB, and the write wait triples (50 to 170 ms).
  - The cause is not isolated. This phase ran without the guard, and churn ran on the other drive the
    whole time. What changes looks like the drive's own management of its SMR zones: the scratch
    writes are not the only writes to this drive.
  - Plan on the lower figure.
- **Writing into freed space runs at 0.54× fresh** (the tool's `ratio`: rewrite MB/s over fresh MB/s,
  mean over the run). The rows swing between 17 and 105 MB/s, and the pack's worst case reaches 101 s.

**Steady-state churn at 85% and 90% fill.**

*Setup.*
- Each drive got a 128 GiB xfs on a loop device (`--direct-io=on`) over an image in its scratch
  directory, so the drive's own file system kept its headroom.
- One writer added packs of 64 MiB–1 GiB (drawn in turn), the way the tier writes them.
- A reader read 4 MiB every 200 ms, most often from the newest packs.
- When the fill passed the band's top, the least recently read packs were unlinked until the fill was
  under the band's bottom.
- After the fill phase, 2 capacities (256 GiB) were written.
- Both drives ran at once, 90% on hdd2 and 85% on hdd1.
- Rows are per 8 GiB written. The full tables are `c5-churn-hdd2-90.md` and `c5-churn-hdd1-85.md`.

| band | fresh fill MB/s | churn turn 1 | churn turn 2 | turn 2 over fresh | fill at window ends | packs evicted per 8 GiB | extents per pack |
|---|---|---|---|---|---|---|---|
| 89–91% (hdd2) | 61.3 | 60.5 | 59.2 | 0.97 | 88.6–90.9% | 11–32 | 1 |
| 84–86% (hdd1) | 57.5 | 56.2 | 53.1 | 0.92 | 83.2–86.0% | 10–32 | 1 |

- **At 90% fill, writes keep 97% of the fresh rate after two capacities of churn**, and every pack
  is still one extent.
  - The rate is about half of A's media rate for three reasons: two drives ran at once, a reader
    shared the drive, and the loop added its own layer.
  - The comparison that matters is within a run: churn against the same run's fill.
- **85% is not better than 90%**: 0.92 against 0.97, within the windows' swing (34–72 MB/s).
- **Evicting by re-reading the file system's free space is wrong on xfs.**
  - A first run evicted until `statvfs` showed the band's bottom. xfs returns an unlinked file's blocks a
    while after the unlink, so every eviction removed 110–150 packs instead of about 20.
  - The fill then swung between 55% and 91%, not 89–91%.
  - The tool now counts the fill as the tier must: the use at the start plus its own packs' bytes.
    The rows above are from that rerun.
  - The tier's eviction has to work the same way: it counts its own bytes and does not re-read
    `statvfs` after each unlink.
- **Rewriting into a third of freed 1 GiB holes (the sustained run) reached only 0.54× fresh.** The
  churn above reached 0.92–0.97×. Both runs wrote into freed space on the same drives. The cause of the
  difference was not isolated:
  - the sustained run had no guard, and its rate had already fallen to 40–60 MB/s before the deletes;
  - the churn ran later, through a loop.
  
  Plan on the lower figure for a drive whose freed space is scattered.

## D. CPU

**What ran.** For each hash: MB/s over 1 MiB buffers for 3 s, on one thread and on 88 threads
at once.
- n3 had only the I/O-bound measurements running (load 13).
- n1, n2, n4, n5 and n6 were building, at load 44–304.
- None of the CPUs (Xeon E5-4669 v4, Broadwell) has the SHA extensions.

| node (load) | sha256 (`sha2`) 1 thread | sha256 (`ring`) 1 thread | `ring` 88 threads | blake3 1 thread | crc32c 1 thread |
|---|---|---|---|---|---|
| n3 (13) | 216 | 402 | 13 343 | 3600 | 6265 |
| n1 (44) | 162 | 309 | 11 342 | 2542 | 4682 |
| n6 (161) | 146 | 281 | 9 779 | 2384 | 4106 |
| n4 (111) | 151 | 275 | 10 259 | 2354 | 4126 |
| n2 (238) | 149 | 281 | 10 687 | 2432 | 4222 |
| n5 (304) | 97 | 154 | 4 148 | 1509 | 2949 |

`openssl speed sha256` on 1 MiB measured 446 MB/s on n3, and 297 MB/s on n2 at load 28.

**What it shows.**
- The design's "about 0.4 GB/s without SHA-NI" is right for an assembly SHA-256 (`ring`,
  OpenSSL). It is not right for the `sha2` crate, which runs at about half that rate.
- Under build load a core gives 150–310 MB/s.

**Decisions.**
- The cell verifier uses `ring`'s SHA-256, which is already a workspace dependency.
- **Hash threads:**
  - The design's formula is `ceil(1.2 × target_rate / core_sha_rate)`.
  - The target rate is the cache device's write ceiling, about 150 MB/s (B), not 500.
  - At 280 MB/s per loaded core that is **1 thread**; at the worst node's 154 MB/s, 2.
  - So 2 threads, with `core_sha_rate` measured at start as the design says.
- **`cpu.weight`:** the hash work is about 1.5% of a node's 88 cores at the cache's write rate.
  Nothing here argues for a weight above the job scopes' beyond what the design states.
- BLAKE3 (placement) and CRC-32C (footer) cost nothing at these rates.

## Inferences the measurements contradict

- **"A 4 MiB `O_DIRECT` chunk is one request at the drive".** It reaches the drive as about
  510 KiB, for reads and for writes. The limit is the scatter list of a buffer of 4 KiB pages (A).
- **"The cache device writes about 500 MB/s".** The SSD sustains 120–165 MB/s (B).
- **"SHA-256 at about 0.4 GB/s without SHA-NI".** True only for an assembly implementation;
  the `sha2` crate gets half of it (D).
- **"Abort the run if a drive is over 5% busy for 60 s".** On these drives silo keeps every
  drive 8–43% busy with 2–12 small writes a second, so no run could have started. The guard
  replaces it (method).
- **"Eviction frees space down to the low mark" is wrong if the low mark is read from
  `statvfs`.** xfs frees an unlinked file's blocks late (C-5).
- **"A drive sustains about 100 MB/s of writes".** It does for the first 130 GiB, then
  40–60 MB/s (C-5).
- **"An 80% fill limit".** 90% costs nothing measurable after two capacities of churn (C-5).

## Decisions

These are the choices this report made where the plan left a choice, or where the plan could not be
followed.

- **A reduced grid for "both drives".** The full 120-cell grid ran on one drive. On both drives the
  grid was cut to 36 cells (three sizes, three stream counts, two modes). The one-drive grid
  already ranks the modes, and two drives turned out to be independent.
- **A per-cell guard instead of the 5% abort.** silo keeps every drive busy (E), so the abort could
  never pass. Each cell records what else used its drives, and is retried once when that was too
  much.
- **The 16-writer cells were not repeated on today's loop.** One run stalled the node for 20
  minutes (B), and the gate fails without them.
- **The rewrite was capped at 200 GiB.** The plan's bound, min(60% of free space, 400 GiB), would
  have been 400 GiB. 200 GiB already ran at a stable rate for 70 GiB.
- **Two copies are the two drives of one node.** C-3's copies on two nodes needed a second node's
  drives; C-3 measured the drive side, striping and hedging, on one node.
- **B ran beside A.** They use different devices, and B's node-wide effect (the dirty page cache)
  was recorded.
- **The page-cache growth of B comes from `/proc/meminfo`.** The nodes have no `fincore`.
- **CPU was measured under the other nodes' real build load** instead of a synthetic one. The loads
  are in the table.
- **`ring` for SHA-256, with 2 hash threads.** `ring` is twice `sha2`, and it is already a workspace
  dependency.
- **The churn arm ran 2 capacities on both drives at once** (85% on one, 90% on the other), after its
  eviction was fixed. That gave both bands in one window.
- **The silo arms were dropped** when silo's removal was decided during the run (C-1, C-6, C-7).
  The tool's listing verb was changed to resume and to keep a partial listing first, and it stays.
- **The prototype numbers are used only where both runs agree.** Neither run had idle drives
  (C, the prototype). The constants that rest on them are marked provisional.
- **The peer read and the loaded first byte were not run.** The node went back to the farm when the
  silo arms were cancelled. The tier's farm benchmarks measure them on the real peer service.
- **The fill limit is 90%.** The churn measured no loss at 90% against 85%, and C-5's sustained
  rewrite is above the design's 0.5.
