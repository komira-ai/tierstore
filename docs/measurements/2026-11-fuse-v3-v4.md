# FUSE variants V3 and V4, November 2026: `tsfuse` with cloned readers, by `writev` and by splice

The second measurement of the FUSE benchmark (`crates/fsbench`), for the variants V3 and V4 of
`docs/design/fetch-cache-serve.md` (17.1). It runs the same harness, tree and load as the
baseline (`docs/measurements/2026-11-fuse-baseline.md`) on one build node of the same hardware:
256 processes that open, read and close the files of a real tree over and over, beside 176 CPU
burners, then whole-file reads.

- **V3**: `fsbench tsfuse-null-fs`, a null file system on `tsfuse` (the FUSE library of the
  redesign) on `/dev/fuse`, with 1 reader and with 2, 4, 8 and 22 readers (the mount's
  descriptor and its clones, a thread each); READ replies by `pread` and `writev`.
- **V4**: the same, with READ replies of 16 KiB and more by splice through pooled pipes
  (`tsfuse::ReplyPath`, threshold `tsfuse::SPLICE_MIN`); **V4m** is V4 at 8 readers with
  `SPLICE_F_MOVE`.
- **null**: the same-day control, `fsbench null-fs` on the `fuser` fork with 16 threads, as in
  the baseline.

The null file systems answer from the list alone: a `LOOKUP`, `GETATTR`, `OPEN` or `READDIR` is
answered from the tree in memory, and a READ from a data file (below), so the series measure the
transport and nothing of `tierstore fs`.

**In short.** Cloned readers scale to a knee at 4: with the caches off, opens/s go 2,278, 3,974,
5,972, 6,066 and 3,461 at 1, 2, 4, 8 and 22 readers, while the server CPU per 1000 cycles goes
438, 493, 654, 1,173 and 4,912 ms; with the caches on the best is also at 4 (195,313 opens/s at
20.2 ms per 1000 cycles). Splice cuts the server CPU per GB of cold whole-file reads by 9 to 25% at
1 to 4 readers with the read rate equal or higher, and by nothing at 8 and 22. `SPLICE_F_MOVE`
saves nothing and, in the no-open regime, costs 28% more CPU per GB. The `fuser` control on 16
threads still makes more opens/s than `tsfuse` at its best (8,002 against 6,066 to 6,347 with the
caches off; 235,858 against 195,313 with them on), at three times the server CPU per cycle. All
figures are medians of five runs; the tables give the least and the most.

## Setup

| | |
|---|---|
| Node | one build node of the farm, the same model as the baseline's: 2 x Xeon E5-4669 v4 (44 cores, 88 CPUs online), governor `schedutil`, kernel `7.0.0-42-generic`, `fuse` module defaults (`max_user_bgreq` 65535, `enable_uring` N); its job agent stopped for the whole collection |
| Tree | the baseline's list, unchanged: 20,219 regular files, 410,896,895 bytes (list SHA-256 `a01bea3dceeb...`, in every record) |
| Load | 256 reader processes, each going round its 1/256 of the list; 176 CPU burners; 60 s per run |
| Cycle | `stat`, `open`, a `read` of the first 4096 bytes, `close`, each timed on its own (client side) |
| Whole-file reads | after the cycles and with no burner: the largest files of the list up to 256 MiB (141 files, 268,544,714 bytes), by 16 readers, cold (each file's pages dropped with `posix_fadvise(DONTNEED)` first) and then warm, **each phase 8 times over**, with the CPU time of the server and of its control group read before and after each phase (new in this measurement: format 2 of the record, `cold.cpu` and `warm.cpu`) |
| Samples | once a second: processes in D state, and the requests waiting on the mount's FUSE connection |
| CPU | per 1000 cycles: the server process's `utime` + `stime`, its control group's `system_usec`, and the node's busy time, over the 60 s; per GB of whole-file reads: the server's and its control group's kernel time over each phase |
| Runs | 6 per series; the first is left out, and each figure is the median of the other 5 with their least and most |

**The servers.** Each server ran as root in a `systemd-run` scope of its own (its control group
is the one measured), mounted with `mount(2)`, and was stopped by closing its standard input.

- `tsfuse-null-fs`: the INIT terms of a tree session (`InitConfig::tree()`: `max_pages` 256,
  readahead 128 KiB, `max_background` 1024; every flag it asks for was granted, as each server's
  last line in its log said), a tree mount (`MountOptions::tree()`), `--readers N` descriptors
  with a thread each. Its data file holds the files of the list one after another on 4 KiB
  boundaries (464,936,960 bytes); the runner let the server make it, so it is a hole and every READ is of
  zeros: the bytes do not change what the transport does with them, and a hole has page-cache
  pages like any file once read. The pipes of the splice path were 2 MiB (`F_SETPIPE_SZ`, as
  root). `library=tsfuse (tierstore dbcf42f5)` in the settings is the commit of the branch of
  this change; the code it names is the code this change adds.
- `null-fs`: as in the baseline (`komira-ai/fuser` at `0d8f5da`, 16 threads).

`cores/4` of the design is taken as the CPUs online divided by 4: 22.

**The regimes.** As in the baseline, and as the design asks for both the library regime and the
production regime:

| regime | entry and attribute timeouts | `OPEN` | series |
|---|---|---|---|
| `caches-off` (library) | 0: every `stat` is a `LOOKUP` or `GETATTR` | answered, `FOPEN_KEEP_CACHE` | null, V3, V4, V4m |
| `caches-on` | 32,000,000 s | answered, `FOPEN_KEEP_CACHE` | null, V3 |
| `no-open` (production) | 32,000,000 s | `ENOSYS`, so the kernel opens without asking | null, V3, V4, V4m |

V4 differs from V3 only in READ replies of 16 KiB and more, so its cycles (whose READ is 4096
bytes) are V3's by construction, and it ran in the two regimes the design names; the regime in
between is V3's alone.

### Reading

- **The knee of cloned readers (measured).** With the caches off, opens/s rise by 74% from 1
  reader to 2 and by 50% from 2 to 4, then by 2% from 4 to 8 (V4: 5%), and fall by 43% from 8 to
  22. The server CPU per 1000 cycles rises at every step: 438, 493, 654, 1,173 and 4,912 ms (its
  control group's kernel time 299, 348, 432, 900 and 4,619 ms). With the caches on the knee is the
  same: 195,313 opens/s at 4 readers against 182,668 at 8 and 108,297 at 22, at 20.2, 41.2 and
  157 ms per 1000 cycles. Past 4 readers a reader adds CPU and no opens.
- **Why (inferred, not measured).** The design predicts this (5.2): every clone polls the one
  input queue of the connection, so a request wakes every reader's `AsyncFd` and N-1 of them read
  `EAGAIN`. The kernel time growing faster than the readers (4,619 ms at 22 against 900 at 8, 5.1
  times for 2.75 times the readers) is what those wasted wakeups would cost; this harness does
  not count them.
- **Against `fuser` on 16 threads.** The control makes more opens/s than `tsfuse` at any reader
  count: 8,002 with the caches off (`tsfuse` at most 6,347, V4 at 8) and 235,858 with them on
  (`tsfuse` at most 195,313), at an open p50 of 16.4 against 20.8 ms (caches off, `tsfuse` at 8 readers). It spends
  three times the server CPU per cycle to do it (1,972 ms per 1000 cycles against 654 for
  `tsfuse` at 4 readers with the caches off; 65.3 against 20.2 with them on). Its 16 threads block
  in `read(2)` on one descriptor, where the kernel wakes one waiter per request; `tsfuse`'s readers
  wait in `epoll`, where every reader of the connection is woken (inferred from the two designs,
  not measured). A `tsfuse` reader count of 16 was not run.
- **Splice (V4 against V3), measured.** The cycles of V3 and V4 are the same by construction, and
  their opens/s differ within their ranges (caches off at 8 readers: 6,066, 5,733 to 6,446,
  against 6,347, 6,079 to 6,457). In the cold whole-file reads, V4's server CPU per GB is lower
  at 1, 2 and 4 readers: 465, 521 and 801 ms against 577, 694 and 880 with the caches off (19, 25
  and 9% less), 358, 456 and 703 against 465, 600 and 856 in the no-open regime (23, 24 and 18%
  less); at 8 readers it is the same (1,308 against 1,331; 968 against 968), and at 22 it is 2 to
  7% more. The cold read rate is the same or higher at 1 to 4 readers (1,638, 1,957 and 1,777
  MB/s against 1,536, 1,772 and 1,765 with the caches off; 2,037, 2,163 and 1,896 against 1,843,
  1,827 and 1,784 in no-open), within the ranges of the runs. Where the readers wake each other
  (8 and 22), what splice saves in copies is lost in the wakeups.
- **`SPLICE_F_MOVE` (V4m against V4 at 8 readers), measured.** With the caches off it is the same
  (1,327 against 1,308 ms per GB, 1,624 against 1,680 MB/s); in the no-open regime it costs 28%
  more CPU per GB (1,238 against 968) for 10% less cold MB/s (1,570 against 1,739). The kernel moves
  a page only where the source page can be stolen (5.2); here it saved nothing it could show.
- **Warm reads.** With the caches on or no `OPEN`, warm reads never reach the server (0.00 ms per
  GB in no-open), and the warm rate is the page cache's (6,200 to 8,200 MB/s for every server).
  With the caches off, `FOPEN_KEEP_CACHE` keeps the pages but the server still answers some READs
  (93 to 2,523 ms per GB); the warm CPU follows the reader count as the cold does.
- **No-open cycles.** In the no-open regime a cycle never reaches the server (0.00 ms per 1000
  cycles for every series): its 905,063 to 1,035,665 opens/s are the node, not the transport, and
  the spread between series is the node's noise.
- **The same-day control against the baseline day.** `null-fs` made 8,002, 235,858 and 1,027,885
  opens/s in the three regimes against 7,299, 255,927 and 1,002,042 in the baseline: the node of
  this measurement is within 10% of the baseline's, so the baseline's V1 and V2 figures stand for
  comparison (they were not run again; see below).
- **Load at start.** The one-minute load average when a run starts is the tail of the run before
  it (176 burners and 256 readers). The runner counted the processes of the farm's job user
  before and after each series: none, in all 30 series.

## Decisions the rules give

The decision rules of 17.1 were written before the data; their outcomes on these series:

- **The number of cloned readers is the knee of opens/s against CPU: 4.** At 4 readers the opens/s
  are the best of any reader count with the caches on and within 6% of the best with them off,
  at about half the server CPU per cycle of 8 readers. 4 is the knee of this node (88 CPUs); the reader
  count is a setting, and a node of other hardware (the LATER profile of section 21) is measured
  again before its default is taken from this one.
- **Splice replaces `pread` + `writev` above a threshold where it wins on CPU at equal MB/s: yes,
  at 16 KiB, at that reader count.** At 4 readers splice takes 9% (library regime) and 18%
  (production regime) off the server CPU per GB of cold reads at an equal read rate. (The rule
  speaks of CPU per 1000 requests; the whole-file phases read the same files the same way in
  every series, so per GB is per request times a constant.) The threshold was not varied.
- **`SPLICE_F_MOVE` stays off.** It saves no CPU, and in the production regime it costs some.
- **The rules on io_uring and on DONTNEED** are for V5 and for the real-core run: no outcome here.

## How to run it again

On a Linux node with `/dev/fuse`, as a user with `sudo`, from a build of this repository
(`cargo build --release -p fsbench`) and the baseline's list (`fsbench list`, as in the baseline
document):

1. A `tsfuse` series: the server in a scope of its own, served until its standard input closes
   (here a FIFO the runner holds open; the data file is made, as a hole, when it is not there):

   ```text
   mkfifo ctl
   sudo systemd-run --scope --unit=fsbench-v3-r4 -- fsbench tsfuse-null-fs --list tree.list \
     --mountpoint /run/fsbench/v3-r4 --data tsnull.data --entry-timeout-ms 0 \
     --attr-timeout-ms 0 --open explicit --readers 4 --reply writev < ctl > server.out &
   exec 3> ctl
   sudo fsbench run --list tree.list --tree /run/fsbench/v3-r4 --variant v3-r4 \
     --regime caches-off --server-pid <pid of fsbench tsfuse-null-fs> --out results.jsonl \
     --throughput-rounds 8 --setting "server=fsbench tsfuse-null-fs" \
     --setting "library=tsfuse (tierstore <commit>)" --setting readers=4 --setting reply=writev \
     --setting entry_timeout=0ms --setting attr_timeout=0ms --setting open=explicit
   exec 3>&-
   ```

   V4: `--reply splice` (and `--setting reply=splice --setting splice_min=16384`); V4m: also
   `--move-pages` (and `--setting move_pages=yes`). `caches-on`: `--entry-timeout-ms 32000000000
   --attr-timeout-ms 32000000000`; `no-open`: the same and `--open none`. When the input closes the
   server unmounts and writes one line of JSON to its output: the readers, the INIT flags granted
   and missing, `max_pages`, its pipe size, and the bytes it spliced and wrote by `writev`.

2. The control: `fsbench null-fs` with `--threads 16`, as step 5 of the baseline document, with
   `--throughput-rounds 8` on its `fsbench run`.

3. The series, in the order of the records: in each regime the control, then V3 at 1, 2, 4, 8 and
   22 readers, then (not in `caches-on`) V4 at the same counts and V4m at 8.

4. `fsbench report --results results.jsonl` prints the tables above.

## What this does not measure

- **The real core.** No `tierstore` file system is served on `tsfuse` yet (the tree file system
  of the redesign comes with its own task), so V3 and V4 ran on the null file system alone; the
  run on the real core, under a real build, is the next FUSE measurement.
- **The page cache that splice and `SPLICE_F_MOVE` cost the data file** (the "cache lost" of
  5.2). The data file here is a hole, and the node had no tool to count a file's resident pages
  that this harness could call without new `unsafe` code; it is measured with the real core,
  whose pack files hold real pages.
- **V6** (fuse3/rfuse3 and fuse-backend-rs). It would add two FUSE libraries to the workspace
  for one series each; the static feature table of 17.1 comes with the result tables.
- **V1 and V2 again.** They are `tierstore fs` releases, run as a second instance beside the
  node's own; the same-day control here is the null file system on their library, within 10% of
  its baseline figures.
- **Reader counts other than 1, 2, 4, 8 and 22**, splice thresholds other than 16 KiB, and the
  `tsfuse` reader count that matches `fuser`'s 16 threads.
- **Latency inside the server**: every latency here is the client's.
