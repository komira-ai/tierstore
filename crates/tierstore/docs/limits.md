# Limits

What tierstore does not do on main, so that you can decide before you depend on it.

- **No TLS on the S3 listener.** It serves plain HTTP, and an S3 tier's endpoint is `http://`. Put it on a network you trust, or terminate TLS in front of it. (The OCI front has TLS, `--oci-tls-cert` and `--oci-tls-key`.)
- **One bucket, path-style, SigV4 in the header.** No virtual-host addressing, no session tokens, no STS. Presigned PUT URLs are the one exception to signing in the header.
- **Objects are immutable.** A put is create-only; there is no overwrite and no copy. A delete removes both tiers' copies, the hot tier's first.
- **Bodies are streamed, with limits.** A put or part is passed on as it arrives and never held whole, but it is bounded by `--max-request-bytes` (256 MiB by default); a larger object needs the flag raised, a multipart upload or a presigned PUT. At most `--max-concurrent-puts` bodies are taken at once. A manifest served by the OCI front is read whole (at most 4 MiB).
- **No scrub of stored objects.** Nothing re-reads a storage node's objects to find bit rot. A cache node in a release does not hash a hit again either: an object that rots in its directory is served until it is evicted (the scrub below is not in a release yet). The OCI front checks a blob's SHA-256 as it serves it; the S3 front checks the checksums a client sends when it writes.
- **Copies are not atomic with deletes at the edges.** Two puts of one key at the same moment, one to each tier, may both succeed when the hot tier has just filled; and a put dropped by its caller after the hot tier took it and before its journal entry was written leaves an object that is never copied. See the proxy's source notes for these.
- **A deleted key can come back if a copy's outcome is never learned.** A copy to the cold tier reads the hot tier again after it writes, and takes its own cold object back if the hot tier no longer holds the object, so a delete that runs during a copy leaves nothing behind. If the reconciler is killed or loses its lease between the write and that read, or the cold tier takes the write after the call timed out, the cold object stays, and a get of the deleted key finds it. A delete entry no longer removes it. An operator deletes the key from the cold tier. A copy removes its own object by the content tag it reads just before: a put of the same bytes that went straight to the cold tier in that moment is removed with it.
- **A cold object that differs from the hot one is replaced.** When the reconciler finds the cold tier holding a key with other bytes than the hot tier's object, the hot tier's object replaces it (a get returns the hot tier's first), as long as the hot tier still holds the object it read. If the cold tier refuses the delete that the replacement needs (a retention lock, a missing permission), the copy fails in every pass and the journal of that proxy stops at it; the failure is in the pass's report. Where the two tiers tag content by different functions (a directory hot tier over an S3 cold tier), the cold object is read once to compare the bytes, for each such copy.
- **A conditional delete is best effort on S3.** A tier over a store that enforces `If-Match` on a DELETE (Amazon S3 does) deletes only the object with the tag it was given. A store that ignores the header (the start-up self-test says which, in a `conditional delete:` line) gets a HEAD, a comparison and a plain DELETE, with a window between the two requests in which another writer's replacement of the key is deleted. A start whose probe could not be answered (the line says `could not ask`) is on this way too, whatever the store does. A directory tier does the same in one step, among the calls of one process only; a plain delete there waits for a replacement in progress, through its temporary write and sync. The tag names content: an object deleted and put again with the same bytes has the same tag.
- **A hot tier that is lost loses what was not yet copied.** A put is acknowledged when its journal entry is durable in the hot tier, not when the cold tier has a copy. The reconciler publishes the copy lag in the hot tier; `/metricz` does not export it.
- **Checksums.** CRC-32, CRC-32C, SHA-1, SHA-256 and `Content-MD5` are checked; CRC-64/NVMe, `aws-chunked` bodies and trailing checksums are refused with 501 `NotImplemented`. A client SDK needs its checksum settings turned to "when required".
- **Anonymous OCI reads.** The registry front never asks for a token. Put only public images under its prefix.
- **No update mechanism.** The host updater does not manage tierstore yet; place the next binary and restart.
- **Release tarballs for Linux (x86_64, arm64) and macOS (Apple silicon).** The example unit and its account are for Linux. On macOS tierstore runs as one LaunchDaemon, a build node on loopback, and the update hook updates it by a plain restart with a gap in serving; the hand-over without a gap is Linux only ([The update hook](update-hook.md#on-a-mac)).

## Not in a release yet

- A background scrub of a build-node cache: it re-reads each cached object at `local_cache.scrub_rate` and drops one whose bytes no longer hash to the digest the cache recorded, so the next read fills it again. A storage node's objects are not scrubbed.
