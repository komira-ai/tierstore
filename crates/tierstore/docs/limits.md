# Limits

What tierstore does not do on main, so that you can decide before you depend on it.

- **No TLS on the S3 listener.** It serves plain HTTP, and an S3 tier's endpoint is `http://`. Put it on a network you trust, or terminate TLS in front of it. (The OCI front has TLS, `--oci-tls-cert` and `--oci-tls-key`.)
- **One bucket, path-style, SigV4 in the header.** No virtual-host addressing, no session tokens, no STS. Presigned PUT URLs are the one exception to signing in the header.
- **Objects are immutable.** A put is create-only; there is no overwrite and no copy. A delete removes both tiers' copies.
- **Bodies are streamed, with limits.** A put or part is passed on as it arrives and never held whole, but it is bounded by `--max-request-bytes` (256 MiB by default); a larger object needs the flag raised, a multipart upload or a presigned PUT. At most `--max-concurrent-puts` bodies are taken at once. A manifest served by the OCI front is read whole (at most 4 MiB).
- **No scrub of stored objects.** Nothing re-reads a storage node's objects to find bit rot. A cache node in a release does not hash a hit again either: an object that rots in its directory is served until it is evicted (the scrub below is not in a release yet). The OCI front checks a blob's SHA-256 as it serves it; the S3 front checks the checksums a client sends when it writes.
- **Copies are not atomic with deletes at the edges.** Two puts of one key at the same moment, one to each tier, may both succeed when the hot tier has just filled; and a put dropped by its caller after the hot tier took it and before its journal entry was written leaves an object that is never copied. A mirror entry (the journal entry of a copy-back) that a later put or delete of its key supersedes is skipped by the reconciler, not applied. A get that copies an object back into the hot tier while it is deleted can be served that copy until the reconciler's next pass, which finds the cold tier without the object and drops it. A mirror entry names two tags, the cold tier's tag of the object read and the hot tier's tag of the copy, and the two are never compared with each other (a directory tier and an S3 tier tag the same bytes differently). The hot tag is given by the create-only write that made the copy (the tag of the file a directory tier published, the `ETag` of the answer to the PUT on S3), with no HEAD after it, so it is the copy's whatever another proxy puts under the key later, and every removal of the copy (a failed journal entry, the reconciler's drop) is a delete on that tag; a write that gave no tag deletes nothing. Because the tag names content, a later put of the very same bytes has the same tag and is not told from the copy. the reconciler keeps a copy as an eviction candidate only if the cold object has the first and the hot object the second, and drops a copy by the second; an entry written before the hot tag existed names none, so it drops nothing and makes nothing an eviction candidate. A delete entry of a key that a reserved put or a mirror last put is not applied to the cold tier (the proxy removed the cold object itself); one that is applied more than the journal retention after that put is applied as any other is, and can take an object that a put straight to the cold tier made after the delete. See the proxy's source notes for these.
- **A conditional delete is best effort on S3.** A tier over a store that enforces `If-Match` on a DELETE (Amazon S3 does) deletes only the object with the tag it was given. A tier with `conditional_delete = false`, which is the default of an S3 tier (tierstore does not ask the store, and does not know an Amazon S3 endpoint from another), gets a HEAD, a comparison and a plain DELETE, with a window between the two requests in which another writer's replacement of the key is deleted. A store that takes the header and ignores it must have the setting `false`. A directory tier does the same in one step, among the calls of one process only; a plain delete there waits for a replacement in progress, through its temporary write and sync. The tag names content: an object deleted and put again with the same bytes has the same tag.
- **A hot tier that is lost loses what was not yet copied.** A put is acknowledged when its journal entry is durable in the hot tier, not when the cold tier has a copy. The reconciler publishes the copy lag in the hot tier; `/metricz` does not export it.
- **A reconciler pass that outlasts the lease is not fenced.** It copies, and may evict, beside the process that took the lease over. It stores no checkpoint, prunes nothing and publishes no usage once it finds the lease gone, and a stored checkpoint never moves backwards, but the check is a read, not a fence ([The reconciler's checkpoint](operations.md#the-reconcilers-checkpoint)).
- **Checksums.** CRC-32, CRC-32C, SHA-1, SHA-256 and `Content-MD5` are checked; CRC-64/NVMe, `aws-chunked` bodies and trailing checksums are refused with 501 `NotImplemented`. A client SDK needs its checksum settings turned to "when required".
- **Anonymous OCI reads.** The registry front never asks for a token. Put only public images under its prefix.
- **No update mechanism in a release yet.** The update hook is written for hostkeeper's host updater, which is in development, and no release carries the hook as a step an updater calls (see [the update hook](update-hook.md#not-in-a-release-yet)); until then place the next binary and restart.
- **Release tarballs for Linux (x86_64, arm64) and macOS (Apple silicon).** The example unit and its account are for Linux. On macOS tierstore runs as one LaunchDaemon, a build node on loopback, and the update hook updates it by a plain restart with a gap in serving; the hand-over without a gap is Linux only ([The update hook](update-hook.md#on-a-mac)).

## Not in a release yet

- A background scrub of a build-node cache: it re-reads each cached object at `local_cache.scrub_rate` and drops one whose bytes no longer hash to the digest the cache recorded, so the next read fills it again. A storage node's objects are not scrubbed.

## A storage node with a local cache

On main, not in v0.0.41. A file with `[hot_store]`, `[cold_store]` and `[local_cache]` serves reads from a disk cache in front of the node's own proxy. What it does not do:

- **A kept object is not checked again.** A key that another process deletes or re-puts, over the same tiers, is served by this cache as it was until it is evicted, and its listing and the cache's hits can disagree. Several such nodes over the same tiers, or a storage node without a cache beside one, are for prefixes that are never rewritten (`cache = true` only on content-addressed prefixes, as for a build node).
- **Versions are compared by size.** Over two tiers an object's tag moves with the tier, so a fill and a long read of a key that is not named by its content (`cas/l/<digest>` keys are hash-checked) cannot tell two same-size versions apart: another process deleting and re-putting such a key with other bytes of the same size during one fill is not detected.
- **The ETag of a hit may differ from the ETag of a miss.** A hit gives the tag the cache recorded at its fill, a miss the tag of the tier that answers; a client that sends `If-Match` or `If-None-Match` with a tag it read before the fill can be refused for it.
- **A fill of a cold-only object is not copied up.** The cache reads an object in ranged chunks (8 MiB), and the proxy answers a ranged read that misses the hot tier from the cold tier for that range alone, so a fill holds one chunk in memory whatever the size of the object, and the hot tier gets no copy. Only a read without a range (a client of the proxy without a cache) reads a cold-only object whole and copies it up.
- **Paths are checked by text.** The cache path against the tiers' directories, the lock file and the key files of `[oci]` is a check by component of the strings in the file, with `.` and `..` resolved, not of the places they lead to through links. The cache path and the directory of a `dir` tier must be absolute in this shape.
