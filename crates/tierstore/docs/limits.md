# Limits

What tierstore does not do, so that you can decide before you depend on it.

- **Moving a store onto the markers and back is a pause of writes, and the old release must be fenced.** `tierstore format-epoch --activate-marks` needs the store drained (writes answer 503 while the release that knows markers is rolled), the marks bucket made by the operator, and the credential of the release before the markers rotated; the verb takes the last on the operator's word (`--old-release-fenced`). Going back is `--drain` over `active-marks`, which waits for every marker to be run to its end and has no time limit. There is no pause-free path ([Rolling out the markers](operations.md#rolling-out-the-markers-and-going-back)). The entry protocol is still in this release; a later one removes it.
- **TLS on the S3 listener is optional, and a tier's endpoint has none.** `server.tls_cert_file` and `server.tls_key_file` make the S3 listener serve HTTPS; without them it serves plain HTTP and, off loopback, the start prints a warning. An S3 tier's endpoint is still `http://`, so a build node cannot use an HTTPS front as its upstream. (The OCI front has its own, `params.tls_cert_file` and `params.tls_key_file`.)
- **One bucket, SigV4 in the header, virtual-hosted-style only for the domains you list.** A request is path-style (`/<bucket>/<key>`) unless its `Host` is `<bucket>.<domain>` for a domain in `server.domains`, which is empty by default. tierstore does not make the DNS names or the certificates: the names `<bucket>.<domain>` must resolve to the server (a wildcard record), and a TLS listener needs a certificate that covers `*.<domain>`. The one bucket must be reachable by a DNS-style name for a client to use it virtual-hosted. On a bucket's host the paths `/healthz`, `/readyz`, `/usagez` and `/metricz` are keys, not probes. No session tokens, no STS. GetBucketLocation answers with `server.region` (an empty constraint for `us-east-1`, as S3 does). ListBuckets lists that one bucket, with the time `_tiering/format` was last written as its creation date (the time the format change was made active; a store with no such object gets the time the server started; the server is not told when the bucket was made, and stores nothing for it) and `tierstore` as the owner, to the full key and read-only keys only; A bucket of another name is `NoSuchBucket` for HeadBucket, CreateBucket and DeleteBucket: there is one bucket per process, set by `server.bucket`, and no call makes or removes one. HeadBucket carries `x-amz-bucket-region`. CreateBucket of the bucket answers as S3 answers a create of a bucket you own (200 in `us-east-1`, 409 `BucketAlreadyOwnedByYou` in any other region), and a `LocationConstraint` other than `server.region` is 400 `IllegalLocationConstraintException`. DeleteBucket is 409 `BucketNotEmpty` while the bucket has an object and 403 `AccessDenied` when it has none (S3 would delete it); the bucket and its objects are never touched. **A bucket has no settings.** Versioning, object lock, ACL, policy, lifecycle, CORS, encryption, tags, replication, website, notification, acceleration, logging, request payment, ownership controls and public access block cannot be set (the writes are 501); a read answers as S3 does for a bucket with none: an empty document (versioning, notification, acceleration, logging), the payer `BucketOwner`, the ACL with the owner's `FULL_CONTROL`, or the 404 code S3 gives (`NoSuchBucketPolicy`, `ObjectLockConfigurationNotFoundError`, `NoSuchLifecycleConfiguration`, `NoSuchCORSConfiguration`, `ServerSideEncryptionConfigurationNotFoundError`, `NoSuchTagSet`, ...). Amazon S3 itself now reports default SSE-S3 encryption for every bucket; tierstore does not encrypt what it stores and so does not claim to. Versions, analytics, metrics, inventory and intelligent-tiering configurations are 501. Presigned GET and PUT URLs are the one exception to signing in the header.
- **DeleteObjects is for the full key, and has no versions.** `POST /<bucket>?delete` (up to 1000 keys, `Quiet`, a hash of the document in `Content-MD5` or an `x-amz-checksum-*` header (CRC-64/NVMe included), as S3 requires) deletes each key as a single DeleteObject does and answers for each key. A read-only, scoped, GC or presigning key is refused with 403: the keys are in the body, and a scoped key's prefixes are not checked key by key. A key of the proxy (`_journal/`, `_tiering/`, `_entries/`) is an `AccessDenied` of that key alone, and a key with a `VersionId` is a `NotImplemented` of that key alone. A document is read whole, up to what 1000 keys of the longest key fill (about 6 MiB). `server.delete_concurrency` bounds how many of its deletes run together.
- **A multipart upload stays in the tier it began in.** It is made in the hot tier when that has room, and in the cold tier when it is full; a part is never moved. A hot tier that fills up in the middle of an upload answers the part (or the completion) 503 `SlowDown` and keeps the upload; the client retries, or aborts and starts again (see [Multipart uploads](operations.md#multipart-uploads)). The parts of uploads in flight are not in the usage the budget is compared with. An upload nobody completes is kept until its client aborts it, as in S3, and its parts hold hot-tier space until then; `hot_store.abandoned_upload_after` makes the reconciler abort uploads older than a limit you choose (off by default).
- **Whether a key can be overwritten depends on the format phase.** On a store on the entry format (`active`) a put is create-only and there is no overwrite; on the marker format (`active-marks`) a plain put replaces the key, `If-None-Match: *` still creates only and `If-Match` replaces conditionally ([operations](operations.md#the-format-object-and-the-pause-of-writes)). Scoped and presigned writes are create-only under either. There is no copy. A delete removes both tiers' copies. The bucket is not versioned: ListObjectVersions lists each object as one version with the id `null` (`IsLatest` true, no delete markers), and a GET, HEAD or DELETE of an object may name `versionId=null`; any other version id is 404 `NoSuchVersion`, so a delete is permanent and there is no undelete.
- **Bodies are streamed, with limits.** A put or part is passed on as it arrives and never held whole, but it is bounded by `server.max_request_bytes` (256 MiB by default); a larger object needs the key raised, a multipart upload or a presigned PUT. At most `server.max_concurrent_puts` bodies are taken at once. A manifest served by the OCI front is read whole (at most 4 MiB).
- **Keys follow S3's rules, with three exceptions, listed in the next three items.** A key is any UTF-8 text of 1 to 1024 bytes: spaces, `+`, `%`, `&`, `<`, `?`, `#`, parentheses, non-ASCII text, dots in a name (`a..b`, `...`), `//` and a leading or trailing `/` all work, over every tier and through a cache, a storage node and an S3 tier in a chain, and the S3 client escapes them. A key over 1024 bytes is answered 400 `KeyTooLongError`, as S3 does. The three items that follow are what S3 takes and tierstore does not.
- **A dot segment** (a path segment, the text between `/`, that is exactly `.` or `..`, as in `a/../b`) is refused by an S3 tier, 400 `InvalidArgument` with a message that names the rule (it is not a length error). It is a limit of the store, and of the HTTP client of the tier: the client removes such segments from a path before it sends the request, so the request would name another object, and the farm's MinIO refuses such a name itself (measured on `RELEASE.2025-09-07T16-13-09Z` with the path sent as written: 400 `XMinioInvalidResourceName`, "Resource name contains bad components", for a PUT and a GET of `a/../c`, `a/./d` and `x/%2e%2e/e`). Amazon S3 takes the key; whether another store does was not measured. A directory tier takes such a key, but a proxy with an S3 cold tier cannot copy it there, as before. A presigned or scoped-key grant refuses the same segments and nothing more: `a..b` is a name.
- **A path segment over 255 bytes** is refused by MinIO (measured on `RELEASE.2025-09-07T16-13-09Z`: 400 `XMinioInvalidObjectName` for a segment of 256 bytes, for `k` repeated 1024 times, and for 341 three-byte characters in one segment). It is MinIO's limit and not tierstore's: the front's own checks take any key of up to 1024 bytes, and tierstore does not check segment lengths itself. So on a MinIO tier a key of up to 1024 bytes works if no segment is over 255 bytes; for text of 3-byte characters that is 85 characters in a segment. What tierstore maps MinIO's 400 to was not checked.
- **A character XML 1.0 cannot hold** (U+0000 to U+0008, U+000B, U+000C, U+000E to U+001F, U+FFFE, U+FFFF) is refused 400 `InvalidArgument`, because a listing is XML, and this refusal lets a client that does not ask for `encoding-type=url` list every key. A presigned or scoped-key grant refuses exactly these characters too.
- Not an exception: **a directory tier** keeps a key as one file named by the key with every byte but ASCII letters, digits and a few marks written as three bytes; a key whose name would be over 255 bytes (about 85 non-ASCII or special characters, or 255 plain ones) gets a file named by the first 100 bytes of that name, a `~` and the SHA-256 of the key in hex, and the file holds the key, so every key up to 1024 bytes works on a directory tier, and a listing of such a key costs one more read of the start of its file. Objects put before this change keep their files and stay readable, listed and deletable; the release before this one lists a long key's file under the 165-byte key its name decodes to, and cannot read it. A bucket written by something else that holds a key the client cannot name (a `.` or `..` segment) makes a listing of that bucket fail with an error that names the key.
- **No scrub of stored objects.** Nothing re-reads a storage node's objects to find bit rot. A cache node in a release does not hash a hit again either, with one exception: after a stop that was not clean (see [the cache and a power cut](operations.md#the-cache-and-a-power-cut)) each object is hashed on its first read. Otherwise an object that rots in its directory is served until it is evicted (the scrub below is not in a release yet). The OCI front checks a blob's SHA-256 as it serves it; the S3 front checks the checksums a client sends when it writes.
- **A stalled process can act on a key that another has taken since.** The entry of a key serialises a put, a delete, a copy to the cold tier, a copy-back and an eviction of it, and a delete that meets a copy in flight waits for the reconciler to release the entry and is answered 503 at the request deadline. What the entry cannot stop is a process that stalls between its check and its write (a store call that answers after its deadline, or a frozen process that wakes after another has taken over): the design document states these residuals as R1 to R4 (section 11) and the tests pin them. Two puts of one key at once end with one winner: the other is answered 503 while the first is in flight and 412 once it has landed. A put dropped by its caller after the object reached the hot tier and before its entry was made pending leaves the entry held until its owner has departed (`hot_store.departure`); the reconciler then takes it and finds the object.
- **A conditional delete is best effort on S3.** A tier over a store that enforces `If-Match` on a DELETE (Amazon S3 does) deletes only the object with the tag it was given. A tier with `conditional_delete = false`, which is the default of an S3 tier (tierstore does not ask the store, and does not know an Amazon S3 endpoint from another), gets a HEAD, a comparison and a plain DELETE, with a window between the two requests in which another writer's replacement of the key is deleted. A store that takes the header and ignores it must have the setting `false`. A directory tier does the same in one step, among the calls of one process only; a plain delete there waits for a replacement in progress, through its temporary write and sync. The tag names content: an object deleted and put again with the same bytes has the same tag.
- **A hot tier that is lost loses what was not yet copied.** A put is acknowledged when its entry says it landed (`PUT`, `PENDING`) in the hot tier, not when the cold tier has a copy. The reconciler publishes the copy lag in the hot tier; `/metricz` does not export it.
- **A reconciler step that loses the lease is not fenced.** It may finish a copy beside the process that took the lease over, and a step with less than the margin of its lease left starts no copy and no delete; the copy is create-only and an entry is changed on its content tag, so the new holder finds what was done ([The reconciler's lease](operations.md#the-reconcilers-lease)).
- **Checksums.** CRC-32, CRC-32C, CRC-64/NVMe, SHA-1, SHA-256 and `Content-MD5` are checked on the body of a put and of each part, as the body arrives. The checksum a client sends on CompleteMultipartUpload (S3's full-object CRC-64/NVMe, or a composite checksum of the parts) is not checked, because the checksums of the parts are not kept; the answers to a put and to a part carry no `x-amz-checksum-*` header. A body in `aws-chunked` framing (the three `STREAMING-` payloads of S3) is decoded as it arrives, on a put and on a part, and a trailing checksum is checked like a header one; `server.max_request_bytes` bounds the framed body, which is a little longer than the object. A `STREAMING-AWS4-ECDSA-P256-SHA256-PAYLOAD` body (SigV4a) is refused with 501.
- **A listing walks the keys of a prefix it folds.** ListObjectsV2 takes `prefix`, `max-keys`, `continuation-token`, `start-after`, `delimiter` (common prefixes count against `max-keys`) and `encoding-type=url`; ListObjects (version 1, a `GET` of the bucket with no `list-type=2`) takes `prefix`, `marker`, `max-keys`, `delimiter` and `encoding-type=url`, and answers `Marker`, `NextMarker` (only for a truncated page of a request with a delimiter, as S3 does; without a delimiter the client takes the last key) and an `Owner` for every object, over the same walk and with the same ETag; each object has its `ETag`, in quotes, which is the `ETag` of a HEAD or a GET of it through the same front (over two tiers, the tier that answers the HEAD: the hot tier's where both hold the key; through a cache, the tag the cache recorded for a kept object, and the upstream's for one it does not keep; an S3 tier gives the listing's `ETag`, so a store that leaves it out is refused as one without `LastModified` is; a directory tier reads the tag from the first bytes of each file it lists); `fetch-owner=true` gives each object an `Owner` (the same one for all, named `tierstore`: the proxy has no accounts). The backend cannot skip a prefix, so a page after a common prefix reads the keys under it again to pass them (a thousand at a time), and a listing with a delimiter over a prefix of millions of keys is slow. ListMultipartUploads takes `delimiter` and `encoding-type=url` the same way. A key with a character XML 1.0 forbids is still refused at the put, so that a client that does not ask for `encoding-type=url` can list every key.
- **An OCI front with an upstream registry dials out, and re-checks a tag on each pull.** With an `upstream` param on an `oci` interface the process connects to the upstream registry, so its host must be allowed to; a request for an object that is not stored waits for it to be pulled and stored whole (there is no first byte before that, and two requests for one object pull it twice). Each `GET` or `HEAD` of a tag that is stored costs one `HEAD` to the upstream, which counts against its rate limit; if the upstream moved the tag, the new manifest is pulled and the tag gets a new version, and if the re-check fails or takes longer than `params.upstream.recheck_timeout` (`5s`) as a whole, the stored tag is served (counted in `tierstore_oci_tag_recheck_failures_total`). A pull by digest is never re-checked. A blob or manifest pulled is kept until something deletes it. A token is fetched for each pull and not kept. See [configuration](configuration.md#paramsupstream).
- **Anonymous OCI reads.** Unless `params.require_auth` is true, the registry front never asks for a token. Put only public images under its prefix.
- **The first update to this release is a restart.** `tierstore update-hook` is the contract of hostkeeper, which runs its steps as root ([the update hook](update-hook.md#the-shape-of-an-update)). A hand-over needs both releases to list the capability `handoff-socket-v1` and a `handoff_socket` key in the `[server]` table. This binary is the first to list it, so the update to it from an earlier release is a restart with a gap. A node with a `[local_cache]` table also needs both releases to list `handoff-cache-v1`, so the first update to this release of such a node is a restart too, and its params must say `mode = "restart"`, since its configuration cannot have the key while the earlier release runs; later updates hand over ([the hand-over socket](update-hook.md#the-hand-over-socket)).
- **Release tarballs for Linux (x86_64, arm64) and macOS (Apple silicon).** The example unit and its account are for Linux. On macOS tierstore runs as one LaunchDaemon, a build node on loopback, and the update hook updates it by a plain restart with a gap in serving; the hand-over without a gap is Linux only ([The update hook](update-hook.md#on-a-mac)).

## Not in a release yet

- `local_cache.revalidate_after`, a bound on how long a cache node serves an object that another process deleted or wrote over. Unset, the default, a hit is served from the disk until the entry is evicted. Set to a duration T, a hit whose entry is older than T (since it was filled or last checked) is checked first by one HEAD to the upstream, and the body is never read for it: a changed or missing object drops the entry and the read goes upstream, and the object is served stale for at most T after the change plus the HEAD that finds it. If that HEAD fails, the cached copy is served and the failure is logged and counted, so the bound is also "while the upstream answers". The check compares the tag and the size, so a same-size overwrite is seen, also over a proxy of two tiers; there the tag is the tag of the tier that answers, so an object that the other tier answers for since the fill (the hot copy was evicted, say) may have another tag and is read once more, after which the entry holds the new tag. A node's own writes and deletes drop the entry at once whatever the setting.
- A plain `PUT` through a cache that writes through (no `If-None-Match`) replaces the object only where the upstream does: a proxy on `active-marks` or an S3 bucket. The cache sends it as a plain put with no HEAD before it, keeps the new copy under the upstream's tag, and forgets its older copy even if the upstream refuses the put. A put that replaces on a tag (`If-Match`) and a copy are refused by the cache. Other nodes' caches still serve their older copy of the key until it is evicted or `local_cache.revalidate_after` has passed. Two puts of one key at once on one cache, one of them plain, leave the key uncached (the next read fills it), because the order in which the upstream took them is not known to the cache.
- `local_cache.head_before_put`, default `true`. With `false`, a create-only put through a cache sends no HEAD of the key to the upstream before the body, for an upstream that refuses a key it holds before it reads the body (a proxy whose format is `active-marks`); against an upstream that refuses only after the body (a proxy in the entry protocol, a plain S3 bucket) a put of a key it holds then sends the whole body first and is refused at its end.
- A background scrub of a build-node cache: it re-reads each cached object at `local_cache.scrub_rate` and drops one whose bytes no longer hash to the digest the cache recorded, so the next read fills it again. A storage node's objects are not scrubbed.

## A storage node with a local cache

A file with `[hot_store]`, `[cold_store]` and `[local_cache]` serves reads from a disk cache in front of the node's own proxy. What it does not do:

- **A kept object is not checked again.** (Unless `local_cache.revalidate_after` is set, which is not in a release yet; see below.) A key that another process deletes or re-puts, over the same tiers, is served by this cache as it was until it is evicted, and its listing and the cache's hits can disagree. Several such nodes over the same tiers, or a storage node without a cache beside one, are for prefixes that are never rewritten (`cache = true` only on content-addressed prefixes, as for a build node).
- **Versions are compared by size.** Over two tiers an object's tag moves with the tier, so a fill and a long read of a key that is not named by its content (`cas/l/<digest>` keys are hash-checked) cannot tell two same-size versions apart: another process deleting and re-putting such a key with other bytes of the same size during one fill is not detected.
- **The ETag of a hit may differ from the ETag of a miss.** A hit gives the tag the cache recorded at its fill, a miss the tag of the tier that answers; a client that sends `If-Match` or `If-None-Match` with a tag it read before the fill can be refused for it.
- **A fill of a cold-only object is not copied up.** The cache reads an object in ranged chunks (8 MiB), and the proxy answers a ranged read that misses the hot tier from the cold tier for that range alone, so a fill holds one chunk in memory whatever the size of the object, and the hot tier gets no copy. Only a read without a range (a client of the proxy without a cache) reads a cold-only object whole and copies it up.
- **Paths are checked by text.** The cache path against the tiers' directories, the lock file and the key files of an `oci` interface is a check by component of the strings in the file, with `.` and `..` resolved, not of the places they lead to through links. The cache path and the directory of a `dir` tier must be absolute in this shape.
