# The update hook

`tierstore update-hook` is the part of the binary that hostkeeper runs, as root, to put a new release of tierstore in place. hostkeeper owns the release directories and the link `current` that names the release in use; the hook owns the service: which instance runs, and the proof that the new release serves. This page is for the person who writes the package manifest for tierstore or reads what a step said.

On Linux (systemd) an update is a hand-over without a gap when both releases can do it, and a restart with a gap when they cannot. A node whose file has an `fs` interface hands its mount over with its sockets and its cache lock in one conversation when both releases list `handoff-service-v1` (see [the one hand-over](operations.md#the-fs-interface-the-mount-in-the-nodes-own-process)): the new instance serves the mount from the old one's `bye` and is the cache's writer once the old one's cache writes in flight have ended, while the old one still drains. On macOS (launchd) an update is a hand-over to the next image of the job's process (`SIGUSR2`, see [drain and restart](operations.md#drain-and-restart)) when both releases list `handoff-exec-v1`, and a restart with a gap otherwise; a node that holds a mount refuses the restart (`mode_unsupported`) unless the params say `mode = "restart"`. (`tierstore fs` on a Mac can hand its NFS socket over, see section 0 of `docs/design/tierstore-handover.md` in the repository; the hook does not use that. When the params name the fs job, the update is a restart, and the hook stops the fs job before the main job and starts it after, see [on a Mac](update-hook.md#on-a-mac).) Both arms are in every build; the params file chooses between them.

## The command line

```text
tierstore update-hook prepare <staged release> --params <file>
tierstore update-hook <cutover|verify|rollback|cleanup|uninstall|restore> --params <file>
```

hostkeeper runs one step per process. `prepare` is given the staged release directory twice, as the argument and as `updater.staged_release` in the params file; the two must agree, or the step is refused (`bad_args`). The verb is answered before the server's flags are parsed, and no value comes from the environment.

A step reports in two ways:

- the exit status: `0` success, `1` failure, `75` deferred (not now: hostkeeper runs the step again after `retry_after_secs`, except a deferred `prepare` or `cutover`, which it rolls back and orders the update again later);
- the last line of standard output, one JSON object: `class` (`release` or `environment`: whom a failure is blamed on), `reversible` (whether the hook can still undo what it did; `false` is the commit), `promotion_pending`, and when set `reason` (a token from [the reasons](update-hook.md#the-reasons)), `retry_after_secs` and `detail` (a sentence for the log).

The steps are `prepare`, `cutover`, `verify`, `rollback`, `cleanup`, `uninstall` and `restore`. `restore` is the boot step.

## What hostkeeper does and what the hook does

hostkeeper switches the link `current` to the new release before `cutover`, and back to the previous release before `rollback`; it relinks the units the package ships (`units/`) with it. The hook never moves `current`. hostkeeper keeps every package directory closed to every user but root, and the service runs as its own account, so the units of hostkeeper's archive package do not run the binary inside the package: they run `/usr/local/libexec/tierstore/tierstore`, a copy that the hook, as root, makes of the binary of the release the link names before it starts the service. `cutover` copies the staged release's `bin/tierstore` there, `rollback` the previous release's, and the boot step `restore` the current release's (the release its params name), so starting an instance after the switch starts the release the link names: that is how `cutover` runs the new release and `rollback` the old.

The copy is owned by root, mode 0755, in directories that the hook makes when they are absent (mode 0755) and that must be root's, not links, and not writable by others, from `/usr` down to `/usr/local/libexec/tierstore`, which its group may not write either (a group-writable `/usr/local`, root:staff mode 2775, is accepted); a directory that is not is refused (`host_failed`), and so is a release binary that is a link, not root's, or writable by a group or others. Only a release of the archive package (anything at `bin/tierstore` or `bin`) is copied: a release of a native package (the Debian or RPM package, or the macOS installer package, whose job runs its own installed binary) is left to its package manager, and a host that has no copy is not looked at by `uninstall`. The hook writes the copy to a temporary file beside it and renames it over the old one, so an instance that runs the old copy (the live instance of a hand-over) keeps running it until it exits. A first install's `rollback` and `uninstall` remove the copy.

With the Debian or RPM package the units run `/usr/libexec/tierstore/tierstore`, and the hook copies nothing: the package manager replaces that binary at hostkeeper's `activate`, before `cutover`, so `cutover` starts the new binary; hostkeeper re-installs the previous package before the hook's `rollback` starts the old instance. The hook finds such a release's binary, for `prepare`, at `<release>/tree/usr/libexec/tierstore/tierstore`. The manifest of the apt entry names the hook command `/usr/libexec/tierstore/tierstore update-hook`.

The hook keeps one record of where an update stands, reads it at the start of every step and writes it as the step's acts happen, so a step that was killed is run again and ends where it would have. A step sets state rather than does things once.

## The params file

hostkeeper writes one TOML table of scalars for each run. A dotted key is quoted. A key the hook does not know is ignored.

| Key | Meaning |
| --- | --- |
| `"updater.staged_release"` | required: the unpacked version directory of the release being installed |
| `"updater.target_version"` | required: the version its binary must report, such as `0.5.0+0123456789ab` |
| `"updater.previous_release"` and `"updater.previous_version"` | both or neither: the release the host ran before. Neither means a first install |
| `"updater.promotion_ceiling_secs"` | read and not acted on: hostkeeper applies the ceiling itself |
| `service_manager` | `"systemd"` (the default when the key is absent) or `"launchd"`; any other value is refused by every step, `prepare` included (`service_manager_unknown`) |
| `launchd_label` | required with `service_manager = "launchd"`: the label of the one job |
| `fs_launchd_label` | optional, read only with `service_manager = "launchd"` (with systemd it is ignored, like any other key the hook does not read): the label of the launchd job of `tierstore fs`, which the hook boots out before the main job and in after it |
| `config_file` | the path of the node's configuration file; `prepare` reads it |
| `mode` | `"restart"` is the only value: the update is a restart even when both releases could hand over (see [the hand-over socket](update-hook.md#the-hand-over-socket)), and a node that holds a mount is not refused the restart (`mode_unsupported`) |

The boot step and `uninstall` carry the manifest's keys, the current release as `updater.staged_release` and `updater.target_version`, and no previous release. Every step after `prepare` refuses params whose staged release or target version differ from the update the record holds (`bad_params`), but for a `rollback` that finds the record at rest, which has nothing to roll back (see `rollback`).

A version is read back from the build gauge `tierstore_build_info{version="0.5.0",commit="0123456789ab"}` of `/metricz`; it matches a target version that is the version alone or the version, `+` and the commit.

## The shape of an update

### On Linux

The package ships one unit template, `tierstore@.service`, and the hook alternates between its two instances, `tierstore@a` and `tierstore@b`. Both run the binary (`/usr/local/libexec/tierstore/tierstore`, the hook's copy, with the archive package; `/usr/libexec/tierstore/tierstore` with the Debian or RPM package) and serve the public port 9300. Clients keep calling 9300; there is no redirect and no second port.

An instance starts only when its start marker exists: the template has `ConditionPathExists=/var/lib/tierstore/run-%i`, so `/var/lib/tierstore/run-a` starts `tierstore@a` and `/var/lib/tierstore/run-b` starts `tierstore@b`. A start that finds its marker missing is skipped, not failed: the unit stays inactive. With the archive package both instances are enabled at boot; with the Debian or RPM package nothing enables them, and hostkeeper starts the run units at its own start and the boot step `restore` starts the recorded instance. Either way only the one with a marker runs.

The record names `live`, the instance that serves at rest, and, during an update, `next`, the other one. In `cutover` the hook sets the marker of `next` and starts it.

- **Hand-over.** `next` asks `live` for its listening sockets over the hand-over socket and takes them: no connection the kernel holds is reset. `live` then drains and exits with status 0, which the template does not restart (`Restart=on-failure`). No step waits for the drain (see [an old instance that drains](update-hook.md#an-old-instance-that-drains)).
- **Restart.** The hook stops `live` first (the stop waits for its drain), then starts `next`: new connections are refused in between.
- **First install.** No instance serves, so `next` (`a`) starts and binds the port normally.

The next update starts the other letter: a, b, a, and so on. A cache node serves read-only while another instance holds the cache lock, and takes the lock, and becomes read-write, by itself once the old instance has exited; the hook only watches for it (and `cutover` waits for it before it starts the fs instance, see [cutover](update-hook.md#cutover)).

### On a Mac

One job, whose label is `launchd_label`, loaded from the plist `/Library/LaunchDaemons/tierstore.plist` (hostkeeper links it from the archive package's `units/`), which runs `/usr/local/libexec/tierstore/tierstore` as `_tierstore`: the hook's copy, as on Linux. (The macOS installer package's plist runs its own binary, and the hook copies nothing for it.) An update is one of two ways, decided in `prepare`, `cutover` and `rollback` alike from the same inputs (the record holds no mode). It is a **hand-over** when it has a previous release, the params name no fs job (`fs_launchd_label`), `mode` is not `"restart"`, and both releases list `handoff-exec-v1` (the hook asks the staged and then the previous release). `cutover` of a hand-over, with the job loaded and not yet serving the target, copies the staged release's binary there, sends the job's process `SIGUSR2` (`launchctl kill SIGUSR2 system/<label>`), and waits for the build gauge on 9300 to name the target: the process drains, keeps its sockets and its mount, and executes the new binary under the same pid, so launchd sees no exit, and nothing is unmounted. A job that is not loaded is started by bootstrap, as in a restart. Every other update is a **restart** with a gap: `cutover` copies the staged release's binary there, boots the job out, then bootstraps the plist, which starts the release `current` now names. A restart unmounts a mount the process holds, so `prepare` refuses it, with `mode_unsupported`, for a node whose file has an `fs` interface and whose params name no fs job, unless the params say `mode = "restart"` (for a node whose jobs are drained); the detail names `handoff-exec-v1` and the releases that lack it. A first install, `restore` and `uninstall` boot the job in or out as before. The hook waits up to 240 seconds for `launchctl bootout` of the job: it returns when the process has exited, which launchd forces at the plist's `ExitTimeOut` of 210 seconds. A first install bootstraps the job, and boots nothing out when the job is not loaded; when it is loaded and does not serve the target (a copy installed by hand that the first install takes over), it is booted out first, as in an update, with the fs job before it. The record has no `live`, `next` or `mode`, and `prepare` does not ask for a hand-over socket. `prepare` checks that the `config_file` param is there and names a file; it asks the releases for their capabilities only when the params leave the way open (see above), and runs a release to check the file only for a hand-over: the staged release's `--check-config` of the file, which fails the step with `config_refused` (the new image would exit on a file it refuses, and launchd would start it again). A restart checks nothing, so a configuration that the live or the staged release refuses is found when the job starts. A Mac has no `handoff_socket` key to hand sockets over by: the hand-over is the exec, and a configuration with `[server] handoff_socket` and `[local_cache]` is no different. The hook touches the one label and, when `fs_launchd_label` is given, that one.

The fs job, when the params name it, is the job of `tierstore fs`: the plist `/Library/LaunchDaemons/tierstore-fs.plist` (the macOS installer package puts it there; the hook loads it and never writes it) and the configuration `/usr/local/tierstore/etc/fs.toml`, whose `[fs] mountpoint` is the mount point (`/run/tierstore/fs` when the key is left out). The fs process serves a NFS mount that jobs read their trees through, and a mount whose server is gone blocks whatever touches it, so an update never leaves the mount in place beside a stopped fs process:

- Every boot-out of the main job (`cutover` of an update or of a first install over a loaded job, `rollback`, `uninstall`) is preceded by the boot-out of the fs job, when it is loaded. The hook waits for the job to be gone for up to 180 seconds (`launchctl bootout` returns when the process has exited, and launchd kills it at the plist's `ExitTimeOut` of 150 seconds) and then looks at most 30 times, a second apart, for the domain to let it go.
- It then runs `/sbin/mount` and looks for a line with ` on <mount point> (` (the mount point as written and as it resolves, since `mount` prints the resolved path). A mount that is gone lets the step go on with the main job. A mount that is still listed ends the step with `not_ready` and a detail that names the mount point: nothing else is stopped, the main job is left as it is (running, when it ran), and the fs job is booted in again, which takes the mount over. A list that cannot be had is `host_failed`, with the fs job booted in again.
- The mount point comes from `/usr/local/tierstore/etc/fs.toml` before anything is stopped: a file that is not there is `config_missing`, one that is not TOML or whose `fs.mountpoint` is not an absolute path is `config_refused`, and the detail says that nothing was stopped. The file is read only when the fs job is loaded. A first install looks at the fs job too, before it starts the main job: an fs job a copy installed by hand left loaded is booted out, its mount checked, the same way.
- After the main job serves (`cutover`, `rollback`) or is loaded (`restore`), the fs job is booted in when it is not loaded. A first install loads it after the main job too; nothing else loads it. A run again after a crash does the same from whatever it finds.
- A config package drives the fs job only when its params carry `fs_launchd_label` (its manifest names it): then the arm's `cutover` and `rollback` stop it, check its mount and boot it in again exactly as for a release. With no `fs_launchd_label` the config hook leaves the fs job alone and restarts the main job only, except for the switch to one process (the config hook's section below), which boots the fs job out and disables it.

## The second unit, `tierstore-fs`

`tierstore fs` (see [the virtual build file system](operations.md#the-virtual-build-file-system)) has a unit of its own, `tierstore-fs@.service`, with instances `a` and `b`, the same binary as the first unit and the start marker `/var/lib/tierstore/run-fs-<instance>`. A release lists `handoff-fs-v1` in `tierstore --capabilities` when its `tierstore fs` takes the mount from a running instance of the other letter (it asks on `fs.handoff_socket`, stores the `/dev/fuse` descriptor in its unit's descriptor store, and says `READY=1` once it serves), and offers it to the next one. The hook updates the unit in the same steps as the first, and the two follow one rule: in an update the hook never stops an fs instance that may be taking or holding the mount (`uninstall` and the boot step `restore` stop instances too, as they end or make the node's units afresh). Stopping an instance that has no successor drops its descriptor store, the kernel aborts the connection and the jobs fail; and an instance that is taking the mount does not act on SIGTERM until it serves, so one stopped while its take is in progress that then completes leaves at once, after the old instance has ended, and the mount is aborted. An instance that failed to take the mount, or that `rollback` finds activating (it may be in a `Restart=on-failure` retry), therefore has its marker removed instead: the template tests for the marker at every start with `ExecCondition=`, automatic restarts included (systemd evaluates `ConditionPathExists=` only at a start from inactive or failed, not at a restart of `Restart=`), so with the marker gone the next restart is skipped, the unit is left inactive and not failed, and the instance ends by itself.

**Which nodes.** The hook manages the unit on a node where an instance of it runs, or where the record already names one (`fs_live`). `prepare` looks at both instances: both running defers the step (75, `host_not_ready`, retry after 30 seconds: the old instance of an earlier update still drains); one running is `fs_live`; none running is the record's `fs_live` (a node that never had the unit has none, and the hook never touches the unit there). A first install manages no fs process: an operator writes `/etc/tierstore/fs.toml` and makes the marker `run-fs-a` by hand, and from the next update on the hook manages it.

**Hand-over, or left alone.** The fs process is handed over when both releases list `handoff-fs-v1`: `fs_next` is the other letter of `fs_live`. For any other pair the fs process is left alone, running the release it runs, and the details of `prepare` and `cutover` say so (`tierstore-fs@a is left on its release`). The detail of `verify` then says first that the fs process still runs release X and the update installed Y, with both versions (`tierstore-fs@a (pid 4101) still runs release 0.4.0+0123456789ab, and the update installed 0.5.0+0123456789ab: it was left on its release`), and `verify` does not fail for it: that would force the restart the hook refuses. The hook does not restart it: on a kernel without `FUSE_HAS_RESEND` (before Linux 6.9) a restart of the process can leave requests unanswered until `fs.recover_wait` aborts the connection, which fails jobs, and an update must not fail a job. The release the fs process runs after a hand-over is the binary at `/usr/local/libexec/tierstore/tierstore` that the hook installed before it started the instance, and `verify` checks it on the process itself (see [verify](update-hook.md#verify)). `mode = "restart"` and a directory hot tier are about the first unit only: the fs process is still handed over, as its hand-over has no gap and shares no lease. The runtime directory's stored formats are additive and each release reads the other's (see [stored formats](https://github.com/komira-ai/tierstore/blob/main/docs/stored-formats.md)), so the hook checks no layout: a release that changes a layout in a way the other cannot read stops listing `handoff-fs-v1` and lists a new word instead, and the hook then leaves the process alone until both releases list it.

**An update prepared by an earlier release.** With a Debian or RPM package the hook command is the installed binary, so the `prepare` of an update is run by the release that is installed before it, which may not know the fs unit and writes a record with no `fs_live` and no `fs_next`; `cutover` runs the new release's hook. When `cutover` finds such a record (neither key, no `swapped`) it plans the fs process itself, with the rule of `prepare`, before the step's first act (before the binary is copied or any unit is touched; a plan that fails, a capabilities list that cannot be read, changes nothing) and saves the record with the plan: exactly one fs instance runs, both releases (the staged one and the previous one) list `handoff-fs-v1` and so `fs_live` is that instance and `fs_next` the other letter, or one of them does not and `fs_live` is left alone with no `fs_next`. It saves the record with the plan first (the plan is not an act, and a `rollback` or a run again then sees it), and the detail of the step says what it did. With both fs instances running, `cutover` cannot defer (the store has started) and leaves the fs process alone, saying so; with none running, or with no previous release, it plans nothing. The limit of this: the first update from a release whose hook does not know the fs unit, if it is rolled back, is rolled back by that previous release's hook, which ignores `fs_live` and `fs_next` and does nothing to the fs unit. The fs process then stays on the new release, on its new instance with only its marker (`cutover` removed the old one's), and serves; the next update, run by a hook that knows the unit, manages it again from the instance that runs.

**The start timeout.** A start of an fs instance that takes the mount over lasts up to `fs.handoff_wait` (120 seconds by default) plus the attachments the new process makes again, and the process does not act on SIGTERM until it serves, so a start timeout below that would end a take half way. The unit sets `TimeoutStartSec=300`, and the hook waits up to 330 seconds for `systemctl start` of an fs instance (the store's start is limited to 120 seconds), so that it sees systemd's verdict and does not kill `systemctl` first. A node that raises `fs.handoff_wait` keeps `TimeoutStartSec` of the fs unit above it (and below the hook's 330 seconds).

**What each step does to it** (see below): `cutover` starts the first unit and then the fs instance, which takes the mount from the old one; `verify` and `cleanup` need it active, and `verify` needs its process to run the binary the update installed; `cleanup` removes the old one's marker and neither waits for it nor stops it; `rollback` goes the other way, the fs process first; `restore` starts the instance the record names; `uninstall` stops the instances that run. The hook does not look at the mount itself, since the fs process has no port: it judges the unit's state, and a unit of `Type=notify` is active only after it said `READY=1`, which a new instance does after it has taken the mount. That is also why `systemctl start tierstore-fs@<next>` returns success only once the take is done.

## The steps

### prepare

Nothing a client sees changes, and nothing is started.

- A record whose update is past `cutover` and not committed is refused (`out_of_order`): finish or roll back the update in flight first. A record at rest, committed or idle, starts a fresh update. A record whose update is committed (`stopping`) but still in flight, which a `cleanup` of an earlier release leaves when it gave up while the old instance drained, is finished first, as `cleanup` finishes it (the old instances' markers go, the new ones become `live` and `fs_live`, and the record is saved at rest), and the update is prepared from it; the detail begins with `finished the committed update to <version>`. That record is an earlier update's, so `prepare` reports `reversible` `true`, and a `rollback` of the new update finds nothing to roll back.
- Both arms: the `config_file` param must be there (`bad_params`) and name a file that exists (`config_missing`).
- systemd, an update, no `mode = "restart"`: the hook reads the configuration. A `handoff_socket` key of the `[server]` table that is an empty string or not a string, and a configuration that is not TOML (with the parse message), are refused with `handoff_not_configured`. A key that is left out is not: the socket is then the default, `handoff.sock` in the unit's state directory (see "The hand-over socket"). A configuration whose hot tier is a directory (`[hot_store]` `kind = "dir"`) is a restart, and is not asked for a socket.
- systemd: the hook runs `<staged release>/bin/tierstore --capabilities`, or, when nothing is at that path, `<staged release>/tree/usr/libexec/tierstore/tierstore --capabilities` (a release of the Debian or RPM package); a staged release with neither (the refusal names both), or a binary that does not run, is `host_failed`, and for an update the previous release's too. The mode is a hand-over when `mode` is not `"restart"`, the hot tier is not a directory, and both list `handoff-socket-v1` (for a configuration with a top-level `[local_cache]` table, both also list `handoff-cache-v1`; for one that leaves `handoff_socket` out, both also list `handoff-state-dir-v1`), and a restart otherwise. A node whose file has an `fs` interface (it holds a mount) also needs `handoff-service-v1` in both lists: an update of it that would be a restart, because a word is missing or the hot tier is a directory, fails `prepare` with `mode_unsupported` before anything is recorded or started, and the detail names the releases that lack a word and says that a restart would drop the mount under running jobs. `mode = "restart"` in the params overrides it (for a node whose jobs are drained), and the update is then the restart as for any node. A first install is never refused, and a node with no `fs` interface is decided as above. A first install records no mode.
- systemd, an update or a first install, whenever the params name a `config_file` (with `mode = "restart"` too): before anything is recorded or stopped, the hook has the staged release and then, for an update, the previous release check the configuration, by running `<release>/bin/tierstore --config <config_file> --check-config` (or the package path above). Exit 0 is a configuration the release accepts. Exit 2 is one it refuses: `prepare` fails with `config_refused`, and the detail says whether the staged or the previous release refused, its path, and the refusal line it printed. Any other exit, a signal, a binary that cannot be started and a check that does not end within 10 seconds are `host_failed`. Nothing is recorded and no unit is touched in either case. A first install has no previous release, so only the staged one checks. `mode = "restart"` without a `config_file` checks nothing. When the hook runs as root, the check runs as the account `tierstore` (the template's `User=`, found in `/etc/passwd`; an account that is not there is `host_failed`), because the check refuses key files that the user it runs as does not own, and the unit does not run as root. A hook that is not root runs the check as itself. hostkeeper keeps every staged package closed to every user but root (a package may hold a secret), so the account cannot reach the staged binary by its path: on Linux the hook opens the binary itself, holds what it opened to the same checks as the path (a regular file, not a link, owned by root, not writable by a group or others), and the check, started under the account's user and group ids, executes that open file (`/proc/self/fd/<n>`), which needs no search of the directories above it; the account needs only the right to execute the file. The configuration file is still named by its path, so the check proves that the account can read it and every key file it names. A failure names the command (the binary by its path), the user it ran as with its ids, and the error. The check is the loader's only: what a start finds of the disk, the tiers or the heartbeat is not checked.
- systemd: it looks at the units, on every run, also when the record holds an update in flight that never reached `swapped` (a `cutover` that failed may have started its instance, which then took the sockets while the record still names the other one). Both running defers the step (75, `host_not_ready`, retry after 30 seconds). One running is `live`. None running is the record's `live` on an update, and no instance on a first install. `next` is the other one of `live`, or `a` when there is none.
- systemd, an update: it looks at the two `tierstore-fs` units (see [the second unit](update-hook.md#the-second-unit-tierstore-fs)): both running defers the step the same way (`host_not_ready`, 30 seconds, naming `tierstore-fs@a` and `tierstore-fs@b`). On a node that has an fs process, whether it is handed over is decided by `handoff-fs-v1` in both releases' lists, whatever the first unit's mode is: the previous release is asked for its capabilities for that even when `mode = "restart"` or the hot tier makes the first unit's mode a restart (a previous release that cannot be asked is `host_failed`, as for the mode). A first install and a node with no fs process make no other fs call.
- It saves the record: updating, from the previous release, to the staged release, the version, and on systemd `live`, `next`, the mode, and, on a node that has an fs process, `fs_live` and, when it is handed over, `fs_next`. The detail ends with the fs process's part (`; fs serving tierstore-fs@a, next tierstore-fs@b`, or `; fs tierstore-fs@a is left on its release: both releases must list handoff-fs-v1`).

### cutover

Needs an update in flight that has not committed (`out_of_order`) with params that match it. On a Mac whose params name the fs job, an update, or a first install that finds the fs job loaded, first boots the fs job out and checks that its mount is gone (see [on a Mac](update-hook.md#on-a-mac)), and boots it in once the main job serves; a mount that stays is `not_ready`, with nothing else stopped. Before it stops or starts anything else, it copies the staged release's binary to `/usr/local/libexec/tierstore/tierstore` (an archive release; nothing for a release of a native package); a copy that cannot be made fails the step with `host_failed`, with `live` still serving. As above, the mode decides how `next` starts. After the start the hook waits, up to 1000 looks a second apart, for a look at 9300 that `/readyz` answers and whose build gauge names the target version, and then for the gauge to name it three times in a row within 60 looks. In a hand-over the old instance answers `/readyz` until the new one has opened its local cache and taken the sockets, which on a slow disk takes minutes, so the wait is for the target version and not for any answer. `/readyz` never answered is `not_ready`; answered but never by the target version is `probe_failed`. Then, when the record names an `fs_next` (or, for a record that `prepare` of an earlier release wrote with no fs keys, when `cutover` has planned the hand-over itself and saved the record first, see the second unit), the fs instance. A new instance is started only while the old one runs, since one that finds nobody to ask makes a mount afresh, which over a held mount is a collision: when the old instance is `activating` or `deactivating` the hook starts nothing and the step defers (`draining`, retry after 10 seconds; the detail says the old instance is restarting or stopping and `cutover` runs again), and when it is `failed` or `inactive` it holds nothing (its unit, and with it its descriptor store, is gone) and the new instance makes the mount afresh, the only way, which the detail says. An `fs_next` that is already active is not started again. Nor is one started while the new store's `/readyz` says `read-only`: it answers the file system's calls of the cache only once it holds the cache lock (after the old store exited and its cache was scanned again, minutes on a large cache), and a hand-over while nothing answers them waits on the old fs instance's uploads and unpins, each until its deadline. In a hand-over the old store holds the lock until it has drained and exited, which it does by itself only after the new one serves, so the step waits for the lock in the same run: it looks at `/readyz` a second apart, up to 2400 looks (the old store's settle and drain deadline, 910 s with the defaults, and a scan of the cache as long as the slowest read-only open, with a margin), until it says `read-write` (or `ready`), and then goes on; the detail then adds how long it took (`; the store took the cache lock after 39 s`). It does not defer on the first read-only answer: hostkeeper rolls a deferred `cutover` back and orders the update again later, and never runs `cutover` again, so a deferral there would end every update of a node with a local cache in a rollback. A store still read-only after the last look defers the step (`draining`; the detail says the store still serves read-only and the fs instance is not started), with the store started and no fs unit touched, and hostkeeper rolls it back. Otherwise the hook lays down the marker, starts `tierstore-fs@<fs_next>`, which takes the mount from the old instance and says `READY=1` (the old one deactivates and ends by itself with status 0), and looks at the unit, which must be active; at once after it, the hook removes the old instance's marker, so that the two markers exist together only during the take (`cleanup` removes it too, which changes nothing). A start that fails, or leaves the unit anything but active, has taken nothing and the old instance serves on: the hook does not stop the new instance (it may be a `Restart=on-failure` retry that is taking the mount, and a stop then aborts the mount when the take completes), removes its marker so that systemd does not start it again, and fails the step (a start that succeeded followed by a look at the unit that fails leaves the marker: the unit may hold the mount as its only holder, and the step fails with that error); the detail says the marker was removed so that it is not started again and the old instance serves on (`not_ready` for a unit that is not active, `unit_failed` for a start that failed), still reversible. The record gets `swapped` after both units serve. A failure is reported and nothing is undone: hostkeeper switches `current` back and runs `rollback`. A re-run after `swapped` looks again and, if the new instance serves the target and the fs instance is active, succeeds without starting anything. If `fs_live` names an instance that does not run, the new fs instance finds nobody to ask and mounts afresh: nothing held the mount. The detail ends with `; tierstore-fs@b holds the mount`, or `; tierstore-fs@a is left on its release`, and then, when the step waited for the cache lock, with how long it took.

### verify

An observation. After the commit it looks at the service again (`observed`) and says whether the promotion is pending; a look that `/readyz` does not answer ready (the old instance may still drain after `cleanup` and answer 503 on the sockets the two share) defers with `not_ready` and `verify_retry_secs`, not reversible, as before the commit, and is not a failure. Before it, it needs `swapped` (`out_of_order`), the new instance (on launchd, the job) running (`not_ready`), on a node whose fs process was handed over the new fs instance active (`activating` defers like the first unit's, anything else is `not_ready` naming `tierstore-fs@<fs_next>`) and its process running the binary the update installed, and the build gauge on 9300 naming the target version (`wrong_build`, exit 1). A new instance that answers `ready read-only` has not taken the cache's write role yet: until it has, the node's jobs cannot fill their trees through the mount or reach the mount provider, so `verify` defers with `not_ready` and `verify_retry_secs` and records nothing, and hostkeeper keeps the node in its update and ends the deferrals itself at `verify_deadline_secs`. Then, on a node whose file has a `mount-provider` interface, the mount check (below). Otherwise it records `verified` and exits 0. After the commit a build node that still serves read-only says `promotion_pending: true`, and hostkeeper runs `verify` again until it does not, within its promotion ceiling.

**The mount check.** An instance that is active, answers `/readyz` and reports the target build may still refuse every job's tree. So on a build node, once the new instance is the cache's writer (it binds the provider's socket only then), `verify` drives the node's mount provider end to end, as jobscheduler's agent does for a job. It uses the socket the interface names and two small trees that the release carries for the purpose. Both are stored in a form the build service writes today. The first has its version 2 list at `cas/l/<id>` and its L2 sidecar at `cas/l2/<id>`, and the provider places it from the sidecar. The second has its list alone, and the provider places it from the list. Their files lie in one pack under `cas/check/`. A node with a mount provider answers the reads of exactly these objects itself, in front of its upstream: the check reads nothing from the network and writes nothing to the store. Its sources are those of the agent `tierstore-verify`, which no job's are, under the run `js.tierstore-verify`. The check never sweeps, so it is safe while jobs run. The steps are:

1. `Release` of both sources, so that nothing of a check that ended halfway remains.
2. `Prepare` of each source with its tree's list, read-only.
3. `Mount` of each. The answer must be a directory below the interface's `mountpoint`, with no `..` leading out of it.
4. A read of every path below each directory through the mount, as root and without following a link, compared with the tree: every file's bytes, every directory, and the link's target, with nothing more.
5. `Release` of both, then a `Mount` of each, which must be answered `UNAVAILABLE` with `the source is not prepared here`: the provider finds no placement at the source's path. A directory answered then is a placement that outlived its release. Any other answer is judged as at any call, below.

The calls have the bounds jobscheduler's agent gives them (`Prepare` 10 s, `Mount` 30 s, `Release` 5 s), and the read has 30 s. A call that passes its bound is a provider that does not answer.

The outcomes are:

- **Failure, `provider_refused`.** Any status but `UNAVAILABLE` at any call fails `verify`, before the commit and so reversible. The detail names the call, the tree and its key, and gives the status and the provider's reason as it said it (`the mount provider at /var/lib/tierstore/provider.sock refused Mount of the tree without an L2 sidecar (cas/l/<id>) with FailedPrecondition: no tree list at cas/l/<id>`).
- **Failure, `mounted_tree_wrong`.** Any of these fails `verify`:
  - a tree read back wrong: a path missing, of another kind, or not in the tree, a file of other bytes, or a link to another target;
  - a read that fails;
  - a directory outside the mount;
  - a placement that outlives its release.

  The detail names the tree, its directory and the first difference. A file that differs is described by its size, never its bytes.
- **Deferral, `not_ready`.** A provider that does not answer (its socket not bound yet), or that answers `UNAVAILABLE` (a tree not placed within the call's wait), defers `verify` with `not_ready` and `verify_retry_secs`. hostkeeper ends the deferrals itself at `verify_deadline_secs`. A node whose file has a `mount-provider` interface and no `fs` interface has no file system that serves its trees, and its provider answers every `Prepare` `UNAVAILABLE` saying so: such a node cannot run a job from the provider, and its `verify` defers until that deadline, after which hostkeeper rolls the update back.

Before a check that got as far as `Prepare` ends with a failure or a deferral, it asks for the release of both sources, each even when the other's release is not answered. A placement the provider cannot release then is released by the first step of the next check, or ends at `trees.ttl_max`. A node whose file has no `mount-provider` interface, or whose params name no `config_file`, has no check. An interface with no absolute `socket` or `mountpoint` is `config_refused`. After the commit, `verify` does not run the check again.

**The binary of the fs process.** An active unit does not say which binary its process runs. On a node whose fs process was handed over, `verify` reads the main process of `tierstore-fs@<fs_next>` from systemd (the unit's `MainPID`) and the file its `/proc/<pid>/exe` names, and requires it to be the file at `/usr/local/libexec/tierstore/tierstore` that the update installed: the same device and inode. The hook installs its copy by a rename, so a process that still runs an older copy runs a file that no longer has that name: its link reads `/usr/local/libexec/tierstore/tierstore (deleted)` and the inodes differ. That fails the step with `not_ready`, before the commit and so reversible, and the detail names the unit, the pid, both paths and both files (`tierstore-fs@b (pid 4102) runs /usr/local/libexec/tierstore/tierstore (deleted) (device 2049, inode 10), not the binary the update installed, /usr/local/libexec/tierstore/tierstore (device 2049, inode 11): it is still on an older release`). A unit that systemd names no main process of is `not_ready` too (a `systemctl show` that fails is `unit_failed`), and a process whose link cannot be read or followed (it is gone, or the hook may not look at it), or an installed binary that cannot be looked at, is `host_failed` with words of its own: none of them is a pass.

On a node whose fs process the update left alone (the two releases do not both list `handoff-fs-v1`), `verify` does not fail for it. Its detail says first that the fs process still runs release X and the update installed Y, with both versions, before what it says of the store (`tierstore-fs@a (pid 4101) still runs release 0.4.0+0123456789ab, and the update installed 0.5.0+0123456789ab: it was left on its release; 0.5.0+0123456789ab serves on port 9300`). The fs process's version is what its own binary prints for `--version`, run as `/proc/<pid>/exe --version` (which runs the file the process runs, also when its name was replaced): the fs process serves no port and so no build gauge to read. A process that runs the installed release already is said to (`runs 0.5.0+0123456789ab, the release the update installed`); one with no process, or whose pid or version cannot be had, is said to be so, with the reason, and the step still succeeds. A record with no `fs_live` (a node with no fs process, or a record written by a hook that does not know the fs unit) has nothing of the fs process looked at, as before.

### rollback

Runs with `current` already back at the previous release (and, for the Debian or RPM package, with the previous package re-installed). Before it starts anything, the hook copies the previous release's binary back to `/usr/local/libexec/tierstore/tierstore` (an archive release), so starting an instance starts the previous binary. Not updating: nothing to roll back, exit 0. A record at rest that names another update than the params (the params' update was never recorded: its `prepare` failed, or never ran) also has nothing to roll back: exit 0, reversible, and the detail names the params' update and the last one on record; the record and the units are left alone. After the commit of the update the params name: `committed`, exit 1. On launchd likewise. With the fs job named, the fs job is booted out first, with the same mount check (`not_ready` when the mount stays, the update left on record and the main job as it is), and booted in after the previous release serves.

- **First install.** The instance `cutover` started is stopped and its marker removed (on launchd the job is booted out, whatever runs under its label, and the fs job before it), the copy of the binary is removed, and the step fails with `no_previous_release`: there is nothing to go back to. The record keeps the update in flight with no markers, so a re-run says the same and a later `prepare` starts afresh.
- **Update, restart mode** (and launchd, for a restart): the new instance is stopped, the old one started, and the hook waits for the previous version to serve; the record is idle again.
- **Update, launchd hand-over:** the previous release's binary is put back at `/usr/local/libexec/tierstore/tierstore` and the job's process is sent `SIGUSR2` again, which executes it: the hook waits for the previous version to serve, and the record is idle again. A job that is not loaded is bootstrapped. There is no way back for a process that executed a new image: if that image cannot serve at all, it is this step that puts the old one in place.
- **The fs process** (when the record names an `fs_next`), first, before the first unit, in whichever mode the first unit rolls back: if the new fs instance holds the mount (active, or deactivating after it gave it away) and the old one runs, one of them drains and the step defers with `draining`; if the old one does not run it is started with its marker, takes the mount back from the new one, which ends by itself, and the step defers with `draining` until it has; a new instance that is only `activating` (a start that failed and is retrying, or a take in progress) is not stopped: its marker is removed so that it is not started again, and the step defers with `draining`; it ends by itself, either failed, or inactive once `ExecCondition=` skips its next restart (the next run finds it holds nothing), or active after it took the mount (the next run takes the mount back). A new instance that is failed or inactive holds nothing. The new instance is never stopped, and its marker goes once it is out. The record is idle again with `fs_live` the old instance. The limit: a rollback run by the previous release's hook (the first update from a release that does not know the fs unit, which `cutover` planned itself) does nothing to the fs unit: the fs process stays on the new release, on the new instance, and serves, until the next update's hook manages it.
- **Update, hand-over mode:** if the new instance runs it holds the sockets. If the old instance still runs (it is draining after it handed over), the step defers with `draining` (75, retry after 10 seconds). Otherwise the old instance is started, takes the sockets back from the new one, which exits, and the hook waits for the previous version to serve. If the new instance is not running, an old instance that still serves means `cutover` never took over, and an old instance that does not serve is a drain that will end; with none running the old one is started cold. A new instance that is still draining after the sockets went back defers the step again (`draining`); the run after it finishes.

### cleanup

The commit, and the end of the update. It needs a `verify` that succeeded (`not_verified`). Before the commit it confirms again, freshly, that the new instance runs and serves the target, and that the new fs instance is active when there is one (`not_confirmed`; nothing is committed), then records `stopping`. From then on `reversible` is `false`: `rollback` is refused. On systemd the same run then finishes the update, whatever the old instances are doing: it removes the old instance's marker and, on a node whose fs process was handed over, the old fs instance's, records the new instance as `live` and the new fs instance as `fs_live`, with no update in flight, and exits 0. It never stops an old instance and does not wait for one: an old instance of a hand-over ends by itself, in a time that is not the hook's to know (see [an old instance that drains](update-hook.md#an-old-instance-that-drains)), and the detail names each one that still runs (`committed: tierstore@b serves; tierstore-fs@a still drains and ends by itself`). A `cleanup` that ends between the commit and the end (a crash, a record that cannot be written) is run again by hostkeeper and finishes then. On launchd there is no instance to retire. A re-run after `cleanup` finished says there is nothing left to clean.

### uninstall

Stops both instances (the job, on launchd, after the fs job when the params name it and its mount is gone, `not_ready` when it stays; on systemd also each `tierstore-fs` instance that runs, and only those, as `systemctl stop` of a unit that is not loaded fails), removes the markers (the fs unit's too) and the copy of the binary at `/usr/local/libexec/tierstore/tierstore`, and records no instance. It leaves the data, the cache and the configuration (`/var/lib/tierstore` apart from the markers, `/etc/tierstore`; on a Mac, `/usr/local/tierstore`) and the record directory as they are.

### restore

The boot step. On a Mac it loads the job when it is not loaded, and then the fs job when the params name it and it is not loaded. It starts the instance the record names, and only it: the recorded `live`, or `next` when an update is in flight and `cutover` finished (`swapped`). Any other instance has its marker removed, and is stopped if it runs while the one the record names is not active; while that one is active, the other is the old instance of a hand-over that still drains (hostkeeper runs the boot step at every start of its own, not only after a reboot), and it is left to end by itself; the marker of the one that starts is set again if it was missing, which repairs a marker that disagrees with the record. Before the start the hook copies the binary of the release its params name (the current release) to `/usr/local/libexec/tierstore/tierstore`, so the instance runs the release `current` names whatever copy a step that died left there. Then the fs instance the record names (`fs_next` when an update that hands the fs process over has swapped, else `fs_live`) gets the same: its marker is set, the other's removed, the other stopped if it is active or deactivating while the one the record names is not active (one that is only `activating` may be taking the mount, and one beside an active instance of the record is the old instance of a hand-over that drains: neither is stopped, its marker goes and it ends by itself), and it is started, after the first unit. A record whose update is committed and still in flight is then finished, as `cleanup` finishes it. A record that names no fs instance makes no fs call. No record, or no instance in it, is success with nothing copied or started. On launchd it copies the binary and bootstraps the plist when the job is not loaded, and does nothing when it is.

## An old instance that drains

After a hand-over the old instance of each unit ends by itself. The store's drains until its last request is answered, within its `--drain-deadline`. The fs process of this release ends at once after `ready`: it answered every request it read, its commits of the put directory included, before it said `done`, and it leaves its memory and files to the end of the process rather than freeing them one by one. The fs process of an earlier release frees its whole state before it ends, which on a node whose process held tens of gigabytes, part of it swapped out, took minutes; nothing a job does depends on it meanwhile. No step waits for either, and none stops one. `cleanup` finishes the update at once (see [cleanup](update-hook.md#cleanup)); the old instance has no marker from then on, so systemd never starts it again, and the record names only the new instances. Each later step reads the units themselves:

- `prepare` of the next update finds both instances of a unit running and defers (75, `host_not_ready`, retry after 30 seconds), having recorded no update (a committed record still in flight is finished first, see [prepare](update-hook.md#prepare)). hostkeeper then runs `rollback`, which has nothing to roll back, reports the update deferred, and orders it again later (its coordinator waits at least 300 seconds, doubling up to an hour, and at least the 30 the hook asked for), with no limit on the number of times: the host waits, and the update is not failed. Once the old instance has ended, the next `prepare` goes on from the new instances.
- `rollback` of the update that drains is refused once `cleanup` began (`committed`), as before; hostkeeper does not run it after a `cleanup` that succeeded.
- `restore`, after a reboot, starts only the new instances: the old ones have no marker. At a start of hostkeeper with no reboot it finds the new instances active and the old ones draining, stops nothing, and keeps only the new markers.
- `uninstall` stops every instance that runs, the old ones too: it ends the service.

## The record

`state.json` in `/var/lib/tierstore-hook` (the state directory, `STATE_DIR`), which only root can use; the hook makes it when it is absent, and neither hostkeeper nor `uninstall` removes it. It is replaced whole (a temporary file, synced, renamed over) under an exclusive lock, so two steps never run at once: a step that finds the lock held fails with `locked`. The record is JSON with `schema` 1, `kind` `single`, `updating`, `from`, `to`, `version`, `markers` (`swapped`, `verified`, `stopping`, in that order of need), and on systemd `live`, `next` and `mode`, and, on a node that has an fs process, `fs_live` (the `tierstore-fs` instance that serves at rest, or served before the update in flight) and `fs_next` (while an update that hands the fs process over is in flight). Both are optional keys, written only when set, so that the schema stays 1 and a hook of the previous release reads this record and ignores them; so is `reload`, the config hook's key of a change applied in place (below), which never goes with `next`, `mode`, `fs_next` or `fs_switch` (`state_invalid`). `swapped` and `verified` follow their acts; `stopping` is written before its act. A record that does not decode, names an instance that is not `a` or `b`, names `fs_next` with no `fs_live` or outside an update, names the same instance as `fs_live` and `fs_next`, or has markers out of order is `state_invalid`, and nothing else is touched. A key the hook does not know is ignored.

## The start markers

`/var/lib/tierstore` (`MARKER_DIR`) is the template's `StateDirectory`: it holds the markers `run-a` and `run-b` (and `run-fs-a` and `run-fs-b` of the second unit), and the hand-over socket. The hook makes it with mode 0700 when it is absent, writes a marker as a regular file and never follows a link. A marker that is a directory or a link is an error (`state_io`).

## The hand-over socket

A hand-over needs a control socket, a Unix socket in a directory the service owns. A node's configuration need not name it: without the `handoff_socket` key in the `[server]` table, the socket is `handoff.sock` in the unit's state directory, `/var/lib/tierstore/handoff.sock` (the process finds the directory in `STATE_DIRECTORY`, which systemd sets for the template's `StateDirectory=tierstore`; a process started without it, as on a Mac, makes no control socket). A key that names another path wins. The new instance connects to the socket, takes the listening sockets and then binds the path itself. A hand-over also needs both releases to list the capability `handoff-socket-v1` in `tierstore --capabilities`. For a configuration with a top-level `[local_cache]` table (a build node, or a storage node with a cache), both releases must also list `handoff-cache-v1`. For a configuration that leaves `handoff_socket` out, both must also list `handoff-state-dir-v1`: a running release without it would have no control socket to take from. When any of these is missing, the update is a restart, which `prepare` records as the mode. An empty or non-string `handoff_socket` is refused with `handoff_not_configured`, whatever the shape, unless the params force a restart or the hot tier is a directory.

This binary has the hand-over socket and lists `handoff-socket-v1`: the new instance takes the sockets of the running one over `server.handoff_socket`, waiting at most `server.handoff_wait` (10s) for it to hand them over (see [Live update by hand-off of the sockets](operations.md#live-update-by-hand-off-of-the-sockets)). An update from a release that does not list it is still a restart. A build node and a storage node with `[local_cache]` hand over too, and this binary lists `handoff-cache-v1` for it. The update to this release from v0.3.47 or an earlier one, of a node with `[local_cache]`, is a restart, and its params must say `mode = "restart"`: that release refuses the key in that shape, so the configuration cannot have it yet, and its instance has no control socket. Later updates of such a node hand over, once the key is in the configuration (see [The order of releases](update-hook.md#the-order-of-releases)).

`mode = "restart"` in the manifest's params forces a restart. A storage node whose hot tier is a directory (`[hot_store]` `kind = "dir"`) is a restart whatever the params say: the lease's compare-and-swap there is atomic within one process only, so two instances must never run side by side. `prepare` reads `kind` of `[hot_store]` from the configuration the hook is given in `config_file`; a first install, which hands nothing over, reads nothing.

### The order of releases

A release that refuses `server.handoff_socket` on a build node or a storage node with `[local_cache]` (v0.3.47 and earlier) exits 2 at start when the key is there, and the unit's `RestartPreventExitStatus=2 3` then keeps it from being started again. So the key goes in by this order:

1. The first release that accepts the key on every shape of node (it lists `handoff-cache-v1`) goes in with `mode = "restart"` in the manifest's params. A restart needs no `handoff_socket` key, and the configuration still has none.
2. Only when that release is live is `server.handoff_socket` added to the node's configuration. While the live release still refuses the key, `prepare` of any update refuses the edited configuration with `config_refused`, naming the previous release, before anything is stopped.
3. The next release, whose manifest has no `mode = "restart"`, is the first hand-over: both releases list the capabilities, and the configuration has the key.

## The reasons

`reason` is a token of lowercase letters, digits and `_`. The class decides whether the fleet rolls back: `release` blames the new version, `environment` the host or the hook's inputs.

| Reason | Class | Meaning |
| --- | --- | --- |
| `bad_args` | environment | the command line was refused, or the artifact is not the staged release |
| `bad_params` | environment | the params file is unreadable or wrong, or names another update than the record's |
| `locked` | environment | another step holds the lock of the state directory |
| `state_invalid` | environment | the record is not as the hook requires |
| `out_of_order` | release | the step does not follow from the record: `cutover` before `prepare`, a `prepare` past `cutover`, and so on |
| `not_verified` | release | `cleanup` before a `verify` succeeded |
| `committed` | release | `rollback` after `cleanup` began |
| `not_confirmed` | release | `cleanup` could not confirm, freshly, that the new release serves; nothing was committed |
| `host_not_ready` | environment | both instances run (of either unit); try again later (75) |
| `draining` | environment | in `cutover` or `rollback`, an instance that gave its sockets (or, for `tierstore-fs`, the mount) away is still draining, or, in `cutover`, the new store is still read-only after the step waited for it to take the cache lock, and the fs instance would find the cache not answering (75); `cleanup` does not use it |
| `not_ready` | release | `/readyz` on 9300 was not answered with 200, or the new instance is not running, or the new `tierstore-fs` instance did not take the mount (its unit is not active), or, in `verify`, the process of the new `tierstore-fs` instance does not run the binary the update installed (or systemd names no process of it), or, on a Mac, the mount is still listed after the fs job was booted out |
| `probe_failed` | release | 9300 was never answered by the release with the target version |
| `wrong_build` | release | the build gauge on 9300 is not the target version |

| `config_missing` | environment | there is no file at `config_file`, or, on a Mac that names the fs job, none at `/usr/local/tierstore/etc/fs.toml` |
| `config_refused` | environment | the staged or the previous release refuses the configuration at `config_file` when it checks it (`--check-config` exits 2); the detail names the release and the line. | `service_manager_unknown` | release | `service_manager` names a manager the hook does not drive |
| `no_previous_release` | release | `rollback` of a first install: there is nothing to go back to; the instance `cutover` started is stopped |
| `unit_failed` | environment | a unit or the launchd job could not be started, stopped or asked |
| `state_io` | environment | the record or a start marker could not be read or written |
| `host_failed` | environment | the host could not be asked: in `verify`, the `/proc/<pid>/exe` of the new `tierstore-fs` instance's process (gone, or not to be looked at) or the installed binary; the configuration, or `--capabilities` or `--check-config` of a release (no binary at `bin/tierstore` or `tree/usr/libexec/tierstore/tierstore`, cannot be run, exits any status but its answer, or does not end), or a root hook cannot find the service account its check runs as (`tierstore` in `/etc/passwd` on systemd, `_tierstore` in the directory service on launchd); or the binary of an archive release cannot be copied to, or removed from, `/usr/local/libexec/tierstore/tierstore` (a binary that is a link, not root's, or writable by a group or others; a directory on the way that is a link, not root's, or writable by others, or by its group for the copy's own directory; or a write that fails) |
| `provider_refused` | release | `verify`: on a node with a mount provider, the provider refused a call of the mount check (any status but `UNAVAILABLE`) for one of the check's two trees, which are of the forms the build service writes, with an L2 sidecar and without one: the node's jobs would be refused the same way; the detail has the call, the tree, the status and the provider's reason |
| `mounted_tree_wrong` | release | `verify`: a tree of the mount check read back wrong through the mount (a path missing, of another kind or not in the tree, a file of other bytes, a link to another target, a read that fails), a `Mount` answered a directory outside the provider's mount, or a placement outlived its release |
| `mode_unsupported` | environment | `prepare`: the node's file has an `fs` interface (the node holds a mount) and the update cannot hand the mount over: on Linux the two releases do not both list `handoff-service-v1`, on a Mac they do not both list `handoff-exec-v1`, or a config update moves the mount point, the control socket or the runtime directory of the interface. A restart would drop the mount under running jobs; nothing is recorded or stopped. `mode = "restart"` in the params overrides it, for an operator who has drained the node's jobs |

## The config hook

`tierstore config-hook` is the hook of a **config package**: a package of one host group that replaces only the node's configuration files (`/etc/tierstore/config.toml` and the network guard's file beside it on Linux, `/usr/local/tierstore/etc/tierstore.toml` on a Mac) and carries no binary. hostkeeper runs it as it runs this hook: the same command line (`tierstore config-hook <step> [<staged release>] --params <file>`), the same params file, exit statuses, last line and reasons. Its steps are `prepare`, `cutover`, `verify`, `rollback`, `cleanup` and `uninstall`; it has no boot step, and `restore` is refused (`bad_args`).

The params may leave out `config_file` and `service_manager`: on Linux the file is `/etc/tierstore/config.toml` and the manager systemd; on a Mac the file is `/usr/local/tierstore/etc/tierstore.toml` and the manager launchd, with the job `tierstore`. What the params name is kept.

The release does not change, so the version every step looks for in the build gauge is the build of the binary that runs the hook: run it as the service's installed binary (`/usr/libexec/tierstore/tierstore config-hook` with the Debian or RPM package, `/usr/local/libexec/tierstore/tierstore config-hook` with the archive package), and every check of a configuration is that binary's `--check-config`. hostkeeper runs a hook program that the package itself installs, so a config package ships a one-line wrapper as its `hook.command` that runs the installed binary with its own arguments (`exec /usr/libexec/tierstore/tierstore config-hook "$@"`). The steps move the same instances as an update of the release, except that a node's fs process of the old layout is left alone (it keeps running the release it runs, with no hand-over, whatever the capabilities say: the fs process's own file, `/etc/tierstore/fs.toml`, is not in this package, so a configuration update of the store has nothing to hand over to it). `prepare` records the instance that runs as `fs_live` with no `fs_next`, `cleanup` writes that letter into the release's record, and no step starts or stops an fs unit, unless the package is the switch of the node to one process, which moves the mount from that process to the new instance of the store (below), and unless the change is applied in place (below):

- `prepare` refuses (`out_of_order`) while an update of the release is in flight. It has the binary check the file the package staged, `<staged release>/tree/<config file>`, before it is installed (`config_missing` when the package stages none, `config_refused` with the binary's line when it refuses it). The staged package is closed to every user but root, so the hook reads the staged file and hands its text to the check: on Linux in a file in memory that the check inherits and reads at `/proc/self/fd/<n>` (standard input would not do: the account may not reopen a pipe that root made), on a Mac on its standard input (`--config /dev/stdin`). The file that `verify` checks, the installed one, is named by its path. It chooses a hand-over when the file that serves and the staged one have the same `[[interface]]` tables (the `fs` interface apart: its params do not count, so a hand-over keeps the mount when only they change), the same listening keys of `[server]` and the same `server.handoff_socket`, and neither has a hot tier of kind `dir`; otherwise, or with `mode = "restart"`, a restart. It refuses with `mode_unsupported`, and records nothing, a staged file with an `fs` interface that would drop or move a mount: when the file that serves has an `fs` interface too and the staged one names another `mountpoint`, `control_socket` or `runtime_dir` (the process that takes the mount would answer `nak`), and when the change must be a restart while the node holds a mount (the file that serves has an `fs` interface, or the switch below applies). `mode = "restart"` overrides it, for an operator who has drained the node's jobs. Nothing is started. On systemd, a change the instance that serves can apply is recorded as one applied in place instead of a hand-over or a restart (below).
- `cutover` reloads the network guard first (`systemctl reload-or-restart tierstore-guard.service`, only on a node that has the guard's file), then starts the other instance on the new file, by the hand-over or the restart of an update. On a Mac it boots the job out and bootstraps it. For the switch, see below.
- `verify` has the binary check the installed file (`config_refused`), then observes `/readyz` and the build, as for an update. For the switch of a Mac it also requires the mount listed at the mount point of the installed file.
- Every check of a file runs, when the hook is root, as the account the service runs as, because the check refuses key files that the user it runs as does not own. On Linux (systemd) that is `tierstore`, found in `/etc/passwd`, as for an update. On a Mac (launchd) it is `_tierstore`, the job's `UserName`, which the package's postinstall makes in the directory service and not in `/etc/passwd`. The hook reads its ids, `UniqueID` and `PrimaryGroupID`, from the user record `_tierstore` of the local directory with `/usr/bin/dscl . -read`. An account that is not there, or a `dscl` that fails or prints no numeric ids, fails the step with `host_failed`, and the detail names the account and the `dscl` call. On Linux the check is started under the account's user and group ids; on a Mac it is started as `/usr/bin/sudo -n -u #<UniqueID> -- <binary> --config <file> --check-config`, so that it has the account's groups, as the job has them from launchd (started under the ids alone, it would have the effective group 0 on macOS and could not enter `/usr/local/tierstore/etc`, root:`_tierstore` mode 0750). `sudo` needs only the stock rule that lets root run anything as any user; a `sudo` that refuses exits 1, which fails the step with `host_failed` and is never taken for a refusal of the file. A hook that is not root runs the check as itself.
- `rollback` comes after hostkeeper has put the previous package's files back: it reloads the guard and hands back to the instance that served (for the switch, the mount goes back first: below). A node's first config package has no files to go back to (hostkeeper takes the package and its files off the node): the rollback leaves the instance that runs serving on what it read, records nothing in flight, and fails with `no_previous_release`; the node needs a configuration before its next start.
- `cleanup` commits and finishes the update without waiting for the old instance to drain, as for an update, and writes the instance that now serves, and the fs instance the config hook's record names (none after a switch), into the release's record (`state.json`), which `restore` reads at boot.
- `uninstall` changes nothing: the service keeps the configuration it read.

### The switch to one process

A config package whose staged file has an `fs` interface, on a node whose file that serves has none and whose `tierstore-fs` process of the old layout runs, moves the mount to the one process of the new file (`docs/design/one-service.md` sections 4.2 and 4.3). Where no fs process runs (or, on a Mac, the `tierstore-fs` job is not loaded), the package is an ordinary config update.

- **Linux.** `prepare` records the switch with the optional record key `fs_switch` (written only when set, so every other record is unchanged) and keeps `fs_live` naming the fs instance that runs, with no `fs_next`. `cutover` starts `tierstore@<next>` on the new file exactly as for a hand-over of the store: the new process takes the sockets from the old store and the mount from the old fs process itself. Only after the new instance serves does the hook remove both `run-fs-*` markers, so that the old fs unit never starts again; it never stops or starts an fs unit (the old fs process ends by itself once it has handed the mount over). `verify` is the arm's: `/readyz` and the build of the new instance; the mount is not listed, as the mount list of this hook reads the format of macOS. `cleanup` commits, and the records name no fs instance from then on. A staged file that must restart is refused, as above, unless the params say `mode = "restart"`.
- **Linux, rollback.** The mount goes back first, then the sockets: the hook lays `run-fs-<y>` and starts `tierstore-fs@<y>` (the fs instance the record names, on the old `/etc/tierstore/fs.toml`), which takes the mount from the one process, and requires its unit active (a start that fails removes the marker again and fails the step); then `tierstore@<live>` is started on the old file and takes the sockets, as for any rollback. If `y` still runs (the new process never took the mount), only the store is handed back; one that is still ending makes the step wait (`draining`).
- **macOS.** The switch is a restart, as every update of a Mac that unmounts: the Mac is drained by the operator, and the arm is run with a declared restart. `prepare` records `fs_switch`. `cutover` boots the `tierstore-fs` job out (as `cutover` of an update does, with the same bounds), checks that its mount, the one `/usr/local/tierstore/etc/fs.toml` names, is gone (a mount that stays boots the fs job in again and ends the step with `not_ready`, nothing else stopped and the job not disabled), disables the job (`launchctl disable system/tierstore-fs`, kept across reboots, so the plist that the installed package still has never starts it again), then boots the main job out and in on the new file, which mounts and serves. `rollback` enables the job first, then runs the old restart: fs job out (not loaded: nothing), main job out and in on the old file, fs job in.

### A change applied in place

On systemd, a config package whose staged file differs from the file that serves in nothing but `tree_list_ram_bytes` of the `fs` interface (`fs.tree_list_ram_bytes`), or in nothing at all, starts no other instance: the instance that serves applies it, keeps its mapped tree lists, and does not scan its cache again. The two files are compared as TOML tables with that param taken out (a file that names none has the default, 512 MiB, and a params table left with nothing else is as none), so a byte-identical file, or one that differs only in comments, spacing or the order of its keys, is the case with nothing to set. The guard is reloaded only when the package's guard file differs from the installed one. Nothing moves, so the refusals of `prepare` above (of a change that must restart a node that holds a mount, or moves its mount) do not apply: a node with a hot tier of kind `dir` takes such a package in place too. Any other difference, a file that is not TOML, a cap that is not a whole number of bytes, params that say `mode = "restart"` (an operator who asks for a restart gets one), a node where no instance or both run (or both instances of its fs process of the old layout), and a config record with an update of the other kind in flight, take the ways above, refusals included. A Mac restarts its job for every config package, as before.

- `prepare` records the update with the optional record key `reload` (written only when set) and no `next` or `mode`: whether the guard's file changes, and, when the cap changes, the value of the file that serves (`from`), of the staged one (`to`) and the control socket of the `fs` interface; `fs_live` names the fs instance of the old layout that runs, as above. Nothing is started. A `prepare` run again over the reload it recorded keeps it, even once hostkeeper has installed the staged file.
- `cutover` reloads the guard when its file changed, then sends `set tree_list_ram_bytes <to>` to the control socket of the instance that serves (`fs.control_socket`; see [operations](operations.md#the-virtual-build-file-system)), which answers with the id of its mount, and records `swapped` with that mount. A socket that cannot be reached, or does not take the value, fails the step with `host_failed`. Run again, it sets the same value again. No unit is started or stopped and no marker changes.
- `verify` has the binary check the installed file, requires the instance that serves active (`not_ready`), observes `/readyz` and the build as for an update (deferred, `not_ready`, while its cache is read-only), and reads the value back from the gauge `tierstore_fs_tree_list_ram_bytes` of that mount on `/metricz`; while the gauge shows another value (the mount tells the node's cache at once) the step is deferred (`not_ready`, after `verify_retry_secs`).
- `rollback`, before the commit, reloads the guard again when its file changed (not for a node's first config package), and sets `from` again, unless the instance that serves no longer runs, whose start reads the file hostkeeper put back. A node's first config package still fails with `no_previous_release`, its record at rest.
- `cleanup` confirms afresh that the instance that serves is active and answers with the build (`not_confirmed`), then records the commit and the update at rest in one write, with the same instance serving, and writes it into the release's record as above.

The config hook keeps its own record, `config-state.json`, beside `state.json` in `/var/lib/tierstore-hook` and under the same lock, so a config update never changes the release's `to`, `version` or promotion.

## First install

A `prepare` whose params have no previous release is a first install. The hook copies the binary to `/usr/local/libexec/tierstore/tierstore` (an archive release) and starts `tierstore@a` (or bootstraps the job) with a normal bind. If it fails and hostkeeper rolls back, the instance is stopped and the copy removed, the step exits 1 with `no_previous_release`, and no instance is left running. On a Mac, a first install that finds the job already loaded (a copy installed by hand, stopped or running) boots it out before it bootstraps the job, with the fs job and its mount first, as an update does; its rollback then stops that job too, so `no_previous_release` with the job stopped is what the host is.

## What the hook leaves to hostkeeper

hostkeeper's hookless Force starts every `run` unit of the package and waits for every one of them to be active. A standby instance is inactive by design (it has no marker), so a Force reports a failure while tierstore serves. hostkeeper's observer treats one active unit as the service being live. Nothing in the hook changes that: a Force is not a hook step.

## Limits

- Hand-over needs both releases to list `handoff-socket-v1` (and, for a configuration with a top-level `[local_cache]` table, `handoff-cache-v1`); the first update from a release that does not is a restart, and so is the first update to a release from one that does not list `handoff-state-dir-v1`, when the configuration leaves `handoff_socket` out.
- A host with a `dir:` hot tier always restarts; the hook reads the tier's kind from the configuration.
- On macOS an update that restarts the job has a gap in serving while it restarts, and, when the params name the fs job, the file tree's mount is absent while the fs job is out: a job that reads a tree through it in that gap fails to find the mount, and none hangs on it. The hand-over to the next image has a pause instead: nothing is accepted from the drain to the start of the new image, the clients wait in the sockets' backlogs, and the mount of a node whose file has an `fs` interface stays.
- The fs process is handed over only between releases that both list `handoff-fs-v1`, and only on a node where an instance of `tierstore-fs@.service` runs or the record names one; otherwise it stays on its release, and the update of the first unit goes on without it.
- An update does not stop the `tierstore-fs` instance that holds the mount. A hand-over that fails leaves the old instance serving; there is no step that moves the mount away from the only instance.
