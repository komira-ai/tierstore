# The update hook

`tierstore update-hook` is the part of the binary that hostkeeper runs, as root, to put a new release of tierstore in place. hostkeeper owns the release directories and the link `current` that names the release in use; the hook owns the service: which instance runs, and the proof that the new release serves. This page is for the person who writes the package manifest for tierstore or reads what a step said.

On Linux (systemd) an update is a hand-over without a gap when both releases can do it, and a restart with a gap when they cannot. A node whose file has an `fs` interface hands its mount over with its sockets and its cache lock in one conversation when both releases list `handoff-service-v1` (see [the one hand-over](operations.md#the-fs-interface-the-mount-in-the-nodes-own-process)): the new instance serves the mount from the old one's `bye` and is the cache's writer once the old one's cache writes in flight have ended, while the old one still drains. On macOS (launchd) an update is a hand-over to the next image of the job's process (`SIGUSR2`, see [drain and restart](operations.md#drain-and-restart)) when both releases list `handoff-exec-v1`, and a restart with a gap otherwise; a node that holds a mount refuses the restart (`mode_unsupported`) unless the params say `mode = "restart"`. (`tierstore fs` on a Mac can hand its NFS socket over, see section 0 of `docs/design/tierstore-handover.md` in the repository; the hook does not use that. A release's params name no fs job, so an update of a Mac that serves its mount from its one process is that hand-over, and a Mac of the two-process layout is refused, see [on a Mac](update-hook.md#on-a-mac).) Both arms are in every build; the params file chooses between them.

## The command line

```text
tierstore update-hook prepare <staged release> --params <file>
tierstore update-hook <cutover|verify|rollback|cleanup|uninstall|restore> --params <file>
```

hostkeeper runs one step per process. `prepare` is given the staged release directory twice, as the argument and as `updater.staged_release` in the params file; the two must agree, or the step is refused (`bad_args`). The verb is answered before the server's flags are parsed, and no value comes from the environment.

A step reports in two ways:

- the exit status: `0` success, `1` failure, `75` deferred (not now: hostkeeper runs the step again after `retry_after_secs`, except a deferred `prepare` or `cutover`, which it rolls back and orders the update again later);
- the last line of standard output, one JSON object: `class` (`release` or `environment`: whom a failure is blamed on), `reversible` (whether the hook can still undo what it did; `false` is the commit), `promotion_pending`, and when set `reason` (a token from [the reasons](update-hook.md#the-reasons)), `retry_after_secs` and `detail` (a sentence for the log).

The steps are `prepare`, `cutover`, `verify`, `rollback`, `cleanup`, `uninstall` and `restore`. `restore` is the boot step.

## What hostkeeper does and what the hook does

hostkeeper switches the link `current` to the new release before `cutover`, and back to the previous release before `rollback`; it relinks the units the package ships (`units/`) with it. The hook never moves `current`. hostkeeper keeps every package directory closed to every user but root, and the service runs as its own account, so the units of hostkeeper's archive package do not run the binary inside the package: they run `/usr/local/libexec/tierstore/tierstore`, a copy that the hook, as root, makes of the binary of the release the link names before it starts the service. `cutover` copies the staged release's `bin/tierstore` there, `rollback` the previous release's, and the boot step `restore` the current release's (the release its params name), so starting an instance after the switch starts the release the link names: that is how `cutover` runs the new release and `rollback` the old.

The copy is owned by root, mode 0755, in directories that the hook makes when they are absent (mode 0755) and that must be root's, not links, and not writable by others, from `/usr` down to `/usr/local/libexec/tierstore`, which its group may not write either (a group-writable `/usr/local`, root:staff mode 2775, is accepted); a directory that is not is refused (`host_failed`), and so is a release binary that is a link, not root's, or writable by a group or others. Only a release of the archive package (anything at `bin/tierstore` or `bin`) is copied: a release of a native package (the Debian or RPM package, or the macOS installer package, whose job runs its own installed binary) is left to its package manager, and a host that has no copy is not looked at by `uninstall`. The hook writes the copy to a temporary file beside it and renames it over the old one, so an instance that runs the old copy (the live instance of a hand-over) keeps running it until it exits. A first install's `rollback` and `uninstall` remove the copy.

With the Debian or RPM package the units run `/usr/libexec/tierstore/tierstore`, and the hook copies nothing: the package manager replaces that binary at hostkeeper's `activate`, before `cutover`, so `cutover` starts the new binary; hostkeeper re-installs the previous package before the hook's `rollback` starts the old instance. The hook finds such a release's binary, for `prepare`, at `<release>/tree/usr/libexec/tierstore/tierstore`. The manifest of the apt entry names the hook command `/usr/libexec/tierstore/tierstore update-hook`.

With the macOS installer package the plist runs `/Library/Application Support/tierstore/bin/tierstore`, and the hook copies nothing either: `installer` replaces that binary at hostkeeper's `activate`, before `cutover`, and hostkeeper's rollback is the `activate` of the kept previous package, before the hook's `rollback`. hostkeeper expands the package's payload into the version directory's `tree/`, so the hook finds a Mac release's binary at `<release>/tree/Library/Application Support/tierstore/bin/tierstore`. That version directory is root's alone (mode 0700), so the service account cannot execute the binary inside it: a root hook that has `_tierstore` check the node's file with a release of this package runs a copy of its binary at `/usr/local/libexec/tierstore/tierstore-check`, made as the copy above is and removed once the check has answered.

The hook keeps one record of where an update stands, reads it at the start of every step and writes it as the step's acts happen, so a step that was killed is run again and ends where it would have. A step sets state rather than does things once.

## The params file

hostkeeper writes one TOML table of scalars for each run. A dotted key is quoted. A key the hook does not know is ignored.

| Key | Meaning |
| --- | --- |
| `"updater.staged_release"` | required: the unpacked version directory of the release being installed |
| `"updater.target_version"` | required: the version its binary must report, such as `0.5.0+0123456789ab` |
| `"updater.previous_release"` and `"updater.previous_version"` | both or neither: the release the host ran before. Neither means a first install |
| `"updater.promotion_ceiling_secs"` | read and not acted on: hostkeeper applies the ceiling itself |
| `service_manager` | `"systemd"` (the default when the key is absent) or `"launchd"`; any other value is refused by every step, `prepare` included (`service_manager_unknown`) |
| `launchd_label` | required with `service_manager = "launchd"`: the label of the one job |
| `fs_launchd_label` | optional, read only with `service_manager = "launchd"` (with systemd it is ignored, like any other key the hook does not read): the label of the launchd job of `tierstore fs`, which the hook boots out before the main job and in after it. No release manifest names it: no release since 0.3.196 runs that process, and the macOS package ships no plist for it. It is read for the config hook's switch to one process, whose rollback names it to go back to the two-process layout; a params file that names it is driven as described in [on a Mac](update-hook.md#on-a-mac), except that an update of the release (every step, the boot step included) leaves the fs job alone on a node whose file has an `fs` interface |
| `config_file` | the path of the node's configuration file; `prepare` reads it |
| `mode` | `"restart"` is the only value: the update is a restart even when both releases could hand over (see [the hand-over socket](update-hook.md#the-hand-over-socket)), and a node that holds a mount is not refused the restart (`mode_unsupported`) |

The boot step and `uninstall` carry the manifest's keys, the current release as `updater.staged_release` and `updater.target_version`, and no previous release. Every step after `prepare` refuses params whose staged release or target version differ from the update the record holds (`bad_params`), but for a `rollback` that finds the record at rest, which has nothing to roll back (see `rollback`), and a `rollback` that finds another update whose updater is gone, which it rolls back first (see [an update whose updater is gone](update-hook.md#an-update-whose-updater-is-gone)).

A version is read back from the build gauge `tierstore_build_info{version="0.5.0",commit="0123456789ab"}` of `/metricz`; it matches a target version that is the version alone or the version, `+` and the commit.

## The shape of an update

### On Linux

The package ships one unit template, `tierstore@.service`, and the hook alternates between its two instances, `tierstore@a` and `tierstore@b`. Both run the binary (`/usr/local/libexec/tierstore/tierstore`, the hook's copy, with the archive package; `/usr/libexec/tierstore/tierstore` with the Debian or RPM package) and serve the public port 9300. Clients keep calling 9300; there is no redirect and no second port.

An instance starts only when its start marker exists: the template has `ConditionPathExists=/var/lib/tierstore/run-%i`, so `/var/lib/tierstore/run-a` starts `tierstore@a` and `/var/lib/tierstore/run-b` starts `tierstore@b`. A start that finds its marker missing is skipped, not failed: the unit stays inactive. With the archive package both instances are enabled at boot; with the Debian or RPM package nothing enables them, and hostkeeper starts the run units at its own start and the boot step `restore` starts the recorded instance. Either way only the one with a marker runs.

The record names `live`, the instance that serves at rest, and, during an update, `next`, the other one. In `cutover` the hook sets the marker of `next` and starts it.

- **Hand-over.** `next` asks `live` for its listening sockets over the hand-over socket and takes them: no connection the kernel holds is reset. `live` then drains and exits with status 0, which the template does not restart (`Restart=on-failure`). No step waits for the drain (see [an old instance that drains](update-hook.md#an-old-instance-that-drains)).
- **Restart.** The hook stops `live` first (the stop waits for its drain), then starts `next`: new connections are refused in between.
- **First install.** No instance serves, so `next` (`a`) starts and binds the port normally.

The next update starts the other letter: a, b, a, and so on. A cache node serves read-only while another instance holds the cache lock, and takes the lock, and becomes read-write, by itself once the old instance has exited; the hook only watches for it (`verify` defers while the cache is read-only, see [verify](update-hook.md#verify)).

### On a Mac

One job, whose label is `launchd_label`, loaded from the plist `/Library/LaunchDaemons/tierstore.plist` (hostkeeper links it from the archive package's `units/`), which runs `/usr/local/libexec/tierstore/tierstore` as `_tierstore`: the hook's copy, as on Linux. (The macOS installer package's plist runs its own binary, `/Library/Application Support/tierstore/bin/tierstore`, which hostkeeper's `activate` has replaced before `cutover`, and the hook copies nothing for it: the `SIGUSR2` of a hand-over makes the process execute that path again.) An update is one of two ways, decided in `prepare`, `cutover` and `rollback` alike from the same inputs (the record holds no mode). It is a **hand-over** when it has a previous release, the params name no fs job (`fs_launchd_label`; no release manifest does), `mode` is not `"restart"`, and both releases list `handoff-exec-v1` (the hook asks the staged and then the previous release). `cutover` of a hand-over, with the job loaded and not yet serving the target, copies the staged release's binary there, sends the job's process `SIGUSR2` (`launchctl kill SIGUSR2 system/<label>`), and waits for the build gauge on 9300 to name the target: the process drains, keeps its sockets and its mount, and executes the new binary under the same pid, so launchd sees no exit, and nothing is unmounted. A job that is not loaded is started by bootstrap, as in a restart. Every other update is a **restart** with a gap: `cutover` copies the staged release's binary there, boots the job out, then bootstraps the plist, which starts the release `current` now names. A restart unmounts a mount the process holds, so `prepare` refuses it, with `mode_unsupported`, for a node whose file has an `fs` interface and whose params name no fs job, unless the params say `mode = "restart"` (for a node whose jobs are drained); the detail names `handoff-exec-v1` and the releases that lack it. A first install, `restore` and `uninstall` boot the job in or out as before. The hook waits up to 240 seconds for `launchctl bootout` of the job: it returns when the process has exited, which launchd forces at the plist's `ExitTimeOut` of 210 seconds. A first install bootstraps the job, and boots nothing out when the job is not loaded; when it is loaded and does not serve the target (a copy installed by hand that the first install takes over), it is booted out first, as in an update, with the fs job before it. The record has no `live`, `next` or `mode`, and `prepare` does not ask for a hand-over socket. `prepare` checks that the `config_file` param is there and names a file; it asks the releases for their capabilities only when the params leave the way open (see above), and runs a release to check the file only for a hand-over: the staged release's `--check-config` of the file, which fails the step with `config_refused` (the new image would exit on a file it refuses, and launchd would start it again). A restart checks nothing, so a configuration that the live or the staged release refuses is found when the job starts. A Mac has no `handoff_socket` key to hand sockets over by: the hand-over is the exec, and a configuration with `[server] handoff_socket` and `[local_cache]` is no different. The hook touches the one label and, when `fs_launchd_label` is given and the node's file has no `fs` interface (or the config hook drives the arm), that one.

A node's file decides what an update does to the mount (design: [updates of a Mac's release after the switch](https://github.com/komira-ai/tierstore/blob/main/docs/design/one-service.md#45-updates-of-a-macs-release-after-the-switch)):

- **The two-process layout is refused in prepare.** A release (an update or a first install) on launchd whose node file (`config_file`) has a `mount-provider` interface and no `fs` interface is refused with `mode_unsupported`, and the detail: "<config> has a mount-provider interface and no fs interface: the two-process layout, whose mount tierstore fs served as a job of its own. No release since 0.3.196 runs that process, so after this update nothing would serve the provider's mount. Switch the node to one process first (an [[interface]] with type = "fs" in its file, through its config package); nothing was stopped". Nothing is recorded, started or stopped. hostkeeper then runs `rollback`, which finds nothing in flight, and re-activates the previous package, so the Mac stays on its release. The config hook is not refused: its switch is the way off the layout.
- **A switched Mac is updated by the hand-over.** With a file that has an `fs` interface and params that name no fs job, an update between releases that both list `handoff-exec-v1` (every release since 0.3.177 on macOS) is the hand-over above: the hook copies the staged binary and sends `SIGUSR2`; the process keeps its pid and its mount, ends its NFS connections as a hand-over does (every request it has read is answered, and it waits for the clients to close theirs), and executes the new image, which serves on the same NFS listening socket and control socket. The reads of the jobs on the Mac of the mount pause for the drain and the exec (the mount is `hard`, so the clients retry) and then go on; nothing is unmounted and the files they hold stay open.
- **Verify proves the volume.** Before the commit, for a release on launchd whose file has an `fs` interface, `verify` requires the mount listed (`/sbin/mount`, at the interface's mount point, which is also the mount provider's root) and a look-up of `<mount point>/trees` that finds a directory (the namespace every mount of tierstore's file system has at its root; a plain directory that is not mounted lacks it, and the server must answer). Otherwise it fails with `not_ready`, and the detail says which: "<mount point> is not mounted: ...", "<mount point> is mounted and <mount point>/trees is not a directory: the mount is not tierstore's file system", or "<mount point> is mounted and a look-up in it failed (<error>): its server does not answer". hostkeeper then rolls back, which for a hand-over is the hand-over to the previous release. On a hard mount whose server is gone the look-up waits until the kernel marks the mount dead (`fs.nfs.dead_timeout`) and then fails. A file without an `fs` interface has nothing to prove. After the commit `verify` only observes the version, as before.

The fs job, when the params name it (no release manifest does; a config package's rollback does), is the job of `tierstore fs`: the plist `/Library/LaunchDaemons/tierstore-fs.plist` (an earlier macOS installer package put it there; the hook loads it and never writes it) and the configuration `/usr/local/tierstore/etc/fs.toml`, whose `[fs] mountpoint` is the mount point (`/run/tierstore/fs` when the key is left out). The fs process serves a NFS mount that jobs read their trees through, and a mount whose server is gone blocks whatever touches it, so an update never leaves the mount in place beside a stopped fs process:

- Every boot-out of the main job (`cutover` of an update or of a first install over a loaded job, `rollback`, `uninstall`) is preceded by the boot-out of the fs job, when it is loaded. The hook waits for the job to be gone for up to 180 seconds (`launchctl bootout` returns when the process has exited, and launchd kills it at the plist's `ExitTimeOut` of 150 seconds) and then looks at most 30 times, a second apart, for the domain to let it go.
- It then runs `/sbin/mount` and looks for a line with ` on <mount point> (` (the mount point as written and as it resolves, since `mount` prints the resolved path). A mount that is gone lets the step go on with the main job. A mount that is still listed ends the step with `not_ready` and a detail that names the mount point: nothing else is stopped, the main job is left as it is (running, when it ran), and the fs job is booted in again, which takes the mount over. A list that cannot be had is `host_failed`, with the fs job booted in again.
- The mount point comes from `/usr/local/tierstore/etc/fs.toml` before anything is stopped: a file that is not there is `config_missing`, one that is not TOML or whose `fs.mountpoint` is not an absolute path is `config_refused`, and the detail says that nothing was stopped. The file is read only when the fs job is loaded. A first install looks at the fs job too, before it starts the main job: an fs job a copy installed by hand left loaded is booted out, its mount checked, the same way.
- After the main job serves (`cutover`, `rollback`) or is loaded (`restore`), the fs job is booted in when it is not loaded. A first install loads it after the main job too; nothing else loads it. A run again after a crash does the same from whatever it finds.
- A config package drives the fs job only when its params carry `fs_launchd_label` (its manifest names it): then the arm's `cutover` and `rollback` stop it, check its mount and boot it in again exactly as for a release. With no `fs_launchd_label` the config hook leaves the fs job alone and restarts the main job only, except for the switch to one process (the config hook's section below), which boots the fs job out and disables it.

## The second unit, `tierstore-fs`

Earlier releases could run the file system as a second process, `tierstore fs`, under a unit of its own, `tierstore-fs@.service` (the instances `a` and `b`, started only under the marker `/var/lib/tierstore/run-fs-<instance>`), and the hook handed it over beside the store. This release has no step for that unit: the file system is the `fs` interface of the node's file, served by the one process of `tierstore@.service` (see [the virtual build file system](operations.md#the-virtual-build-file-system)). The hook only looks at the second unit, and `prepare` refuses a node that still runs it.

**What it looks at.** On systemd, `prepare` of an update or of a first install looks, before it records anything or asks a release, at the state of the two units `tierstore-fs@<instance>.service`, `a` and `b` (`systemctl show`: active, activating and deactivating count as running), at the markers `run-fs-a` and `run-fs-b`, and at the record at rest for `fs_live`. Any one of them is the refusal. It starts, stops, sets and clears none of them.

**The refusal.** `mode_unsupported`, reversible, with nothing recorded, started or stopped. The detail names each thing found, then says what to do:

```text
this node still runs the two-process layout (tierstore-fs@<instance>.service is active; the marker run-fs-b is present; the record names fs_live a): switch this node to the fs interface with release M first
```

The way out is the earlier release that switches the node to the `fs` interface (see [the switch to one process](update-hook.md#the-switch-to-one-process)); when both fs units are inactive or failed, both markers are gone and the record names no `fs_live`, the update goes on. A record at rest that says `fs_switch` and names no `fs_live` is not a refusal. The `prepare` and the `rollback` that find a record of an update in flight, written by an earlier release, that names `fs_next` or says `fs_switch` are refused in the same words (`the update in flight names fs_next b`, `the update in flight says fs_switch`) instead of rolling it back: the way back of that update goes through the fs process, which this release does not touch. Nothing is recorded or started.

**The record keys.** `fs_live`, `fs_next` and `fs_switch` are read and never written. The hook still decodes them and holds them to their rules, so that the record of a node that has not left the earlier layout is understood and a hook of an earlier release reads this release's record (the formats change only additively); `cleanup` saves a record at rest with no `fs_live` and no `fs_next`.

## The steps

### prepare

Nothing a client sees changes, and nothing is started.

- A record whose update is past `cutover` and not committed is refused (`out_of_order`): finish or roll back the update in flight first. A record of another update past its `cutover`, not committed, that returns the host to the release the params name as the previous one is rolled back first instead, and the update is prepared from the record at rest (see [an update whose updater is gone](update-hook.md#an-update-whose-updater-is-gone)), unless it names `fs_next` or says `fs_switch`: that is refused (see [the second unit](update-hook.md#the-second-unit-tierstore-fs)). A record at rest, committed or idle, starts a fresh update. A record whose update is committed (`stopping`) but still in flight, which a `cleanup` of an earlier release leaves when it gave up while the old instance drained, is finished first, as `cleanup` finishes it (the old instance's marker goes, the new one becomes `live`, and the record is saved at rest with no `fs_live` or `fs_next`), and the update is prepared from it; the detail begins with `finished the committed update to <version>`. That record is an earlier update's, so `prepare` reports `reversible` `true`, and a `rollback` of the new update finds nothing to roll back.
- systemd: a node that still runs the two-process layout is refused (`mode_unsupported`; see [the second unit](update-hook.md#the-second-unit-tierstore-fs)), after the committed update is finished and the past-its-cutover check, before anything is recorded or asked of a release.
- Both arms: the `config_file` param must be there (`bad_params`) and name a file that exists (`config_missing`).
- systemd, an update, no `mode = "restart"`: the hook reads the configuration. A `handoff_socket` key of the `[server]` table that is an empty string or not a string, and a configuration that is not TOML (with the parse message), are refused with `handoff_not_configured`. A key that is left out is not: the socket is then the default, `handoff.sock` in the unit's state directory (see "The hand-over socket"). A configuration whose hot tier is a directory (`[hot_store]` `kind = "dir"`) is a restart, and is not asked for a socket.
- systemd: the hook runs `<staged release>/bin/tierstore --capabilities`, or, when nothing is at that path, `<staged release>/tree/usr/libexec/tierstore/tierstore --capabilities` (a release of the Debian or RPM package); a staged release with neither (the refusal names both), or a binary that does not run, is `host_failed`, and for an update the previous release's too. The mode is a hand-over when `mode` is not `"restart"`, the hot tier is not a directory, and both list `handoff-socket-v1` (for a configuration with a top-level `[local_cache]` table, both also list `handoff-cache-v1`; for one that leaves `handoff_socket` out, both also list `handoff-state-dir-v1`), and a restart otherwise. A node whose file has an `fs` interface (it holds a mount) also needs `handoff-service-v1` in both lists: an update of it that would be a restart, because a word is missing or the hot tier is a directory, fails `prepare` with `mode_unsupported` before anything is recorded or started, and the detail names the releases that lack a word and says that a restart would drop the mount under running jobs. `mode = "restart"` in the params overrides it (for a node whose jobs are drained), and the update is then the restart as for any node. A first install is never refused, and a node with no `fs` interface is decided as above. A first install records no mode.
- launchd: the hook asks `<release>/bin/tierstore`, or, when nothing is at that path, `<release>/tree/Library/Application Support/tierstore/bin/tierstore` (a release of the macOS installer package), for the staged and then the previous release; a release with neither (the refusal names both) is `host_failed`, with nothing recorded or stopped. The staged release's check of the file before a hand-over runs, for a release of the installer package and a root hook, the copy at `/usr/local/libexec/tierstore/tierstore-check` (see [what hostkeeper does and what the hook does](update-hook.md#what-hostkeeper-does-and-what-the-hook-does)); a copy that cannot be made or removed is `host_failed`, naming it.
- systemd, an update or a first install, whenever the params name a `config_file` (with `mode = "restart"` too): before anything is recorded or stopped, the hook has the staged release and then, for an update, the previous release check the configuration, by running `<release>/bin/tierstore --config <config_file> --check-config` (or the package path above). Exit 0 is a configuration the release accepts. Exit 2 is one it refuses: `prepare` fails with `config_refused`, and the detail says whether the staged or the previous release refused, its path, and the refusal line it printed. Any other exit, a signal, a binary that cannot be started and a check that does not end within 10 seconds are `host_failed`. Nothing is recorded and no unit is touched in either case. A first install has no previous release, so only the staged one checks. `mode = "restart"` without a `config_file` checks nothing. When the hook runs as root, the check runs as the account `tierstore` (the template's `User=`, found in `/etc/passwd`; an account that is not there is `host_failed`), because the check refuses key files that the user it runs as does not own, and the unit does not run as root. A hook that is not root runs the check as itself. hostkeeper keeps every staged package closed to every user but root (a package may hold a secret), so the account cannot reach the staged binary by its path: on Linux the hook opens the binary itself, holds what it opened to the same checks as the path (a regular file, not a link, owned by root, not writable by a group or others), and the check, started under the account's user and group ids, executes that open file (`/proc/self/fd/<n>`), which needs no search of the directories above it; the account needs only the right to execute the file. The configuration file is still named by its path, so the check proves that the account can read it and every key file it names. A failure names the command (the binary by its path), the user it ran as with its ids, and the error. The check is the loader's only: what a start finds of the disk, the tiers or the heartbeat is not checked.
- systemd: it looks at the units, on every run, also when the record holds an update in flight that never reached `swapped` (a `cutover` that failed may have started its instance, which then took the sockets while the record still names the other one). Both running defers the step (75, `host_not_ready`, retry after 30 seconds). One running is `live`. None running is the record's `live` on an update, and no instance on a first install. `next` is the other one of `live`, or `a` when there is none.
- It saves the record: updating, from the previous release, to the staged release, the version, and on systemd `live`, `next` and the mode; no fs key.

### cutover

Needs an update in flight that has not committed (`out_of_order`) with params that match it. On a Mac whose params name the fs job, an update, or a first install that finds the fs job loaded, first boots the fs job out and checks that its mount is gone (see [on a Mac](update-hook.md#on-a-mac)), and boots it in once the main job serves; a mount that stays is `not_ready`, with nothing else stopped. Before it stops or starts anything else, it copies the staged release's binary to `/usr/local/libexec/tierstore/tierstore` (an archive release; nothing for a release of a native package); a copy that cannot be made fails the step with `host_failed`, with `live` still serving. As above, the mode decides how `next` starts. After the start the hook waits, up to 1000 looks a second apart, for a look at 9300 that `/readyz` answers and whose build gauge names the target version, and then for the gauge to name it three times in a row within 60 looks. In a hand-over the old instance answers `/readyz` until the new one has opened its local cache and taken the sockets, which on a slow disk takes minutes, so the wait is for the target version and not for any answer. `/readyz` never answered is `not_ready`; answered but never by the target version is `probe_failed`. The record gets `swapped` once the new instance serves. The step does not wait for the cache lock a new store takes after the old one has exited: it goes by the build, and `verify` defers while the cache is read-only. A failure is reported and nothing is undone: hostkeeper switches `current` back and runs `rollback`. A re-run after `swapped` looks again and, if the new instance serves the target, succeeds without starting anything.

### verify

An observation, and, before the commit on launchd for a node whose file has an `fs` interface, the proof of the volume (see [on a Mac](update-hook.md#on-a-mac)): the mount listed at the interface's mount point and a directory at `<mount point>/trees`, else `not_ready`, and hostkeeper rolls back. After the commit it looks at the service again (`observed`) and says whether the promotion is pending; a look that `/readyz` does not answer ready (the old instance may still drain after `cleanup` and answer 503 on the sockets the two share) defers with `not_ready` and `verify_retry_secs`, not reversible, as before the commit, and is not a failure. Before it, it needs `swapped` (`out_of_order`), the new instance (on launchd, the job) running (`not_ready`; `activating` defers), and the build gauge on 9300 naming the target version (`wrong_build`, exit 1). A new instance that answers `ready read-only` has not taken the cache's write role yet: until it has, the node's jobs cannot fill their trees through the mount or reach the mount provider, so `verify` defers with `not_ready` and `verify_retry_secs` and records nothing, and hostkeeper keeps the node in its update and ends the deferrals itself at `verify_deadline_secs`. Then, on a node whose file has a `mount-provider` interface, the mount check (below), after the proof of the volume on a Mac: the volume is listed and answers first, then a real tree is prepared, mounted and read. Otherwise it records `verified` and exits 0. After the commit a build node that still serves read-only says `promotion_pending: true`, and hostkeeper runs `verify` again until it does not, within its promotion ceiling.

**The mount check.** An instance that is active, answers `/readyz` and reports the target build may still refuse every job's tree. So on a build node, once the new instance is the cache's writer (it binds the provider's socket only then), `verify` drives the node's mount provider end to end, as jobscheduler's agent does for a job. It uses the socket the interface names and two small trees that the release carries for the purpose. Both are stored in a form the build service writes today. The first has its version 2 list at `cas/l/<id>` and its L2 sidecar at `cas/l2/<id>`, and the provider places it from the sidecar. The second has its list alone, and the provider places it from the list. Their files lie in one pack under `cas/check/`. A node with a mount provider answers the reads of exactly these objects itself, in front of its upstream: the check reads nothing from the network and writes nothing to the store. Its sources are those of the agent `tierstore-verify`, which no job's are, under the run `js.tierstore-verify`. The check never sweeps, so it is safe while jobs run. The steps are:

1. `Release` of both sources, so that nothing of a check that ended halfway remains.
2. `Prepare` of each source with its tree's list, read-only.
3. `Mount` of each. The answer must be a directory below the interface's `mountpoint`, with no `..` leading out of it.
4. A read of every path below each directory, without following a link, compared with the tree: every file's bytes, every directory, and the link's target, with nothing more. On Linux (systemd) the read is through the mount, as root. On a Mac (launchd) it is from the NFS front of the node's `fs` interface (`fs.nfs.listen`, `127.0.0.1:12049` when the file leaves it out), over loopback TCP, as the kernel's client of the mount asks it (MOUNT of the export `/`, a `LOOKUP` of each name of the directory's path under the mount, `READDIRPLUS`, `READ` and `READLINK`, NFS version 3 with the credential of root), and never through the mount: macOS refuses a process its privacy grant of network volumes (Full Disk Access) does not cover, root included, every read of the volume (`Operation not permitted`), and the process hostkeeper runs the hook in has no such grant. The front answers the same calls the kernel's client makes, from the same placements and the same cache, so the read proves what a job's read of the volume needs of the node; the kernel's client itself is proved by the volume's proof before the check (the mount listed and `<mount point>/trees` answering). A job on a Mac reads its tree through the volume from the processes of jobscheduler's agent, which hold that grant.
5. `Release` of both, then a `Mount` of each, which must be answered `UNAVAILABLE` with `the source is not prepared here`: the provider finds no placement at the source's path. A directory answered then is a placement that outlived its release. Any other answer is judged as at any call, below.

The calls have the bounds jobscheduler's agent gives them (`Prepare` 10 s, `Mount` 30 s, `Release` 5 s), and the read has 30 s (from the front, each of its calls and the whole read). A call that passes its bound is a provider that does not answer.

The outcomes are:

- **Failure** with `provider_refused`: any status but `UNAVAILABLE` at any call fails `verify`, before the commit and so reversible. The detail names the call, the tree and its key, and gives the status and the provider's reason as it said it (`the mount provider at /var/lib/tierstore/provider.sock refused Mount of the tree without an L2 sidecar (cas/l/<id>) with FailedPrecondition: no tree list at cas/l/<id>`).
- **Failure** with `mounted_tree_wrong`: a tree read back wrong (a path missing, of another kind, or not in the tree, a file of other bytes, or a link to another target), what is read being no tree of the check (more paths or a larger file than it has, a path of no kind of a tree, a name that is not UTF-8), a read that the system answers with an error (a stale handle, a permission, a path that is not there, an I/O error) or that the NFS front answers with a status other than `NFS3ERR_JUKEBOX` (or with no answer of its protocol, or a connection refused), a directory outside the mount, or a placement that outlives its release fails `verify` at once. The check's objects are the release's own, read from memory, so a read that is answered with an error is no slow fill and would be answered the same way again: it is not deferred. The detail names the tree, its directory, where it was read (`through the mount`, or `from the NFS front at <address>`) and the first difference, or the path and what the system or the front said (`the tree with its L2 sidecar at /private/var/tierstore/fs/mount-provider/<agent>/<run>/0 could not be read from the NFS front at 127.0.0.1:12049: mount-provider/<agent>/<run>/0 could not be looked up: the NFS front at 127.0.0.1:12049 answered NFS3ERR_NOENT (2)`). A file that differs is described by its size, never its bytes.
- **Deferral** with `provider_busy` (class `environment`): an answer `UNAVAILABLE` to any call defers `verify` with `verify_retry_secs`. That is how the provider answers when it has no room or no turn now, which is load and not the release. It answers a `Prepare` `UNAVAILABLE` (`the node holds <n> sources (trees.max_sources): release one, or retry`) when it holds `trees.max_sources` sources. It takes the `Prepare` and answers the `Mount` `UNAVAILABLE` when `trees.max_placements` placements are alive (`the tree was not made: too many placements: <n> are alive`), and when every one of the `trees.prepare_concurrency` turns is taken past the `Mount`'s wait (`not ready`). A read-ahead queue at its bound refuses nothing: the trees are placed without their reads queued and the check reads them as the mount opens them. A node whose file has a `mount-provider` interface and no `fs` interface has no file system that serves its trees, and its provider answers every `Prepare` `UNAVAILABLE` saying so.
- **Deferral** with `not_ready`: a provider that does not answer (its socket not bound yet, or a call past its bound), and a read that does not end within its 30 s (the mount fills a file as it is opened, slowly on a node under load) or that the NFS front answers `NFS3ERR_JUKEBOX` (a fill that has not ended), defer `verify` with `verify_retry_secs`.

hostkeeper runs `verify` again after each deferral and ends the deferrals itself at `verify_deadline_secs`, 2500 s after the cutover in the package's manifest. A node that stays full, or whose mount stays too slow, past that deadline fails the update, and hostkeeper rolls it back to the previous release, which has the same limits and keeps running the node's jobs. The operator then sees the host `failed` in its stage, with phase `gate_environment` and reason `provider_busy` for a provider that kept answering `UNAVAILABLE` (the detail names the limit), or `gate_release` and `not_ready` for one that never answered or a mount that never read back. An `environment` failure does not count toward the automatic rollback of a release. The check takes no room of its own outside the limits: it waits for the room a job would need.

Before a check that got as far as `Prepare` ends with a failure or a deferral, it asks for the release of both sources, each even when the other's release is not answered. A placement the provider cannot release then is released by the first step of the next check, or ends at `trees.ttl_max`. A node whose file has no `mount-provider` interface, or whose params name no `config_file`, has no check. An interface with no absolute `socket` or `mountpoint` is `config_refused`, and so, on a Mac, is an `fs.nfs.listen` that is not an address and a port, or names port 0. After the commit, `verify` does not run the check again.

### rollback

Runs with `current` already back at the previous release (and, for the Debian or RPM package, with the previous package re-installed). Before it starts anything, the hook copies the previous release's binary back to `/usr/local/libexec/tierstore/tierstore` (an archive release), so starting an instance starts the previous binary. Not updating: nothing to roll back, exit 0. A record at rest that names another update than the params (the params' update was never recorded: its `prepare` failed, or never ran) also has nothing to roll back: exit 0, reversible, and the detail names the params' update and the last one on record; the record and the units are left alone. After the commit of the update the params name: `committed`, exit 1. A record of an update in flight that names `fs_next` or says `fs_switch` (an earlier release wrote it) is refused with `mode_unsupported` and nothing is done (see [the second unit](update-hook.md#the-second-unit-tierstore-fs)). On launchd likewise. With the fs job named, the fs job is booted out first, with the same mount check (`not_ready` when the mount stays, the update left on record and the main job as it is), and booted in after the previous release serves.

- **First install.** The instance `cutover` started is stopped and its marker removed (on launchd the job is booted out, whatever runs under its label, and the fs job before it), the copy of the binary is removed, and the step fails with `no_previous_release`: there is nothing to go back to. The record keeps the update in flight with no markers, so a re-run says the same and a later `prepare` starts afresh.
- **Update, restart mode** (and launchd, for a restart): the new instance is stopped, the old one started, and the hook waits for the previous version to serve; the record is idle again.
- **Update, launchd hand-over:** the previous release's binary is put back at `/usr/local/libexec/tierstore/tierstore` and the job's process is sent `SIGUSR2` again, which executes it: the hook waits for the previous version to serve, and the record is idle again. A job that is not loaded is bootstrapped. There is no way back for a process that executed a new image: if that image cannot serve at all, it is this step that puts the old one in place.
- **Update, hand-over mode:** if the new instance runs it holds the sockets. If the old instance still runs (it is draining after it handed over), the step defers with `draining` (75, retry after 10 seconds). Otherwise the old instance is started, takes the sockets back from the new one, which exits, and the hook waits for the previous version to serve. If the new instance is not running, an old instance that still serves means `cutover` never took over, and an old instance that does not serve is a drain that will end; with none running the old one is started cold. A new instance that is still draining after the sockets went back defers the step again (`draining`); the run after it finishes.

### cleanup

The commit, and the end of the update. It needs a `verify` that succeeded (`not_verified`). Before the commit it confirms again, freshly, that the new instance runs and serves the target (`not_confirmed`; nothing is committed), then records `stopping`. From then on `reversible` is `false`: `rollback` is refused. On systemd the same run then finishes the update, whatever the old instances are doing: it removes the old instance's marker, records the new instance as `live` (no `fs_live`, no `fs_next`), with no update in flight, and exits 0. It never stops an old instance and does not wait for one: an old instance of a hand-over ends by itself, in a time that is not the hook's to know (see [an old instance that drains](update-hook.md#an-old-instance-that-drains)), and the detail names each one that still runs (`committed: tierstore@b serves; tierstore@a still drains and ends by itself`). A `cleanup` that ends between the commit and the end (a crash, a record that cannot be written) is run again by hostkeeper and finishes then. On launchd there is no instance to retire. A re-run after `cleanup` finished says there is nothing left to clean.

### uninstall

Stops both instances (the job, on launchd, after the fs job when the params name it and its mount is gone, `not_ready` when it stays), removes the markers and the copy of the binary at `/usr/local/libexec/tierstore/tierstore`, and records no instance. It leaves the data, the cache and the configuration (`/var/lib/tierstore` apart from the markers, `/etc/tierstore`; on a Mac, `/usr/local/tierstore`) and the record directory as they are.

### restore

The boot step. On a Mac it loads the job when it is not loaded, and then the fs job when the params name it and it is not loaded. It starts the instance the record names, and only it: the recorded `live`, or `next` when an update is in flight and `cutover` finished (`swapped`). Any other instance has its marker removed, and is stopped if it runs while the one the record names is not active; while that one is active, the other is the old instance of a hand-over that still drains (hostkeeper runs the boot step at every start of its own, not only after a reboot), and it is left to end by itself; the marker of the one that starts is set again if it was missing, which repairs a marker that disagrees with the record. Before the start the hook copies the binary of the release its params name (the current release) to `/usr/local/libexec/tierstore/tierstore`, so the instance runs the release `current` names whatever copy a step that died left there. A record whose update is committed and still in flight is then finished, as `cleanup` finishes it. No record, or no instance in it, is success with nothing copied or started. On launchd it copies the binary and bootstraps the plist when the job is not loaded, and does nothing when it is.

## An old instance that drains

After a hand-over the old instance ends by itself. It drains until its last request is answered, within its `--drain-deadline`. No step waits for it, and none stops it. `cleanup` finishes the update at once (see [cleanup](update-hook.md#cleanup)); the old instance has no marker from then on, so systemd never starts it again, and the record names only the new instance. Each later step reads the units themselves:

- `prepare` of the next update finds both instances running and defers (75, `host_not_ready`, retry after 30 seconds), having recorded no update (a committed record still in flight is finished first, see [prepare](update-hook.md#prepare)). hostkeeper then runs `rollback`, which has nothing to roll back, reports the update deferred, and orders it again later (its coordinator waits at least 300 seconds, doubling up to an hour, and at least the 30 the hook asked for), with no limit on the number of times: the host waits, and the update is not failed. Once the old instance has ended, the next `prepare` goes on from the new instances.
- `rollback` of the update that drains is refused once `cleanup` began (`committed`), as before; hostkeeper does not run it after a `cleanup` that succeeded.
- `restore`, after a reboot, starts only the new instance: the old one has no marker. At a start of hostkeeper with no reboot it finds the new instance active and the old one draining, stops nothing, and keeps only the new marker.
- `uninstall` stops every instance that runs, the old one too: it ends the service.

## An update whose updater is gone

A host that loses its network or its power during an update can be left with the record of that update in flight, not committed, and no updater to finish it: hostkeeper gave the update up, moved `current` back to the release it started from, and the `rollback` that would have put the record at rest never ran (or ran and was deferred, and was never run again). hostkeeper then orders the next update with that release as `updater.previous_release`: its params name another update than the record's. Before this rule every step of that order met the record. `prepare` refused it (`out_of_order`) when the update on record was past its `cutover`, or failed or was deferred for a reason of its own. hostkeeper then ran `rollback` with the same params, which refused them (`bad_params`, the params name one update and the record another), and halted the service; every later order met the same record.

A `prepare` that finds another update past its `cutover`, and a `rollback` that finds another update in flight, first roll that update back with its own target and releases, when it is not committed and returns the host to the release the params name as the previous one (its `from` is `updater.previous_release`). That rollback is exactly the `rollback` of the update on record, with the params it was written under: its staged release and version from the record, and the params' previous release, which is its own. The step then runs on the record at rest, and its detail begins with `the record is of the update to <release> <version>, not <release> <version>: rolled back with its own target and releases (<what the rollback said>)`. A `prepare` then prepares its own update; a `rollback` then has nothing to roll back. A rollback that does not finish (it defers with `draining`, or fails) leaves the record as it was, and its detail begins with the same words followed by `and its rollback with its own target and releases is not done`; the next run goes on from there.

- **What it cannot lose.** The rollback is the one hostkeeper would have run, so what it keeps serving is what the `rollback` step keeps. On systemd the instance of the release the update started from (`live`) is the one that serves at the end: a hand-over gives it the sockets back from the instance the update started, which drains and ends by itself and is never stopped (the step defers with `draining` while both run); in a restart the new instance is stopped and `live` started, as any restart has a gap. The config hook's change applied in place sets the cap of the file that served again, and starts or stops nothing. On a Mac whose job already serves the release the update started from (the boot step loaded it again), nothing is booted out or in: the binary of that release is put back, the fs job is booted in when it is not loaded, and only the record changes.
- **The staged release of the update on record.** It is not read: on systemd the rollback uses only the previous release (the one `current` names, which hostkeeper keeps) and the units, and the config hook's reload uses neither. On a Mac whose job already serves the previous release it is not read either. On a Mac whose job still runs the update's release, between releases that may hand over, the way back is decided by asking the staged and the previous release as the `rollback` step does: a staged release that is gone fails the step with `host_failed`, naming it, with the job left serving as it is, and the record kept.
- **Kept, as before.** A record that is committed is never rolled back: `prepare` finishes it on systemd (see [prepare](update-hook.md#prepare)), and a `rollback` finds nothing to roll back (on launchd it is `committed`). A record of the update the params name is that update's, as before. A `prepare` over another update that never reached `cutover` prepares over it, as before. `cutover`, `verify` and `cleanup` of another update are refused (`bad_params`) whatever the params name: hostkeeper runs them only after a `prepare` of their own update succeeded, so another update's record there is a second order racing the first. A first install of another update is kept: its rollback stops the only instance, which only its own params may do. An update whose `from` is not the params' previous release is kept, and its `rollback` says why: an update still in its `cutover` returns the host to its `from` while hostkeeper has moved `current` to its staged release, so a second order names that staged release as the previous one. The config hook's reload names no `from`: it is kept when the params name its staged package as the previous one, and for a node's first config package. A kept record is refused as before (`out_of_order` for `prepare`, `bad_params` for `rollback`, with why at the end of the detail).

## The record

`state.json` in `/var/lib/tierstore-hook` (the state directory, `STATE_DIR`), which only root can use; the hook makes it when it is absent, and neither hostkeeper nor `uninstall` removes it. It is replaced whole (a temporary file, synced, renamed over) under an exclusive lock, so two steps never run at once: a step that finds the lock held fails with `locked`. The record is JSON with `schema` 1, `kind` `single`, `updating`, `from`, `to`, `version`, `markers` (`swapped`, `verified`, `stopping`, in that order of need), and on systemd `live`, `next` and `mode`. The keys `fs_live`, `fs_next` and `fs_switch` of the earlier two-process layout are read and never written (see [the second unit](update-hook.md#the-second-unit-tierstore-fs)). `reload` is an optional key, written only when set, so that the schema stays 1 and a hook of the previous release reads this record and ignores it; it, the config hook's key of a change applied in place (below), which never goes with `next`, `mode`, `fs_next` or `fs_switch` (`state_invalid`). `swapped` and `verified` follow their acts; `stopping` is written before its act. A record that does not decode, names an instance that is not `a` or `b`, names `fs_next` with no `fs_live` or outside an update (the keys of the earlier layout are still held to their rules), names the same instance as `fs_live` and `fs_next`, or has markers out of order is `state_invalid`, and nothing else is touched. A key the hook does not know is ignored.

## The start markers

`/var/lib/tierstore` (`MARKER_DIR`) is the template's `StateDirectory`: it holds the markers `run-a` and `run-b` (and, on a node of the earlier layout, `run-fs-a` and `run-fs-b` of the second unit, which the hook only looks at), and the hand-over socket. The hook makes it with mode 0700 when it is absent, writes a marker as a regular file and never follows a link. A marker that is a directory or a link is an error (`state_io`).

## The hand-over socket

A hand-over needs a control socket, a Unix socket in a directory the service owns. A node's configuration need not name it: without the `handoff_socket` key in the `[server]` table, the socket is `handoff.sock` in the unit's state directory, `/var/lib/tierstore/handoff.sock` (the process finds the directory in `STATE_DIRECTORY`, which systemd sets for the template's `StateDirectory=tierstore`; a process started without it, as on a Mac, makes no control socket). A key that names another path wins. The new instance connects to the socket, takes the listening sockets and then binds the path itself. A hand-over also needs both releases to list the capability `handoff-socket-v1` in `tierstore --capabilities`. For a configuration with a top-level `[local_cache]` table (a build node, or a storage node with a cache), both releases must also list `handoff-cache-v1`. For a configuration that leaves `handoff_socket` out, both must also list `handoff-state-dir-v1`: a running release without it would have no control socket to take from. When any of these is missing, the update is a restart, which `prepare` records as the mode. An empty or non-string `handoff_socket` is refused with `handoff_not_configured`, whatever the shape, unless the params force a restart or the hot tier is a directory.

This binary has the hand-over socket and lists `handoff-socket-v1`: the new instance takes the sockets of the running one over `server.handoff_socket`, waiting at most `server.handoff_wait` (10s) for it to hand them over (see [Live update by hand-off of the sockets](operations.md#live-update-by-hand-off-of-the-sockets)). An update from a release that does not list it is still a restart. A build node and a storage node with `[local_cache]` hand over too, and this binary lists `handoff-cache-v1` for it. The update to this release from v0.3.47 or an earlier one, of a node with `[local_cache]`, is a restart, and its params must say `mode = "restart"`: that release refuses the key in that shape, so the configuration cannot have it yet, and its instance has no control socket. Later updates of such a node hand over, once the key is in the configuration (see [The order of releases](update-hook.md#the-order-of-releases)).

`mode = "restart"` in the manifest's params forces a restart. A storage node whose hot tier is a directory (`[hot_store]` `kind = "dir"`) is a restart whatever the params say: the lease's compare-and-swap there is atomic within one process only, so two instances must never run side by side. `prepare` reads `kind` of `[hot_store]` from the configuration the hook is given in `config_file`; a first install, which hands nothing over, reads nothing.

### The order of releases

A release that refuses `server.handoff_socket` on a build node or a storage node with `[local_cache]` (v0.3.47 and earlier) exits 2 at start when the key is there, and the unit's `RestartPreventExitStatus=2 3` then keeps it from being started again. So the key goes in by this order:

1. The first release that accepts the key on every shape of node (it lists `handoff-cache-v1`) goes in with `mode = "restart"` in the manifest's params. A restart needs no `handoff_socket` key, and the configuration still has none.
2. Only when that release is live is `server.handoff_socket` added to the node's configuration. While the live release still refuses the key, `prepare` of any update refuses the edited configuration with `config_refused`, naming the previous release, before anything is stopped.
3. The next release, whose manifest has no `mode = "restart"`, is the first hand-over: both releases list the capabilities, and the configuration has the key.

## The reasons

`reason` is a token of lowercase letters, digits and `_`. The class decides whether the fleet rolls back: `release` blames the new version, `environment` the host or the hook's inputs.

| Reason | Class | Meaning |
| --- | --- | --- |
| `bad_args` | environment | the command line was refused, or the artifact is not the staged release |
| `bad_params` | environment | the params file is unreadable or wrong, or names another update than the record's |
| `locked` | environment | another step holds the lock of the state directory |
| `state_invalid` | environment | the record is not as the hook requires |
| `out_of_order` | release | the step does not follow from the record: `cutover` before `prepare`, a `prepare` past `cutover`, and so on |
| `not_verified` | release | `cleanup` before a `verify` succeeded |
| `committed` | release | `rollback` after `cleanup` began |
| `not_confirmed` | release | `cleanup` could not confirm, freshly, that the new release serves; nothing was committed |
| `host_not_ready` | environment | both instances run; try again later (75) |
| `draining` | environment | in `rollback`, an instance that gave its sockets away is still draining (75); `cleanup` does not use it |
| `not_ready` | release | `/readyz` on 9300 was not answered with 200, or the new instance is not running, or, on a Mac, the mount is still listed after the fs job was booted out, or, in `verify`, the mount provider does not answer a call of the mount check or a read of one of its trees does not end within its bound (or the NFS front answers it `NFS3ERR_JUKEBOX`); try again (75), until `verify_deadline_secs` |
| `probe_failed` | release | 9300 was never answered by the release with the target version |
| `wrong_build` | release | the build gauge on 9300 is not the target version |
| `handoff_not_configured` | environment | the configuration has a `handoff_socket` key in `[server]` that is empty or not a string, or cannot be read as TOML |
| `config_missing` | environment | there is no file at `config_file`, or, on a Mac that names the fs job, none at `/usr/local/tierstore/etc/fs.toml` |
| `config_refused` | environment | the staged or the previous release refuses the configuration at `config_file` when it checks it (`--check-config` exits 2); the detail names the release and the line. On a Mac that names the fs job: `/usr/local/tierstore/etc/fs.toml` is not TOML, or its `fs.mountpoint` is not an absolute path |
| `service_manager_unknown` | release | `service_manager` names a manager the hook does not drive |
| `no_previous_release` | release | `rollback` of a first install: there is nothing to go back to; the instance `cutover` started is stopped |
| `unit_failed` | environment | a unit or the launchd job could not be started, stopped or asked |
| `state_io` | environment | the record or a start marker could not be read or written |
| `host_failed` | environment | the host could not be asked: the configuration, or `--capabilities` or `--check-config` of a release (no binary at `bin/tierstore` or `tree/usr/libexec/tierstore/tierstore`, on launchd `tree/Library/Application Support/tierstore/bin/tierstore`, cannot be run, exits any status but its answer, or does not end), or a root hook cannot find the service account its check runs as (`tierstore` in `/etc/passwd` on systemd, `_tierstore` in the directory service on launchd); or the binary of an archive release cannot be copied to, or removed from, `/usr/local/libexec/tierstore/tierstore` (a binary that is a link, not root's, or writable by a group or others; a directory on the way that is a link, not root's, or writable by others, or by its group for the copy's own directory; or a write that fails), or, on a Mac, the copy at `/usr/local/libexec/tierstore/tierstore-check` that a check of a release of the installer package runs cannot be made or removed (the same causes) |
| `provider_refused` | release | `verify`: on a node with a mount provider, the provider refused a call of the mount check (any status but `UNAVAILABLE`) for one of the check's two trees, which are of the forms the build service writes, with an L2 sidecar and without one: the node's jobs would be refused the same way; the detail has the call, the tree, the status and the provider's reason |
| `mounted_tree_wrong` | release | `verify`: a tree of the mount check read back wrong (through the mount, or on a Mac from the node's NFS front: a path missing, of another kind or not in the tree, a file of other bytes, a link to another target) or no tree of the check (more paths or a larger file than it has, a path of no kind of a tree, a name that is not UTF-8), a read of it answered with an error by the system or the front (not deferred: the check's objects are read from memory), a `Mount` answered a directory outside the provider's mount, or a placement outlived its release |
| `provider_busy` | environment | `verify`: on a node with a mount provider, the provider answered a call of the mount check `UNAVAILABLE`: it holds `trees.max_sources` sources, `trees.max_placements` placements are alive, its preparations were all taken past the `Mount`'s wait, or the node's file has no `fs` interface; try again (75), until `verify_deadline_secs` |
| `mode_unsupported` | environment | `prepare`: the node still runs the two-process layout (a `tierstore-fs@` unit running, a `run-fs-` marker, or a record that names `fs_live`; the same refusal for a record of an update in flight that names `fs_next` or says `fs_switch`, and for a config update that would be the switch to one process): switch it to the `fs` interface with the earlier release first; or the node's file has an `fs` interface (the node holds a mount) and the update cannot hand the mount over: on Linux the two releases do not both list `handoff-service-v1`, on a Mac they do not both list `handoff-exec-v1`, or a config update moves the mount point, the control socket or the runtime directory of the interface. On launchd also: the file has a `mount-provider` interface and no `fs` interface (the two-process layout), whose mount no release since 0.3.196 serves; the detail says to switch the node to one process first (`mode = "restart"` does not override this). A restart would drop the mount under running jobs; nothing is recorded or stopped. `mode = "restart"` in the params overrides it, for an operator who has drained the node's jobs |

## The config hook

`tierstore config-hook` is the hook of a **config package**: a package of one host group that replaces only the node's configuration files (`/etc/tierstore/config.toml` and the network guard's file beside it on Linux, `/usr/local/tierstore/etc/tierstore.toml` on a Mac) and carries no binary. hostkeeper runs it as it runs this hook: the same command line (`tierstore config-hook <step> [<staged release>] --params <file>`), the same params file, exit statuses, last line and reasons. Its steps are `prepare`, `cutover`, `verify`, `rollback`, `cleanup` and `uninstall`; it has no boot step, and `restore` is refused (`bad_args`).

The params may leave out `config_file` and `service_manager`: on Linux the file is `/etc/tierstore/config.toml` and the manager systemd; on a Mac the file is `/usr/local/tierstore/etc/tierstore.toml` and the manager launchd, with the job `tierstore`. What the params name is kept.

The release does not change, so the version every step looks for in the build gauge is the build of the binary that runs the hook: run it as the service's installed binary (`/usr/libexec/tierstore/tierstore config-hook` with the Debian or RPM package, `/usr/local/libexec/tierstore/tierstore config-hook` with the archive package), and every check of a configuration is that binary's `--check-config`. hostkeeper runs a hook program that the package itself installs, so a config package ships a one-line wrapper as its `hook.command` that runs the installed binary with its own arguments (`exec /usr/libexec/tierstore/tierstore config-hook "$@"`). The steps move the same instances as an update of the release. On systemd the arm's `prepare` refuses a node that still runs the two-process layout, a config update as well (see [the second unit](update-hook.md#the-second-unit-tierstore-fs)), and no step starts or stops an fs unit; a change applied in place (below) moves no instance, and so is not refused:

- `prepare` refuses (`out_of_order`) while an update of the release is in flight. It has the binary check the file the package staged, `<staged release>/tree/<config file>`, before it is installed (`config_missing` when the package stages none, `config_refused` with the binary's line when it refuses it). The staged package is closed to every user but root, so the hook reads the staged file and hands its text to the check: on Linux in a file in memory that the check inherits and reads at `/proc/self/fd/<n>` (standard input would not do: the account may not reopen a pipe that root made), on a Mac on its standard input (`--config /dev/stdin`). The file that `verify` checks, the installed one, is named by its path. It chooses a hand-over when the file that serves and the staged one have the same `[[interface]]` tables (the `fs` interface apart: its params do not count, so a hand-over keeps the mount when only they change), the same listening keys of `[server]` and the same `server.handoff_socket`, and neither has a hot tier of kind `dir`; otherwise, or with `mode = "restart"`, a restart. It refuses with `mode_unsupported`, and records nothing, a staged file that would be the switch of a node that still runs the fs unit of the earlier layout on Linux (see below), and a staged file with an `fs` interface that would drop or move a mount: when the file that serves has an `fs` interface too and the staged one names another `mountpoint`, `control_socket` or `runtime_dir` (the process that takes the mount would answer `nak`), and when the change must be a restart while the node holds a mount (the file that serves has an `fs` interface, or the switch below applies). `mode = "restart"` overrides it, for an operator who has drained the node's jobs. Nothing is started. On systemd, a change the instance that serves can apply is recorded as one applied in place instead of a hand-over or a restart (below).
- `cutover` reloads the network guard first (`systemctl reload-or-restart tierstore-guard.service`, only on a node that has the guard's file), then starts the other instance on the new file, by the hand-over or the restart of an update. On a Mac it boots the job out and bootstraps it. For the switch, see below.
- `verify` has the binary check the installed file (`config_refused`), then observes `/readyz` and the build, as for an update. For the switch of a Mac it also requires the mount listed at the mount point of the installed file.
- Every check of a file runs, when the hook is root, as the account the service runs as, because the check refuses key files that the user it runs as does not own. On Linux (systemd) that is `tierstore`, found in `/etc/passwd`, as for an update. On a Mac (launchd) it is `_tierstore`, the job's `UserName`, which the package's postinstall makes in the directory service and not in `/etc/passwd`. The hook reads its ids, `UniqueID` and `PrimaryGroupID`, from the user record `_tierstore` of the local directory with `/usr/bin/dscl . -read`. An account that is not there, or a `dscl` that fails or prints no numeric ids, fails the step with `host_failed`, and the detail names the account and the `dscl` call. On Linux the check is started under the account's user and group ids; on a Mac it is started as `/usr/bin/sudo -n -u #<UniqueID> -- <binary> --config <file> --check-config` (for a release of the macOS installer package, `<binary>` is the copy at `/usr/local/libexec/tierstore/tierstore-check`), so that it has the account's groups, as the job has them from launchd (started under the ids alone, it would have the effective group 0 on macOS and could not enter `/usr/local/tierstore/etc`, root:`_tierstore` mode 0750). `sudo` needs only the stock rule that lets root run anything as any user; a `sudo` that refuses exits 1, which fails the step with `host_failed` and is never taken for a refusal of the file. A hook that is not root runs the check as itself.
- `rollback` comes after hostkeeper has put the previous package's files back: it reloads the guard and hands back to the instance that served (the switch of a Mac: below). A node's first config package has no files to go back to (hostkeeper takes the package and its files off the node): the rollback leaves the instance that runs serving on what it read, records nothing in flight, and fails with `no_previous_release`; the node needs a configuration before its next start.
- `cleanup` commits and finishes the update without waiting for the old instance to drain, as for an update, and writes the instance that now serves into the release's record (`state.json`), which `restore` reads at boot.
- `uninstall` changes nothing: the service keeps the configuration it read.

### The switch to one process

A config package whose staged file has an `fs` interface, on a node whose file that serves has none and whose `tierstore-fs` process of the old layout runs (on a Mac: the `tierstore-fs` job is loaded), moves the mount to the one process of the new file (`docs/design/one-service.md` sections 4.2 and 4.3). Where no fs process runs (or, on a Mac, the `tierstore-fs` job is not loaded), the package is an ordinary config update.

- **Linux.** This release has no step for the fs unit, so `prepare` refuses the switch with `mode_unsupported`, whatever the params' `mode` says, and records, starts and stops nothing. The detail names the unit that runs (`this node still runs the two-process layout (tierstore-fs@<instance>.service is active): switch this node to the fs interface with release M first`); the node is switched by the earlier release that does it, and this one then updates it. The record keys `fs_live`, `fs_next` and `fs_switch` of an earlier release's switch are only read.
- **macOS.** The switch is a restart, as every update of a Mac that unmounts: the Mac is drained by the operator, and the arm is run with a declared restart. `prepare` records `fs_switch`. `cutover` boots the `tierstore-fs` job out (as `cutover` of an update does, with the same bounds), checks that its mount, the one `/usr/local/tierstore/etc/fs.toml` names, is gone (a mount that stays boots the fs job in again and ends the step with `not_ready`, nothing else stopped and the job not disabled), disables the job (`launchctl disable system/tierstore-fs`, kept across reboots, so the plist that the installed package still has never starts it again), then boots the main job out and in on the new file, which mounts and serves. `rollback` enables the job first, then runs the old restart: fs job out (not loaded: nothing), main job out and in on the old file, fs job in.

### A change applied in place

On systemd, a config package whose staged file differs from the file that serves in nothing but `tree_list_ram_bytes` of the `fs` interface (`fs.tree_list_ram_bytes`), or in nothing at all, starts no other instance: the instance that serves applies it, keeps its mapped tree lists, and does not scan its cache again. The two files are compared as TOML tables with that param taken out (a file that names none has the default, 512 MiB, and a params table left with nothing else is as none), so a byte-identical file, or one that differs only in comments, spacing or the order of its keys, is the case with nothing to set. The guard is reloaded only when the package's guard file differs from the installed one. Nothing moves, so the refusals of `prepare` above (of a change that must restart a node that holds a mount, or moves its mount) do not apply: a node with a hot tier of kind `dir` takes such a package in place too. Any other difference, a file that is not TOML, a cap that is not a whole number of bytes, params that say `mode = "restart"` (an operator who asks for a restart gets one), a node where no instance or both run and a config record with an update of the other kind in flight, take the ways above, refusals included. A Mac restarts its job for every config package, as before.

- `prepare` records the update with the optional record key `reload` (written only when set) and no `next` or `mode`: whether the guard's file changes, and, when the cap changes, the value of the file that serves (`from`), of the staged one (`to`) and the control socket of the `fs` interface. Nothing is started. A `prepare` run again over the reload it recorded keeps it, even once hostkeeper has installed the staged file.
- `cutover` reloads the guard when its file changed, then sends `set tree_list_ram_bytes <to>` to the control socket of the instance that serves (`fs.control_socket`; see [operations](operations.md#the-virtual-build-file-system)), which answers with the id of its mount, and records `swapped` with that mount. A socket that cannot be reached, or does not take the value, fails the step with `host_failed`. Run again, it sets the same value again. No unit is started or stopped and no marker changes.
- `verify` has the binary check the installed file, requires the instance that serves active (`not_ready`), observes `/readyz` and the build as for an update (deferred, `not_ready`, while its cache is read-only), and reads the value back from the gauge `tierstore_fs_tree_list_ram_bytes` of that mount on `/metricz`; while the gauge shows another value (the mount tells the node's cache at once) the step is deferred (`not_ready`, after `verify_retry_secs`).
- `rollback`, before the commit, reloads the guard again when its file changed (not for a node's first config package), and sets `from` again, unless the instance that serves no longer runs, whose start reads the file hostkeeper put back. A node's first config package still fails with `no_previous_release`, its record at rest. A reload of another package whose updater is gone is rolled back the same way by the next package's `rollback`, and by its `prepare` when it is past its `cutover` (see [an update whose updater is gone](update-hook.md#an-update-whose-updater-is-gone)).
- `cleanup` confirms afresh that the instance that serves is active and answers with the build (`not_confirmed`), then records the commit and the update at rest in one write, with the same instance serving, and writes it into the release's record as above.

The config hook keeps its own record, `config-state.json`, beside `state.json` in `/var/lib/tierstore-hook` and under the same lock, so a config update never changes the release's `to`, `version` or promotion.

## First install

A `prepare` whose params have no previous release is a first install. The hook copies the binary to `/usr/local/libexec/tierstore/tierstore` (an archive release) and starts `tierstore@a` (or bootstraps the job) with a normal bind. If it fails and hostkeeper rolls back, the instance is stopped and the copy removed, the step exits 1 with `no_previous_release`, and no instance is left running. On a Mac, a first install that finds the job already loaded (a copy installed by hand, stopped or running) boots it out before it bootstraps the job, with the fs job and its mount first, as an update does; its rollback then stops that job too, so `no_previous_release` with the job stopped is what the host is.

## What the hook leaves to hostkeeper

hostkeeper's hookless Force starts every `run` unit of the package and waits for every one of them to be active. A standby instance is inactive by design (it has no marker), so a Force reports a failure while tierstore serves. hostkeeper's observer treats one active unit as the service being live. Nothing in the hook changes that: a Force is not a hook step.

## Limits

- Hand-over needs both releases to list `handoff-socket-v1` (and, for a configuration with a top-level `[local_cache]` table, `handoff-cache-v1`); the first update from a release that does not is a restart, and so is the first update to a release from one that does not list `handoff-state-dir-v1`, when the configuration leaves `handoff_socket` out.
- A host with a `dir:` hot tier always restarts; the hook reads the tier's kind from the configuration.
- On macOS an update that restarts the job has a gap in serving while it restarts, and, when the params name the fs job, the file tree's mount is absent while the fs job is out: a job that reads a tree through it in that gap fails to find the mount, and none hangs on it. The hand-over to the next image has a pause instead: nothing is accepted from the drain to the start of the new image, the clients wait in the sockets' backlogs, and the mount of a node whose file has an `fs` interface stays.
- The hook has no step for the second unit of the earlier layout, `tierstore-fs@.service`: a node that still runs it is refused, and an update never stops or starts it (see [the second unit](update-hook.md#the-second-unit-tierstore-fs)).
