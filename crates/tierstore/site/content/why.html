Why tierstore

Some stores are big and slow, and some are small and fast. tierstore puts the fast one in front of the slow one and presents both as a single S3 bucket, so that a client does not choose.

The problem

An object store on large, cheap capacity (hard disks, or a remote S3 service) is the right place to keep objects for good, and a poor place to take every write as it arrives. A small store on fast storage (local flash, say) takes writes well and cannot hold everything. Two ways to combine them are common and both leak into the client: write to one store and read from the other, or run a different tool that moves data between them.

tierstore does the combining in one process that speaks S3. A build daemon, a job with a presigned URL and a person with an SDK all talk to the same endpoint with the same calls.

No benchmark numbers on this site. The repository does not publish a measured comparison of tierstore against a single store, so this page makes no claim about speed. It says how the tiers behave, which the code and its tests show.

The shape

  • Hot tier: where new objects are written first. It is meant to hold a bounded number of bytes (hot_store.budget).
  • Cold tier: where every object ends up. It is large.
  • The proxy serves the one bucket and keeps no database. Its only state is a set of entry, registration and lease objects in the hot tier (and, under the marker format, a marker for each key in a marks bucket). Any number of proxies, each with an id of its own, can run over the same two tiers.
  • The reconciler runs inside each process but works only while it holds a lease object in the hot tier, so one runs at a time.

A tier is a bucket of an S3-compatible store, a directory, or memory (memory keeps nothing when the process stops).

Writes: hot first, cold in the background

On a store on the entry format a put is refused if the key exists in either tier. Otherwise the object is written to the hot tier, and the put is acknowledged only after the entry of its key (_entries/<digest of the key>) says it landed in the hot tier. So an acknowledgement is as durable as a write to the hot tier. The reconciler then works the entries and copies each put to the cold tier, in parallel and with create-only writes. A delete removes the object from both tiers. On a store on the newer marker format (active-marks) a plain put of a key that exists replaces it, and If-None-Match: * still creates only; the operator guide says which format a store is on. A multipart upload goes straight to the cold tier, part by part, and is never staged in the proxy.

That is a write-back arrangement: the cold copy trails the acknowledgement. When the hot tier is full, the proxy writes new objects straight to the cold tier instead, which is write-through for those objects.

Freeing the hot tier

When the hot tier passes its high-water mark (80 percent of hot_store.budget by default), the reconciler evicts the oldest objects from it, only those that the cold tier already holds, until usage is down to the low-water mark (70 percent by default). Above the critical mark (95 percent by default) a read of a cold object is not copied back. The reconciler never lists the data prefixes: what to copy comes from the entries, so neither tier's data is scanned.

Reads: hot, then cold, and copy back

A get reads the hot tier, then the cold tier, and copies what it found in the cold tier back into the hot tier. A head does not copy. A listing merges both tiers. A ranged read that misses the hot tier reads the whole object from the cold tier, because the hot tier takes whole objects, and cuts the range from it.

The copy-back means the hot tier also works as a read cache of what was used lately. On a storage node that is the only caching.

The per-node read-through cache is a build node

The crate has a CachedStore, a read cache in RAM for any backend. The tierstore binary does not use it. Its per-node cache is on disk: a configuration file with [local_cache] and [cold_store] and no [hot_store] runs the binary as a read cache in front of one upstream. It serves GET and HEAD of the keys that a [[policy]] with cache = true holds from a directory of raw files, fills it from the upstream on a miss, evicts the least recently used objects under a byte budget, refuses every write, and does not scrub. It has no flag form. See configuration.

What keeps it honest

  • A stated contract with the stores: tierstore is a proxy over a hot and a cold store and does not test them. The hot store must give atomic conditional PUTs (create-only and If-Match) and strong read-after-write for GET, HEAD and LIST, and the cold store the same create-only PUT and an atomic If-Match PUT; Amazon S3, MinIO (conditional PUT) and tierstore's own directory store (within one process) are known to meet this. Nothing verifies it. See operations.
  • Key roles limit what a client may do: full, read-only, presigning (one object under a prefix), garbage collection and scoped keys. See configuration.
  • Objects are byte strings under string keys. On a store on the entry format they are written once; on the marker format a plain put replaces the key.

Where it stops

The S3 front serves one bucket, path-style, over plain HTTP, or over HTTPS when server.tls_cert_file and server.tls_key_file are set. It does not do session tokens or STS. Its /metricz serves the counters of the OCI read front, those of the local cache of a build node and, on main, hit, miss and byte counters of the two tiers (the reconciler's hot-tier size and copy lag are values in the library, not exported), and, on main, the tierstore_build_info gauge (which version and commit answered) and tierstore_drain_late_requests_total (connections that wrote after the drain shut their end); the operator guide says what is there. It is early software: read what is built and what is not before you depend on it.
