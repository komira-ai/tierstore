Install

tierstore is a binary for Linux (x86_64 and arm64) and macOS (Apple silicon). It ships from the releases of this repository: every release carries the tarball, its provenance bundle and its checksum. There is no package and no container image, and nothing updates it afterwards.

Where the code lives. The source is crates/tierstore in komira-ai/tierstore, and the packaging notes are in packaging. tierstore began in kbf: versions up to 0.2.0 were built there, and the release history of those versions is kbf's. From 0.3.0 on, every release is built and signed here.

  1. Take the tarball of your architecture works today

    A release lists tierstore-<commit>-linux-x86_64.tar.gz, tierstore-<commit>-linux-arm64.tar.gz and tierstore-<commit>-macos-arm64.tar.gz, each with a .sigstore.json bundle, and all of them in SHA256SUMS. Take the one for the host by its digest.

    <commit> is the full 40-hex SHA of the commit the release was built from. Find it in the release's asset list, or in SHA256SUMS, where each line is a digest and a file name, so the name of a tierstore tarball carries it. For instance, with the example SHA 0123456789abcdef0123456789abcdef01234567:

    tierstore-0123456789abcdef0123456789abcdef01234567-linux-x86_64.tar.gz
tierstore-0123456789abcdef0123456789abcdef01234567-linux-arm64.tar.gz
tierstore-0123456789abcdef0123456789abcdef01234567-macos-arm64.tar.gz

  2. Verify it works today

    Three checks, in this order: the first proves the download is intact, the second or the third that this repository built and signed it. The second needs gh; the third needs only cosign, for a host whose gh has no gh attestation command. Take the tarball's .sigstore.json bundle and SHA256SUMS from the same release; below, <tarball> is the tarball's file name.

    Integrity. SHA256SUMS lists the tarballs and SBOMs of every platform, so --ignore-missing skips the ones you did not take:

    $ sha256sum -c --ignore-missing SHA256SUMS

    SHA256SUMS is not itself an attestation subject, so this check proves integrity, not authenticity: who built the file is what the next check proves.

    Authenticity with gh. This needs a gh that has the gh attestation command (Ubuntu 24.04's packaged gh, 2.46.0, does not: use the check without gh there). Check the tarball against the workflow of this repository that signed it:

    $ gh attestation verify tierstore-<commit>-linux-x86_64.tar.gz --repo komira-ai/tierstore \
    --signer-workflow komira-ai/tierstore/.github/workflows/artifacts.yml \
    --source-ref refs/heads/main --source-digest <commit> --deny-self-hosted-runners

    <commit> is the full SHA in the tarball's name; --source-digest makes the check prove the build came from that commit, not only from the main workflow.

    Authenticity without gh. This needs only cosign, and checks the tarball against its .sigstore.json bundle; it prints Verified OK.

    $ cosign verify-blob-attestation \
    --bundle <tarball>.sigstore.json \
    --type slsaprovenance1 \
    --certificate-identity-regexp '^https://github.com/komira-ai/tierstore/\.github/workflows/artifacts\.yml@refs/heads/main$' \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com \
    <tarball>

    --type slsaprovenance1 is required: the bundle holds SLSA provenance v1, and with cosign's default type the check fails with "invalid predicate type".

    With a gh that has gh attestation on a host with no network, verify against the bundle and a trusted root fetched beforehand on a host that has one, and copied over with the tarball:

    $ gh attestation trusted-root > trusted_root.jsonl
$ gh attestation verify <tarball> --repo komira-ai/tierstore \
    --bundle <tarball>.sigstore.json --custom-trusted-root trusted_root.jsonl \
    --signer-workflow komira-ai/tierstore/.github/workflows/artifacts.yml \
    --source-ref refs/heads/main --source-digest <commit> --deny-self-hosted-runners

    Every check names one signer: the workflow file .github/workflows/artifacts.yml of this repository, run on refs/heads/main. That identity is part of what a release promises: if the file were renamed or moved, every command here would fail. docs/ci-and-release.md lists the files of a release and what each attests.

  3. On macOS (Apple silicon) works today

    The macOS binary is tierstore-<commit>-macos-arm64.tar.gz, built and signed by the same workflow as the Linux ones and checked the same way. It is built on a macOS 15 runner on Apple silicon, which runs it before it is packaged and refuses it unless it reports the version and the commit of the release. This step covers taking and verifying it; running tierstore as a service on macOS is not described here, and the update hook is Linux only.

    Take the tarball, its bundle and SHA256SUMS from one release, with gh (Homebrew's gh has gh attestation) or with curl, and check its digest with shasum, which every Mac has; it prints OK:

    $ gh release download v<X.Y.Z> --repo komira-ai/tierstore \
    --pattern 'tierstore-*-macos-arm64.tar.gz*' --pattern SHA256SUMS
$ grep -- '-macos-arm64\.tar\.gz$' SHA256SUMS | shasum -a 256 -c

    Then check that this repository built and signed it, offline against its bundle: run the offline check above (gh attestation trusted-root on a host with a network, then gh attestation verify with --bundle and --custom-trusted-root), with <tarball> set to tierstore-<commit>-macos-arm64.tar.gz. cosign's check without gh works the same way.

    The binary is not notarized by Apple. It is ad-hoc signed by the linker, as every binary for Apple silicon must be to run. gh release download and curl save it without the quarantine attribute, so macOS runs it as it runs any program installed from the command line, as a Linux host runs a binary fetched with curl; a file saved by a web browser carries the attribute, and macOS then refuses to open it because it is not notarized. Take it with gh or curl. Its authenticity is what the checks above prove, not an Apple signature.

    $ tar -xzf tierstore-<commit>-macos-arm64.tar.gz tierstore
$ ./tierstore --version

    On a Mac, this is the last step. The steps after it (the placement under /usr/libexec, the systemd unit, the sysusers account, the key files' owner and the start) are for a Linux host.

  4. Place the binary works today Linux

    The tarball holds one member, the binary under its own name.

    $ tar -xzf tierstore-<commit>-linux-x86_64.tar.gz tierstore
$ install -d -m 0755 /usr/libexec/kbf
$ install -m 0755 -o root -g root tierstore /usr/libexec/kbf/tierstore

    The host updater (kbf-updater, kbf-host-install) does not manage tierstore yet. To move to the next release, place the next binary the same way and restart the unit.

  5. Place the unit works today Linux

    The repository has an example systemd unit, tierstore.service, and a sysusers entry, tierstore.conf, in packaging/tierstore. The values in the unit are examples: edit the listen address, the proxy id, the buckets, the endpoints and the hot-tier size to your setup.

    $ install -m 0644 tierstore.conf /etc/sysusers.d/tierstore.conf
$ systemd-sysusers /etc/sysusers.d/tierstore.conf
$ install -d -m 0750 -o root -g tierstore /etc/tierstore
$ install -m 0644 tierstore.service /etc/systemd/system/tierstore.service
$ systemctl daemon-reload

  6. Write the key files works today Linux

    Four files, each owned by tierstore with mode 0600 or 0400 (the process refuses a key file that its group or others can read). A secret is never on the command line and the process reads no environment variable.

    • /etc/tierstore/access.key: the full key, the one clients that write sign with (--access-key-file);
    • /etc/tierstore/daemons.key: a read-only key (--read-only-key-file), which may get, head and list and nothing else;
    • /etc/tierstore/hot.credentials and /etc/tierstore/cold.credentials: the keys tierstore signs its requests to the two stores with.

    A file holds its key as JSON or as two lines, the access key id and then the secret access key. The configuration page has both forms.

  7. Start it works today Linux

    The unit does not start at install or at boot (it has no [Install] section), and it is skipped while /etc/tierstore/access.key does not exist. Start it by hand when the files are in place:

    $ systemctl start tierstore

    To start it at boot, add the section in a drop-in (systemctl edit tierstore, [Install] and WantedBy=multi-user.target) and run systemctl enable tierstore.

Using it from an S3 client

The front serves one bucket, path-style, over plain HTTP, and checks SigV4 in the Authorization header (and presigned PUT URLs). An SDK with its defaults sends some things the front refuses, so a client needs these settings. The crate's tests drive the front with aws-sdk-rust set this way; the aws CLI and boto3 are not tested.

SettingValueWhy
endpointhttp://<host>:<port> of --listenthe front has no TLS; an https:// endpoint fails
addressingpath-stylethe bucket is in the path; virtual-host addressing is not served
bucketthe --bucket namethere is one
regiontierstore's own --region, us-east-1 by defaultthe region is in the credential scope of the signature
request and response checksumswhen_requiredthe SDK default sends a checksum trailer in an aws-chunked body, which the front refuses with 501
use aws_sdk_s3::config::{Credentials, Region, RequestChecksumCalculation, ResponseChecksumValidation};

let config = aws_sdk_s3::Config::builder()
    .behavior_version_latest()
    .endpoint_url("http://tierstore.example:9000")
    .force_path_style(true)
    .region(Region::new("us-east-1"))
    .credentials_provider(Credentials::new(KEY_ID, SECRET, None, None, "static"))
    .request_checksum_calculation(RequestChecksumCalculation::WhenRequired)
    .response_checksum_validation(ResponseChecksumValidation::WhenRequired)
    .build();
let client = aws_sdk_s3::Client::from_conf(config);

From packaging/tierstore/README.md, "Using a stock SDK". That README also lists the settings read from the code and not tested.
