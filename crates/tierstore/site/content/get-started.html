Get started

Install tierstore, write a configuration file, start it and put and get an object. It takes about five minutes on one machine.

Install works today

Choose a method. The tarball works today; the script, Homebrew and apt are planned, and their tabs say so. The steps after the tabs check the download and place the binary as a service.

Take the tarball of your platform from this repository's releases, and unpack the binary.

Linux x86_64

$ gh release download --repo komira-ai/tierstore \
    --pattern 'tierstore-*-linux-x86_64.tar.gz' --pattern SHA256SUMS
$ tar -xzf tierstore-*-linux-x86_64.tar.gz tierstore
$ ./tierstore --version

$ gh release download --repo komira-ai/tierstore \
    --pattern 'tierstore-*-linux-arm64.tar.gz' --pattern SHA256SUMS

The package tierstore in the repository packages.komira.ai, shared with other Komira tools. Fetch the repository's key over HTTPS into /usr/share/keyrings, compare its fingerprint with the one the repository publishes, then write a deb822 source that trusts that file for this source only:

$ sudo install -d -m 0755 /usr/share/keyrings
$ sudo curl -fsSL https://packages.komira.ai/apt/komira-archive-keyring.gpg -o /usr/share/keyrings/komira-archive-keyring.gpg
$ gpg --show-keys --with-fingerprint /usr/share/keyrings/komira-archive-keyring.gpg
$ sudo tee /etc/apt/sources.list.d/komira.sources >/dev/null <<'EOF'
Types: deb
URIs: https://packages.komira.ai/apt
Suites: stable
Components: main
Signed-By: /usr/share/keyrings/komira-archive-keyring.gpg
EOF
$ sudo apt update
$ sudo apt install tierstore

The first fetch of the key trusts TLS once; the fingerprint is the check against it. There is no rpm package.

tierstore is a binary for Linux (x86_64 and arm64) and macOS (Apple silicon). It ships from the releases of this repository: every release carries the tarball, its provenance bundle and its checksum. There is no Homebrew formula, apt package or container image yet (a one-line script, Homebrew, apt and a copy of the release files on tierstore.dev are planned: see Not in a release yet below). hostkeeper packages exist and update it through tierstore update-hook; otherwise nothing updates it afterwards.

Where the code lives. The source is crates/tierstore in komira-ai/tierstore, and the packaging notes are in packaging. Versions up to 0.2.0 were built in another repository, and their release history is there. From 0.3.0 on, every release is built and signed here.

  1. Take the tarball of your architecture works today

    A release lists tierstore-<commit>-linux-x86_64.tar.gz, tierstore-<commit>-linux-arm64.tar.gz and tierstore-<commit>-macos-arm64.tar.gz, each with a .sigstore.json bundle, and all of them in SHA256SUMS. Take the one for the host by its digest.

    <commit> is the full 40-hex SHA of the commit the release was built from. Find it in the release's asset list, or in SHA256SUMS, where each line is a digest and a file name, so the name of a tierstore tarball carries it. For instance, with the example SHA 0123456789abcdef0123456789abcdef01234567:

    tierstore-0123456789abcdef0123456789abcdef01234567-linux-x86_64.tar.gz
tierstore-0123456789abcdef0123456789abcdef01234567-linux-arm64.tar.gz
tierstore-0123456789abcdef0123456789abcdef01234567-macos-arm64.tar.gz

  2. Verify it works today

    Three checks, in this order: the first proves the download is intact, the second or the third that this repository built and signed it. The second needs gh; the third needs only cosign, for a host whose gh has no gh attestation command. Take the tarball's .sigstore.json bundle and SHA256SUMS from the same release; below, <tarball> is the tarball's file name.

    Integrity. SHA256SUMS lists the tarballs and SBOMs of every platform, so --ignore-missing skips the ones you did not take:

    $ sha256sum -c --ignore-missing SHA256SUMS

    SHA256SUMS is not itself an attestation subject, so this check proves integrity, not authenticity: who built the file is what the next check proves.

    Authenticity with gh. This needs a gh that has the gh attestation command (Ubuntu 24.04's packaged gh, 2.46.0, does not: use the check without gh there). Check the tarball against the workflow of this repository that signed it:

    $ gh attestation verify tierstore-<commit>-linux-x86_64.tar.gz --repo komira-ai/tierstore \
    --signer-workflow komira-ai/tierstore/.github/workflows/artifacts.yml \
    --source-ref refs/heads/main --source-digest <commit> --deny-self-hosted-runners

    <commit> is the full SHA in the tarball's name; --source-digest makes the check prove the build came from that commit, not only from the main workflow.

    Authenticity without gh. This needs only cosign, and checks the tarball against its .sigstore.json bundle; it prints Verified OK.

    $ cosign verify-blob-attestation \
    --bundle <tarball>.sigstore.json \
    --type slsaprovenance1 \
    --certificate-identity-regexp '^https://github.com/komira-ai/tierstore/\.github/workflows/artifacts\.yml@refs/heads/main$' \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com \
    <tarball>

    --type slsaprovenance1 is required: the bundle holds SLSA provenance v1, and with cosign's default type the check fails with "invalid predicate type".

    With a gh that has gh attestation on a host with no network, verify against the bundle and a trusted root fetched beforehand on a host that has one, and copied over with the tarball:

    $ gh attestation trusted-root > trusted_root.jsonl
$ gh attestation verify <tarball> --repo komira-ai/tierstore \
    --bundle <tarball>.sigstore.json --custom-trusted-root trusted_root.jsonl \
    --signer-workflow komira-ai/tierstore/.github/workflows/artifacts.yml \
    --source-ref refs/heads/main --source-digest <commit> --deny-self-hosted-runners

    Every check names one signer: the workflow file .github/workflows/artifacts.yml of this repository, run on refs/heads/main. That identity is part of what a release promises: if the file were renamed or moved, every command here would fail. docs/ci-and-release.md lists the files of a release and what each attests.

  3. On macOS (Apple silicon) works today

    The macOS binary is tierstore-<commit>-macos-arm64.tar.gz, built and signed by the same workflow as the Linux ones and checked the same way. It is built on a macOS 15 runner on Apple silicon, which runs it before it is packaged and refuses it unless it reports the version and the commit of the release. This step covers taking and verifying it. A Mac runs it as a LaunchDaemon, one build node on loopback that the host updater updates by a plain restart through tierstore update-hook, with a brief gap in serving; the files and the layout are in The update hook and packaging/macos.

    Take the tarball, its bundle and SHA256SUMS from one release, with gh (Homebrew's gh has gh attestation) or with curl, and check its digest with shasum, which every Mac has; it prints OK:

    $ gh release download v<X.Y.Z> --repo komira-ai/tierstore \
    --pattern 'tierstore-*-macos-arm64.tar.gz*' --pattern SHA256SUMS
$ grep -- '-macos-arm64\.tar\.gz$' SHA256SUMS | shasum -a 256 -c

    Then check that this repository built and signed it, offline against its bundle: run the offline check above (gh attestation trusted-root on a host with a network, then gh attestation verify with --bundle and --custom-trusted-root), with <tarball> set to tierstore-<commit>-macos-arm64.tar.gz. cosign's check without gh works the same way.

    The binary is not notarized by Apple. It is ad-hoc signed by the linker, as every binary for Apple silicon must be to run. gh release download and curl save it without the quarantine attribute, so macOS runs it as it runs any program installed from the command line, as a Linux host runs a binary fetched with curl; a file saved by a web browser carries the attribute, and macOS then refuses to open it because it is not notarized. Take it with gh or curl. Its authenticity is what the checks above prove, not an Apple signature.

    $ tar -xzf tierstore-<commit>-macos-arm64.tar.gz tierstore
$ ./tierstore --version

    On a Mac, this is the last step. The steps after it (the placement under /usr/libexec, the systemd unit, the sysusers account, the key files' owner and the start) are for a Linux host.

  4. Place the binary works today Linux

    The tarball holds one member, the binary under its own name.

    $ tar -xzf tierstore-<commit>-linux-x86_64.tar.gz tierstore
$ install -d -m 0755 /usr/libexec/tierstore
$ install -m 0755 -o root -g root tierstore /usr/libexec/tierstore/tierstore

    The update hook is written for a host updater that is in development; no release carries it as a step an updater calls yet. To move to the next release, place the next binary the same way and restart the unit.

  5. Place the unit works today Linux

    The repository has an example systemd unit, tierstore.service, a configuration file, tierstore.toml, and a sysusers entry, tierstore.conf, in packaging. The values in the file are examples: edit the address of the s3 interface, the proxy id, the buckets, the endpoints and the hot-tier size to your setup.

    $ install -m 0644 tierstore.conf /etc/sysusers.d/tierstore.conf
$ systemd-sysusers /etc/sysusers.d/tierstore.conf
$ install -d -m 0750 -o root -g tierstore /etc/tierstore
$ install -m 0640 -o root -g tierstore tierstore.toml /etc/tierstore/tierstore.toml
$ install -m 0644 tierstore.service /etc/systemd/system/tierstore.service
$ systemctl daemon-reload

    Edit the installed /etc/tierstore/tierstore.toml before you start the unit: the unit reads that file and no other.

  6. Write the key files works today Linux

    Four files, each owned by tierstore with mode 0600 or 0400 (the process refuses a key file that its group or others can read). A secret is never on the command line and the process reads no environment variable.

    • /etc/tierstore/access.key: the full key, the one clients that write sign with (server.access_key_file);
    • /etc/tierstore/daemons.key: a read-only key (server.read_only_key_files), which may get, head and list and nothing else;
    • /etc/tierstore/hot.credentials and /etc/tierstore/cold.credentials: the keys tierstore signs its requests to the two stores with.

    A file holds its key as JSON or as two lines, the access key id and then the secret access key. The configuration page has both forms.

  7. Start it works today Linux

    The unit does not start at install or at boot (it has no [Install] section), and it is skipped while /etc/tierstore/access.key does not exist. If you edited the unit after the daemon-reload above, run it again: once systemd has loaded the unit it keeps that copy until the next daemon-reload, so the reload makes the edit take effect. Start it by hand when the files are in place:

    $ systemctl daemon-reload
$ systemctl start tierstore

    To start it at boot, add the section in a drop-in (systemctl edit tierstore, [Install] and WantedBy=multi-user.target) and run systemctl enable tierstore.

Configure

tierstore is configured by one TOML file, --config <file>, and nothing else for the data path. A new file sets only a few keys; everything else keeps its default until a measurement says otherwise. The reference lists every key and its default, and the configuration guide has a complete file for each shape.

KeyWhat to put
[[interface]] type, params.addresses"s3" and the address to listen on: a private address on a storage node, 127.0.0.1 on a build node
server.proxy_ida name of this process; give each process over the same tiers its own, and keep it across restarts
server.bucketthe one bucket clients see
server.access_key_filethe full key file
hot_store, cold_storethe tiers: kind = "dir" with a path, or kind = "s3" with a bucket, an endpoint and a credentials_file; hot_store.budget is the bytes the hot tier is meant to hold
local_cache.path, local_cache.budgeton a build node, the cache directory and its size

A key file is the access key id and then the secret, one on each line (or JSON). It must be owned by the account that runs tierstore with mode 0600 or 0400: a start with a key file that its group or others can read is refused.

$ printf 'AKIDEXAMPLE\nexample-secret-change-me\n' > access.key
$ chmod 0600 access.key
$ mkdir hot cold

Then a file for the shape you run. Each [[interface]] is something the process serves.

The two tiers are directories. Write this as tierstore.toml next to access.key:

[[interface]]
type   = "s3"
params = { addresses = ["127.0.0.1:9000"] }

[server]
proxy_id        = "tierstore-1"
bucket          = "tierstore"
access_key_file = "access.key"

[hot_store]
kind   = "dir"
path   = "hot"
budget = "1GiB"

[cold_store]
kind = "dir"
path = "cold"

A hot tier on SSD in front of a cold tier on spinning disks, with a read-only key for daemons that only read. Either tier may instead be kind = "s3" with a bucket, an endpoint and a credentials_file. An [[interface]] of type oci adds the read-only OCI registry front.

[[interface]]
type   = "s3"
params = { addresses = ["192.0.2.10:9000"] }

[server]
proxy_id            = "tierstore-1"
bucket              = "tierstore"
access_key_file     = "/etc/tierstore/access.key"
read_only_key_files = ["/etc/tierstore/daemons.key"]

[hot_store]
kind   = "dir"
path   = "/srv/tierstore/hot"
budget = "800GiB"

[cold_store]
kind = "dir"
path = "/srv/tierstore/cold"

A read cache on local disk in front of one upstream, with no hot tier. The upstream is [cold_store], read with a read-only key, and [[policy]] says which key prefixes are kept.

[[interface]]
type   = "s3"
params = { addresses = ["127.0.0.1:9400"] }

[server]
proxy_id        = "tierstore-cache-1"
bucket          = "tierstore"
access_key_file = "/etc/tierstore-cache/access.key"

[local_cache]
path   = "/var/lib/tierstore-cache"
budget = "40GiB"

[cold_store]
kind             = "s3"
bucket           = "tierstore"
endpoint         = "http://s3-cold.example:9000"
credentials_file = "/etc/tierstore-cache/upstream-read.key"

[[policy]]
prefix = "cas/b/"
cache  = true

One process can also be both: the storage node's two tiers with the build node's disk cache in front of them, for a single machine. Its file has [hot_store], [cold_store] and [local_cache]; the reference has an example.

Check a new file before you start with it. --check-config loads the file and reads the key files it names, binds nothing and asks no store, then exits 0 and prints nothing, or prints the refusal and exits 2.

$ ./tierstore --config tierstore.toml --check-config

Start it, then put and get an object

$ ./tierstore --config tierstore.toml

The process does not test its tiers: it opens the proxy (which reads and writes the hot tier's own state) and binds the address, then prints its version and the address it listens on. curl http://127.0.0.1:9000/readyz answers ready. Stop it with Ctrl-C: it drains and exits.

The front serves one bucket, path-style, over plain HTTP (the example file has no TLS). The key id and the secret are the two lines of access.key. The aws CLI below is told to address the bucket in the path; the other clients are under Use it from your code.

$ export AWS_ACCESS_KEY_ID=AKIDEXAMPLE AWS_SECRET_ACCESS_KEY=example-secret-change-me AWS_DEFAULT_REGION=us-east-1
$ aws configure set default.s3.addressing_style path
$ echo hello > hello.txt
$ aws --endpoint-url http://127.0.0.1:9000 s3api put-object --bucket tierstore --key hello.txt --body hello.txt
$ aws --endpoint-url http://127.0.0.1:9000 s3api get-object --bucket tierstore --key hello.txt out.txt
$ cat out.txt

Whether putting hello.txt again is refused depends on the store's format phase: on a store on the older entry format a put is create-only and the second is refused with 412; on a store on the marker format (active-marks) a plain put replaces the key, and If-None-Match: * is what makes a put create-only.

Use it from your code

Point an S3 client at the endpoint of the s3 interface, with path-style addressing, and sign with a key of tierstore. tierstore issues no credentials of its own: the key id and the secret are those of a key file you wrote (Keys and roles), the two lines of server.access_key_file for the full key, or a read-only key's for a client that only reads. Every tab below sets these:

SettingValueWhy
endpointhttp://<host>:<port> of the s3 interfacewithout server.tls_cert_file and server.tls_key_file the front has no TLS, and an https:// endpoint fails
addressingpath-stylethe bucket is in the path; virtual-hosted addressing is served only for the domains of server.domains
bucketthe server.bucket namethere is one
regiontierstore's own server.region, us-east-1 by defaultthe region is in the credential scope of the signature, and a client with another is refused 403 InvalidAccessKeyId
credentialsa static key id and secretthe front has no session tokens and no STS
checksumswhen_required (optional)keeps the client from sending a checksum with every upload; the front takes the checksums of the SDK defaults and checks them
$ export AWS_ACCESS_KEY_ID=<key id> AWS_SECRET_ACCESS_KEY=<secret> AWS_DEFAULT_REGION=us-east-1
$ aws configure set default.s3.addressing_style path
$ aws --endpoint-url http://tierstore.example:9000 s3api put-object --bucket tierstore --key hello.txt --body hello.txt
$ aws --endpoint-url http://tierstore.example:9000 s3api list-objects-v2 --bucket tierstore
